# 全量功能维度分析：解绑与耦合的实测地图

- 日期：2026-10-03
- 定位：**《顶层导航换维度与留存机制》的前置报告**。前一份只切了导航一刀，
  本份把**全部功能点**盘一遍，回答「哪些是解绑的、哪些是耦合的」，并据此定维度。
- 方法：全部结论为 **【代码事实】**，由 `grep` 实测 + `import` 语句判定得出，可复核。
  判据自身的缺陷与修正过程记录在 §6（**请连同结论一起读**）。

---

## 0. 结论速览

1. **导航不是问题本身，是症状。** 全项目 24 个业务页面里，**20 个是次级路由**，
   而其中 **6 个只有唯一入口、且入口全部在「我的」**；`/following` **零入口**。
2. **耦合错位到了一种荒谬的程度**：**小说详情页（用户真正读书的地方）不能收藏、不能稍后看**，
   但**小说介绍页（中间页）四能力齐全**。能力绑在**路由**上，不是绑在**对象**上。
3. **供给侧有 16 个 API 函数零消费者**（§3.3），**组件侧有 1 个零 import 孤儿**（`NavigationBar.vue`）。
   这些不是"还没做"，是**做了但没接上**。
4. **功能天然成 4 簇**，且这 4 簇与当前的「媒介」维度**完全正交**：
   「更新了吗」/「我存的」/「怎么找到」/「怎么调」。

| `/bookmarks` 收藏 | **1** | Me.vue |
| `/watchlist` 追更 | **1** | Me.vue |
| `/later` 稍后看 | **1** | Me.vue |
| `/mypixiv` 好P友 | **1** | Me.vue |

| `/illust/:id/tag-neighbors` 标签近邻 | 1 | IllustDetail |
| **`/following` 关注流** | **0** | 🔴 **无任何用户可达入口**，仅 `router.ts:433` 的 benchNav 调试深链 |

### 2.2 关键读数

- **入口数呈极端长尾**：一个枢纽（12）+ 一个次枢纽（5）+ **十个单入口功能**。
- **十个单入口里有六个全部指向 `Me.vue`**。这不是巧合，是结构：
  功能被**按"归属人"分组**，而不是按"用户要回答的问题"分组。
- ⚠️ **代码自己承认了这个问题**。`pages/Recommended.vue:298` 原文注释：

  > `/** 悬浮通知入口：通知页目前只能从「我的」进入，顶栏补一个直达位。 */`

  这是项目内**对"入口结构有问题"的自陈**，且解法是**局部打补丁**（在推荐页顶栏补一个），
  而不是调整分组。**这类补丁每加一个，分组错误就多藏一层。**

## 3. 维度二：耦合——能力绑在哪个对象上

### 3.1 页面 × 能力矩阵（实测）

| 页面 | 收藏 | 稍后看 | 追更 | 下载/导出 | 标签近邻 | 关注/取关 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| **IllustDetail**（插画详情） | ✓ | ✓ | ✗ | ✓ | ✓ | — |
| **NovelDetail**（小说正文） | **✗** | **✗** | ✓ | ✓ | ✗ | — |
| **NovelIntro**（小说介绍） | ✓ | ✓ | ✓ | ✓ | ✗ | — |
| **UserHome**（作者主页） | ✓ | ✗ | ✗ | ✗ | ✓ | — |

### 3.2 读出来的三处错配

| # | 错配 | 后果 |
|---|---|---|
| **A** | **小说正文页不能收藏、不能稍后看**——但介绍页可以 | 用户在读书正文时无法收藏这本书，得先退回介绍页。**能力绑在"介绍页"这个路由上，而不是绑在"这本书"这个对象上** |
| **B** | **插画详情页没有对等的"追更"** | 追更被建模为「小说系列」概念。插画的对应物是「关注作者」，但那被放在 `/following`（零入口），两边**从未在同一个视野里出现** |
| **C** | **四能力齐全的只有 NovelIntro**——而它是"介绍页"，用户很少停留 | 能力最全的页面，恰恰是使用时长最短的页面 |

### 3.3 供给侧解绑：16 个零消费者 API 函数

按「消费面含 `api/`、排除定义文件自身」实测（判据修正过程见 §6）：

| 模块 | 零消费者函数 |
|---|---|
| `auth` | `isOAuthCredsInjected` |
| `id` | `toChapterId` |
| `nativeTranslate` | `nativeTranslateModule` / `translateStream` / `classifyNativeError` / `attachTranslateFrameListener` / `translatePoll` / `abortStream` |
| `queryClient` | `createAppQueryClient` |
| `translate` | `isAzureBaseURL` / `normalizeAzureBaseURL` / `buildResponsesRequestBody` / `estimateMaxOutput` / `mapEventToChunk` / `mapUsage` |
| `ugoira` | `bytesToDataUrl` |

⚠️ **不要把这 16 个直接当死代码删**——它们多数带单测。
本报告只陈述**「供给存在但当前无产品面消费」**这一事实；
是否清理属另一件事（需逐个确认是否为"备用接线"）。

### 3.4 组件侧解绑：1 个零 import 孤儿

**`components/NavigationBar.vue` 是全仓唯一零 `import` 的组件。**
而 `components/navTabs.ts:3,6` 的注释仍写着：

> `各顶层页（Recommended/IllustList/NovelList/Me）import NAV_TABS 接入 NavigationBar`
> `NavigationBar.vue 与本包页面统一从这里导入。`

⚠️ **这两句在 ADR-0120 之后已是假话**——页面早已不接 `NavigationBar`，改接放射 FAB。
这是本仓「已登记 ≠ 已处理」的**反面**：登记本身过期了，且**没有任何门禁会变红**
（因为删掉一个注释里的 import 路径不会让任何测试失败）。

### 3.5 功能之间的零连接

`收藏`、`稍后看`、`追更`、`下载` 四个功能**彼此没有任何交叉入口**。
即：**「我存的」和「我追的」在产品里从不同时出现在一个视野中。**

实测佐证（四页的**出路径**逐个核过）：

| 功能页 | 出路径 | 备注 |
|---|---|---|
| `Bookmarks.vue` | → `/illust/:id` | 字面 `navigate()` |
| `WatchLater.vue` | → `/illust/:id` | 字面 `navigate()` |
| `Watchlist.vue` | → `openNovel(latest_content_id)` → `/novel/:id`（或 `/intro`） | ⚠️ **经 `utils/novelNavigation.ts` helper，非字面 `navigate()`** |
| `DownloadManager.vue` | 无内容出路径 | ⚠️ **这是设计使然**——它是任务控制面（`toggle/start/pause/stop`，`:191-332`），不进内容是正确的 |

⚠️ **本节两处判读修正**（避免假发现）：
① 我第一遍按字面 `navigate(` 扫描，误判「追更页和下载页无出路径」——
   实际追更页走 helper 导出入口；② 下载管理无内容出口**不是缺陷**，
   它本就是控制面，不该与「我存的东西」并列为同一类功能。
   **真正成立的结论只有一句：四者互不跳转。**

## 4. 维度三：功能天然成 4 簇（与「媒介」正交）

把 §2/§3 的功能点按**用户要回答的问题**重排，簇是自然浮现的：

### 簇 1 —「我关注的东西，更新了吗？」

| 功能 | 现状 |
|---|---|
| 关注流 `/following` | 🔴 **零入口** |
| 追更（小说系列） | 单入口（我的），**无推送** |
| 通知中心 | 2 入口，靠顶栏补丁补位 |

**三件事回答同一个问题，却分散在三个地方，其中一个根本进不去。**

### 簇 2 —「我存的东西在哪？还剩什么没看？」

| 功能 | 现状 |
|---|---|
| 收藏 | 单入口（我的） |
| 稍后看 | 单入口（我的） |
| 下载 | 2 入口，但 ⚠️ `/downloads` 是**队列控制面**（start/pause/stop），不是内容列表 |
| **继续读 / 浏览历史** | 🔴 **不存在**（旧 WebView 客户端曾有，随 ADR-0203 丢失） |

**四个功能无交叉入口（§3.5），且缺最关键的那一个。**

⚠️ **一处需要区分**：「下载」其实有两个视角——
**「我下载了哪些作品」是书架（浏览视角）**，
**「这批任务跑到哪了」是队列控制（运维视角）**。
当前项目只有后者。若要进书架，需要的是前者，**不是把 `/downloads` 挪个位置**。

### 簇 3 —「怎么找到东西？」

搜索（全局 SearchSheet，10 消费者）· 榜单（1 入口 + 开关）· 标签近邻（1 入口）· 作者主页（5 入口）· 静音标签（1 入口）

### 簇 4 —「怎么调？」

R18 / AI 可见性 · 主题色 · 网络退避 · 翻译配置（LLM endpoint）· 引擎降级提示 · 全屏模式 · WebDAV 备份

⚠️ 簇 4 里有**四项是调试/自检性质**（网络自检、引擎降级、限流退避调参），
它们与簇 1–3 的用户价值不在一个量级，**目前却和业务入口平级排在同一页**。

### 4.1 为什么「媒介」维度是错的

| 判据 | 媒介维度 | 四簇维度 |
|---|---|---|
| 同一维度内有重复吗 | **有**：推荐/插画/小说是同一批内容的三个视角 | **无**：四簇互斥且穷尽 |
| 功能能自然归位吗 | **不能**：7 个留存资产不属于任何一种媒介 | **能**：每个功能恰好归一簇 |
| 用户提问能对应吗 | 不能（用户不问「给我看小说」） | **能**（每个簇 = 一个问题） |

## 5. 由此得出的维度建议

### 5.1 顶层改成四簇中的前三簇 + 账号

| 位置 | 对应簇 | 吸收当前散落的 |
|---|---|---|
| **发现** | — | 现推荐页（媒介降为页内二级） |
| **更新** | 簇 1 | `/following`（提为顶层）+ 追更 + 通知 |
| **书架** | 簇 2 | 收藏 + 稍后看 + 继续读（新建）**浏览面**；下载的**队列控制面**留在「我的」 |
| **我的** | 簇 4 | 设置/账号，**并把调试项（网络自检/引擎降级/退避调参）降级进「高级」** |

**簇 3（搜索/榜单/标签/作者）不进顶层**——它已经是"在任何一个簇里按需调用"的动作，
符合 M3/HIG「导航承载导航、不承载操作」。

### 5.2 比换 tab 更该先做的三件事（不动顶层结构）

这三件的共同点：**它们修的是"解绑"，不是"分组"**，且都不需要新后端。

| # | 动作 | 修的是什么 | 证据 |
|---|---|---|---|
| **1** | 让 `收藏/稍后看` 在**小说正文页**可用 | 错配 A（能力绑路由不绑对象） | §3.2 |
| **2** | 给 `/following` 一个入口 | 解绑：能力在、入口无 | §2.1 |
| **3** | 给 `继续读` 重建浏览历史 | 解绑：簇 2 缺最关键能力 | §4 簇 2 |

> 顺序理由：**1、2 是"把已有的东西接上"，成本最低、收益最直接**；
> 3 需要新建。**先接上，再新建。**

### 5.3 一条方法论结论

> 本项目当前的"粘性不够高"，在功能层面可以精确定位为：
> **不是功能少，是功能之间没有连接、且一半的能力没有入口。**
>
> 换 tab 维度是**重组**；先接通已有资产是**连线**。
> **先连线，再重组**——否则重组完还是一堆进不去的入口。

| # | 判据缺陷 | 怎么发现的 | 修正 |

## 7. 本报告未证实 / 未覆盖

- **未做真机验证**：§3.1 能力矩阵、§2.1 入口数均为**代码静态实测**，
  不等于用户实际感知的可达性（用户可能不知道某个功能存在）。
- **未量化用户行为**：项目内无任何埋点（见前一份报告 §2.7），
  因此**无法回答"哪个功能实际被用得最多"**——
  本报告的"功能应当成簇"是**结构推论**，不是行为数据。
- **未评估各功能的实现成本**（除 §5.2 的定性排序外）。
- 未复核 `openwiki/` 是否有更新描述（按仓库纪律不得本地重生成）。
