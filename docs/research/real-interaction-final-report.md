> **口径声明**：全部数据来自 Android 模拟器（pictelio_ui，720×1280，Android 14，WebView 113.0.5672.136），webview flavor debug APK 4.32.0；真实手势（adb input）+ screencap 轮询/screenrecord 逐帧分析；**不以 framestats/gfxinfo 纸面指标作为体验证据**（本轮方法论根基，回应「过于注重纸面数据」的主诉）。

## 0. 用户主诉与方法论修正

主诉：「之前做过性能优化，但过于注重纸面数据了，前端的交互非常糟糕」。体检证实：四轮优化的**纸面收益在已覆盖场景真实可感知**（滚动满帧 58-60fps、渐进加载良好），但**用户实际痛点（加载等待、切换/返回卡顿）全部在纸面测量范围之外**，且优化方向（滚动跟手）与痛点错位。本轮改为：真实手势 + 录屏/轮询逐帧 + 可感延迟为第一证据源。

## 3. 诚实声明：未收敛项与判定线局限

1. **冷启动最长静止段**：本轮 4650ms 超 FT-2 验收线（<1000ms）。帧检（`regression-out/20260905-145217/coldstart`）：该窗为「已恢复 Feed 卡片 + 低对比度占位封面」等待图片下载——**非空白窗**（反馈存在但 diff 不可见）。两个叠加因素：①本 run 网络慢（chrome 6.5s vs 前轮 3.0s，代理抖动）；②FT-2 的占位封面对比度过低，低对比度动效在灰度 diff 判据下不可见（与 P3 定性翻案同一教训）。**待办**：占位对比度提升（小改动，未及本轮）+ 判定线改「卡片存在性」口径（FT-5 脚本 tabs 场景已用此口径，coldstart 待迁移）。
2. **首访冷内容就绪 ~5-9s**：网络支配（当日代理抖动 700ms-7s 波动），应用侧无法承诺；本票治理的是等待期反馈连续性。
3. **P5（新登录首进详情 401 需手点重试）未修**：与主线正交，留在 [#369](https://github.com/a1121611810/Pictelio/issues/369)（P6 logcat token 泄漏面已由 FT-2 的 `loggingBehavior:"none"` 关闭）。
4. **回归脚本一次城区污染事故**：登出竞态导致首轮 coldstart 测成登录页（s15 帧）、back 方差被未就绪 rep 污染——均已修（登录守卫 adb 键入重登 + 未就绪 rep 跳过），脚本化沉淀。

## 5. 结论

用户主诉的两个痛点方向上：**加载等待**——冷启动静止段 6.0s（最坏口径）→0.65s、常规冷启 WaitTime 减半、等待期全程可见反馈；**切换/返回卡顿**——返回从硬切冻结变为 8-27ms 响应+17 帧过渡、tab 切换空白窗归零、查看器翻页黑屏消灭。四张修复票验收线全过，最终回归六场景五过一⚠（余项为网络窗敏感指标的低对比度占位判定局限，非空白回归，待办明确）。剩余 P5 与占位对比度小项留票跟踪。
