## 2. 需求场景与用户价值

### 2.1 背景

Pixiv 小说（novel）以日文内容为主，其次是英文、繁体中文。当前 App 只展示原文，中文用户阅读门槛高。翻译是社区客户端最常见的差异化需求，同类产品已验证该模式：EhViewer（翻译 API）、Tachiyomi 生态（翻译扩展）、沉浸式翻译（BYOK + 自定义 OpenAI 兼容端点）。

### 2.2 用户价值

- 解决"想读但看不懂日文"的核心痛点，直接提升小说模块留存
- 与「中文识别」能力衔接：自动检测源语言 → 预选目标语言 → 一键翻译，形成完整链路

### 2.3 产品形态（一句话）

> 用户进入小说详情页 → 点击「翻译」→ 选择模型（预设 / 自定义 baseURL）→ 填入自己的 API Key（首次）→ 分块并发翻译 → 进度条 → 译文替换正文（可切回原文）→ 结果本地缓存，再次打开直接读译文。

## 3. 技术方案总览：BYOK 端到端直连

### 3.1 架构

```
[Pictelio App (Android WebView / Web)]
        │
        │  HTTPS + OpenAI 兼容协议 (POST {baseURL}/chat/completions)
        │  Authorization: Bearer <用户自己的 Key>
        ▼
[用户所选 LLM 服务商：DeepSeek / OpenAI / Kimi / Qwen / GLM / 自定义 baseURL]
```

- **无中间服务器**：App 直连用户所选服务商，我方不接触 key、不接触内容、不承担中间责任
- **统一协议**：全部走 OpenAI 兼容 `POST /chat/completions`（DeepSeek/Kimi/Qwen/GLM/OpenRouter/Ollama 均兼容）
- **不需要 SDK**：手写 ~150 行 fetch 客户端，避免体积与维护负担

### 3.2 模型预设（MVP 建议 6 项）

| 模型 | baseURL | 国内直连 | 日→中质量 | R18 容忍度 | 备注 |
|------|---------|:---:|:---:|:---:|------|
| DeepSeek `deepseek-chat` | `https://api.deepseek.com/v1` | ✅ | 优 | **宽松** | 性价比之王，推荐默认 |
| OpenAI `gpt-4o-mini` | `https://api.openai.com/v1` | ❌ 需代理 | 优 | 严格（明确禁 NSFW） | 质量稳定 |
| Moonshot Kimi `moonshot-v1-8k` | `https://api.moonshot.cn/v1` | ✅ | 优 | 中等 | 长上下文好 |

## 4. 翻译力度（粒度）策略 —— 深入分析

### 4.1 四种候选方案

| 方案 | 交互 | 首屏等待 | 术语一致性 | token 效率 | 实现复杂度 | 结论 |
|------|------|:---:|:---:|:---:|:---:|:---:|
| A. 整章翻译 | 点一次，等全文 | 30~90s | **全局最优**（一次 system prompt 上下文） | 高 | 低 | ✅ 基础 |
| B. 逐段翻译（随滚动） | 滚动即翻 | <5s | **差**（每段独立上下文，角色名漂移） | **低（system prompt 重复）** | 高 | ❌ |
| C. 用户选区翻译 | 选中一段 | <5s | 差 | 高 | 中（移动端选区交互复杂） | 备选 |
| D. **混合（推荐）** | 点一次，首屏优先，后台续翻 | 3~10s | 全局（整章一次请求上下文） | 高 | 中 | ✅ **MVP** |

### 4.2 关键数据：为什么逐段翻译（B）不可行

token 浪费模型：假设 system prompt 300 token（翻译指令 + 术语表 + 格式约束），单段平均 200 token。

| 方式 | 请求数 | 总 input token | 浪费倍数 |
|------|:---:|:---:|:---:|
| 整章分块（5 块 × 2000 字） | 5 | 5×300 + 15,000 ≈ **16.5K** | 1× |
| 逐段（100 段 × 200 字） | 100 | 100×300 + 20,000 ≈ **50K** | **~3×** |

**结论**：逐段翻译不仅慢、术语乱，还把用户成本抬高 3 倍。翻译必须以"整章为上下文单元"组织。

### 4.3 推荐方案 D 的详细设计

```
点击「翻译」
   │  1. 校验：key 存在？目标语言？R18 分级？（第 8 章）
   │  2. 读缓存：原文 hash 命中 → 直接显示，结束
   ▼
   │  3. 分块（1500~2000 字/块，段落边界）+ 优先级排序：
   │     首屏块（当前阅读进度附近 3~5 块）排最前
   ▼
并发队列（2~3 路）
   │  4. 首屏块完成 → 立即注入渲染（渐进式效果）
   │  5. 其余块完成后按序注入
   ▼
全部完成 → 整章写入缓存（原子）
   │  6. 失败块（如政策拒绝）：回退原文 + 段尾标记「未翻译」
```

**为什么首屏优先可行**：管线本质是"块序列 → 译文块序列 → 重组段落数组"。任意数量的块完成即可重组出**部分译文**（未完成的段落用原文占位），虚拟布局与渲染全部自动工作。这使"点击后 3~10 秒看到首屏译文，其余后台续翻"成为天然产物，无需额外状态机。

### 4.4 力度对系统三性的影响

| 影响面 | 整章/混合（D） | 逐段（B） |
|--------|--------------|----------|
| 内存 | 块结果数组（~100KB）翻译后释放 | 需保留"哪些段已翻"的状态表 + 频繁信号更新 |
| 竞态复杂度 | 单一 AbortController（项目硬约束达标） | 滚动触发新请求需精细的 generation-gate，极易出竞态 bug |
| 可维护性 | 管线纯函数化（分块→并发→重组），易单测 | 状态散落，测试需 mock 滚动行为 |
| 阅读进度 | 段落索引不变，不受影响 | 同 |

## 5. 翻译管线设计（核心）

```
novelHtml (HTML 字符串)
   │  parseNovelBlocks（现有）
   ▼
TextBlock[]（text 为字符串段落）
   │  1. 段落净化：解码实体、剥离标签 → 纯文本段落
   │  2. 语言检测：detectNovelLanguage() → 源语言（zh-Hans/zh-Hant/ja/ko/en/other）
   │  3. 分支：
   │     - 繁⇄简（同语系）→ 本地表驱动转换（第 6 章），零 LLM 调用
   │     - 跨语言 → 进入 LLM 分块管线
   │  4. 分块（≤2000 字，段落边界）+ 首屏优先排序（第 4.3 章）
   ▼
块序列 → 并发队列（2~3 路，指数退避重试 ×2）
   │  5. 保序重组 → 译文段落数组（译文段落数 = 原文段落数）
   ▼
替换 TextBlock.text（注入点：NovelDetail.tsx:360 blocks memo）
   ▼
虚拟布局自动重算（pretext 布局管线零改动）
```

**基于现有代码的核实（v1 已确认，此处保持）：**
- 注入点：`NovelDetail.tsx:360` `blocks` 是 `createMemo`，全文唯一依赖 `novelHtml` + `novelImages`
- 布局层零改动：`createNovelVirtualLayout.ts:117` 直接吃 `TextBlock.text` 字符串
- 阅读进度、搜索定位、系列切章均以**段落索引**为锚点，翻译不破坏
- 图片 `[pixivimage:id]` / 分页 `[newpage]` 是独立 block，不进入翻译流

## 6. 目标语言范围 —— 深入分析

### 6.1 语言矩阵与处理分层

> **v3 决策：MVP 聚焦 日/英 → 中文（简中为主，繁中可选）**。以下分层架构仍成立，但繁简转写与中→英/韩→中等语言对降级为 Phase 2+。

**关键洞察：目标语言处理分两类，必须分层架构：**

| 类型 | 场景 | 处理方式 | 成本 | 质量 |
|------|------|---------|:---:|------|
| **转写（同语系转换）** | 繁中⇄简中 | 本地表驱动（OpenCC 思路） | **0 token、瞬时、离线** | 100%（表驱动） |
| **翻译（跨语言）** | 日→中、英→中、中→英、韩→中… | LLM | 按 token | 模型质量 |

**为什么繁简不能交给 LLM**：繁→简是"确定性转写"而非翻译。用 LLM 有三个问题——① 浪费 token（每次调用按字数计费）；② 可能"顺手翻译"改变原文语义或引入错别字；③ 需要网络与 key，而转写完全可以在无 key 时工作。**繁简转换应作为翻译管线的前置独立层**，无 key 也能用。

### 6.2 繁简转换实现方案（v3 暂缓，Phase 2+）

| 方案 | 包体 | 质量 | 维护 | 结论 |
|------|------|------|------|------|
| `opencc-js` 全量 | ~1.5MB（含词库） | 最佳（短语级转换） | 低（成熟库） | Phase 2 候选 |
| 自研精简表（常用 2500 差异字 + 高频短语表） | ~60KB gzip | 良（覆盖 99% 日常文本） | 中（表需维护） | **MVP 推荐** |
| LLM 转换 | 0 | 良但有翻错风险 | 低 | 仅作兜底 |

> MVP 建议自研精简表（Pixiv 繁中小说词汇量有限，常用字表足够）；若后续实测覆盖不足，切 `opencc-js`。

### 6.3 语言检测扩展（支撑语言矩阵）

v1 的检测只区分 zh/ja/ko/other。要支撑目标语言矩阵，扩展为：

| 检测项 | 依据 | 输出 |
|--------|------|------|
| 假名占比 >1% | `[\u3040-\u30ff]` | `ja` |
| 谚文占比 >1% | `[\uac00-\ud7af]` | `ko` |
| 拉丁字母占比 >10% | `[a-zA-Z]` | `en`（MVP 不分英/法/德，统一 en） |
| CJK 汉字占比 >30% 且无假名 | 简体字表 vs 繁体字表命中数（们/这/说 vs 們/這/說） | `zh-Hans` / `zh-Hant` |
| 其他 | — | `other` |

繁简判别：内嵌 ~200 对高频差异字表做投票，准确率 >99%（差异字在正文中命中率极高）。

### 6.4 目标语言对成本与缓存的影响

| 语言对 | 输入 token 估算 | 输出 token 估算 | 单篇成本（DeepSeek） | 缓存 key 的 targetLang |
|--------|:---:|:---:|:---:|:---:|
| 日→简中（主场景） | 12K~18K | 9K~12K | ~¥0.07 | `zh-Hans` |
| 日→繁中 | 同 | 同 | ~¥0.07 | `zh-Hant` |
| 英→简中 | 3K~5K（英 1 token≈4 字符） | 9K~12K | ~¥0.05 | `zh-Hans` |
| 简中→英 | 9K~12K | 5K~8K | ~¥0.05 | `en` |
| 繁中→简中（转写） | 0 | 0 | ¥0 | `zh-Hans`（本地层，不占 LLM 缓存） |

**架构结论**：语言矩阵用配置表驱动（`localeConfig.ts`），每条配置含 `{ code, 检测规则, 提示词模板, 转写 or 翻译 }`。新增语言 = 新增一行配置，核心管线零改动。目标语言选择器 UI 从配置表渲染。

## 7. 译文保留策略 —— 深入分析

### 7.1 缓存什么

```ts
interface TranslationCacheEntry {
  id: number;            // 复合 key 的 hash
  novelId: number;
  targetLang: string;    // zh-Hans / zh-Hant / en ...
  modelId: string;       // deepseek-chat / 自定义
  sourceHash: string;    // 原文 md5（spark-md5 已有）
  paragraphs: string[];  // 译文段落数组（纯文本）
  createdAt: number;
}
```

- 存储：复用 `db.ts` 的 `createIDBStore`，新增 `translations` store
- **译文必须存纯文本段落**，不存 HTML——渲染路径保持文本（安全，见 11.1），且与原文段落一一对应

### 7.2 保留多久：三种策略对比

| 策略 | 体验 | 磁盘 | 隐私可控性 | 结论 |
|------|:---:|:---:|:---:|:---:|
| A. 永久（无限增长） | 最好 | 无上限，长年累积膨胀 | 需手动清理 | ❌ 失控 |
| B. **LRU 容量上限（200 章 / ~8MB）+ 手动清除** | 好（热章命中率高） | 有界 | 提供「清除翻译缓存」入口 | ✅ **推荐** |
| C. 会话级（不持久） | 差（每章重翻，token 浪费） | 0 | 最好 | ❌ 浪费用户钱 |

容量测算：单章译文 ≈ 30~40KB（万字中文 UTF-8 ≈ 30KB + 结构开销）。200 章 ≈ 8MB，IndexedDB 默认配额（通常 ≥50MB）安全。淘汰算法对齐 `novelCache.ts` 既有 LRU 模式。

### 7.3 失效与边界规则

| 场景 | 行为 |
|------|------|
| 作者修改正文（sourceHash 变化） | 自动失效，重新翻译（hash 比对零成本） |
| 用户换目标语言 / 模型 | 不同 key 维度，分开缓存，互不污染 |
| R18 部分失败（政策拒绝） | **整章不写缓存**（避免缓存"半成品"污染下次阅读）；失败块标记「未翻译」，下次点击仅补翻失败块（断点续翻） |
| 用户清除 API Key | 译文是用户内容的衍生品，**与 key 无绑定关系**——保留译文；但设置页提供「清除全部翻译缓存」一并对齐 |
| 翻译中途退出 | 整章未完成不写缓存（避免碎片）；已注入内存的译文随页面销毁 |

### 7.4 对系统三性的影响

| 面 | 影响 |
|----|------|
| 内存 | 缓存走 IndexedDB（磁盘），运行时仅加载当前章译文（~40KB），虚拟布局只计算可见段——内存影响可忽略 |
| 安全 | 译文含用户内容衍生品，缓存清理入口必须显著；明文存磁盘（无 key 加密需求——译文非凭据），但可选项：与小说正文缓存同级保护即可 |
| 可维护 | 缓存层独立模块（`translationCache.ts`），接口 `get/put/invalidate/clear`，纯函数可单测；与 `novelCache` 模式对齐 |

| **OpenAI** | Usage Policies 禁止生成 NSFW 性内容（含翻译/改写成人内容场景） | enforcement：警告→暂停→封禁 | ⚠️ 反爬，公开政策概述 |
| **阿里 Qwen** | 内容安全审核（通义审核）拦截涉黄；AUP 禁止违规内容 | 违规可暂停/终止服务 | ⚠️ JS 渲染，公开政策概述 |
| **智谱 GLM** | 内容安全策略拦截涉黄 | 用户协议含违规处理 | ⚠️ JS 渲染，公开政策概述 |

### 8.2 三个层面必须区分（重要分析框架）

| 层面 | 含义 | 对功能的影响 |
|------|------|------------|
| **书面条款** | 合同层面禁止什么 | **所有主流服务商（含 DeepSeek）书面都禁色情**——严格讲，任何 R18 翻译都属"违约" |
| **实际执行** | 服务商是否真的拦截/处罚 | 差异巨大：DeepSeek 对 R18 文学翻译实际容忍度高（社区实践）；国内平台（Qwen）内容安全拦截严格，请求直接被拒 |
| **模型行为** | 模型本身是否愿意输出 | Kimi 模型层面就拒绝（官方 prompt 注入）；DeepSeek 模型愿意翻译 |

**⚠️ 对 v2 的修正**：v2 将 DeepSeek 列为"宽松"不准确——**DeepSeek 书面条款并不宽松**（§3.4(5) 明确禁止），宽松的只是实际执行。产品启示：**任何依赖"实际执行宽松"的方案都脆弱**——服务商随时可收紧（条款已授权），用户账号风险始终存在。

### 8.3 封号风险机制（用户最关心的"封号/封批"）

| 触发场景 | 服务商行为 | 封号概率 |
|----------|-----------|:---:|
| 偶发 1 次 R18 请求 | 内容审核拒绝（返回 4xx/截断），无账号影响 | 极低 |
| 个人阅读频率翻译 R18（每周几篇） | 多数服务商不主动处置（DeepSeek 实际执行宽松） | 低 |
| **高频/批量/自动化**发送敏感内容 | 触发风控：警告→限制→暂停→封禁（DeepSeek §8.2、OpenRouter §5.5 明文授权） | 中-高 |
| **R18G（极端暴力/猎奇，含未成年人暗示）** | 服务商零容忍；国内服务商按网信合规**上报主管部门**（DeepSeek §8.2 明文 "report to authorities"） | **极高，且不止封号** |

关键认知：
1. **BYOK 架构下封号发生在"用户的 API 账号"**，不是 App——但用户体验上会迁怒于 App，产品必须提前声明
2. **封号概率取决于"量"**：个人阅读频率（每周几篇）远低于风控阈值；Phase 3 的系列批量翻译风险显著上升，**建议批量功能默认禁 R18 章节**
3. **R18G 不是"政策问题"而是"法律红线问题"**：儿童色情/极端暴力在全球任何服务商都是零容忍，可能触发平台上报执法——**与 R18 必须彻底区分**

### 8.4 「开关 + 二次弹窗告知」方案评估（核心产品决策）

| 评估项 | 结论 |
|--------|------|
| 用户体验 | ✅ 开关默认关 + 首次开启二次告知，用户知情、符合"风险自担"心智 |
| 能否免除服务商处罚 | ❌ **不能**。服务商合同约束是"用户 vs 服务商"，App 内弹窗同意对服务商无效；弹窗只是产品层面的告知与免责 |
| 能否控制封号风险 | ⚠️ 部分。App 无法控制服务商风控，但可：控制请求频率（单章单次、不批量）、默认推荐实际执行宽松的模型、失败即止（不对敏感块自动重试） |
| 我方法律/合规责任 | ✅ 无直接责任（无服务器、不存储、不中转）——但建议在设置页与弹窗显著声明"翻译功能与内容风险由用户自行承担" |

**推荐分级方案（更新 v2）：**

| 分级 | 开关 | 二次告知 | 发送策略 |
|------|------|---------|---------|
| `x_restrict = 0`（全年龄） | 无需 | 无 | 正常翻译 |
| `x_restrict = 1`（R18） | **默认关**，设置页可开启 | 强告知（含封号警告，见下） | 推荐宽松模型（DeepSeek）；**失败即止**，回退原文 + 「未翻译」标记；不做自动重试敏感块 |
| `x_restrict = 2`（R18G） | **不提供开关**，客户端本地拦截 | — | 不发送任何内容（政策 + 法律双重红线） |

**二次告知文案建议（R18 开关开启 / 首次翻译 R18 时）：**

> 「该作品包含 R18 内容。翻译需将正文发送至你选择的 AI 服务商，可能：① 被服务商内容审核拒绝（失败段落保留原文）；② 违反服务商使用条款，导致你的 API 账号被警告、暂停或封禁。所有风险由你自行承担。［取消 / 我已了解并继续］」

### 8.5 对产品价值与系统三性的影响

- **价值**：R18 是 Pixiv 核心内容，完全禁翻会大幅打折——"默认关 + 可开 + 风险告知"是最优平衡；R18G 禁翻损失可控（极端内容占比低）
- **安全**：无服务端、无存储、无中转 → 无法律/合规责任；Play Store 上架（未来）时翻译功能不新增成人内容风险（内容源是 Pixiv，已有年龄确认门）
- **内存**：无额外影响
- **可维护**：分级逻辑收敛为「翻译前决策函数（x_restrict 分级 + 开关 + 告知）」+「失败即止回退函数」，纯函数可单测；政策变更只改配置
- **必须实测**：上线后统计各模型 R18 拒绝率与封号反馈，配置表驱动调整默认模型排序（改默认值零代码）

## 9. 网络与平台集成（v1 保留，含 CORS 关键坑）

| 环境 | 路径 | 问题 |
|------|------|------|
| Web (DEV) | `fetch` 直连 | ✅ 无问题 |
| Android Native | WebView `fetch` 直连 | ❌ **CORS 会失败**（OpenAI 例外，多数国内服务商无 CORS 头） |

**解决方案**：Native 走 `CapacitorHttp`（`novel.ts:205` 已有先例，原生层无 CORS 限制），Web 走 `fetch`，封装成双模式 `translateRequest()`。**不得复用 `apiClient`**（绑定 Pixiv 域 + 401 刷新逻辑）。

> 这是"DEV 正常、真机全挂"的经典陷阱，已列为实现硬约束。另一网络要点：国内用户访问 OpenAI 需自备代理（预设列表已优先国内直连服务）。

## 11. 三性深入分析：安全性

### 11.1 新增风险：LLM 输出注入（XSS）

**这是翻译功能引入的、项目原本没有的安全风险面**：

- LLM 译文是**不可信输入**（可能被原文 prompt injection 诱导输出恶意内容）
- 若译文以 HTML 渲染路径注入（`innerHTML`），恶意输出可执行脚本
- **缓解（架构级）**：
  1. **译文全程保持纯文本**——渲染走 SolidJS 文本节点（当前 `renderParagraphWithHighlights` 的 `{text}` 即安全路径），禁止为译文引入 `innerHTML`
  2. 若未来要支持译文富文本（保留 `<b>` 等），必须过 `sanitizeHtml` 白名单消毒（`html.ts` 已有，白名单仅 `a/br/b/strong/i/em/span/p/div`）
  3. 单元测试覆盖：构造含 `<script>` 的恶意"译文"，断言渲染为纯文本

### 11.2 Key 安全（v1 保留）

- 存储：Keystore 加密（`secureStorage.ts` 成熟模式），不落 Preferences、不进日志、不常驻内存
- 传输：仅作 `Authorization: Bearer` 头发往用户所选服务商，无中间服务器
- 提供「清除所有已存 Key」

### 11.3 隐私

- 首次翻译弹窗告知：正文将发送至所选服务商；Key 仅存本机；费用由服务商按量计费（用户自付）
- 译文缓存提供「清除」入口（7.3）

### 11.4 竞态安全（项目硬约束）

- 翻译管线必须 `AbortController` + generation-gate（系列切章/离开页面时中止），复用 `createNovelLoader` 既有模式
- 翻译注入 blocks 的 memo 更新必须带版本号，防止旧响应覆盖新数据

## 12. 三性深入分析：低内存占用

| 数据面 | 量级 | 说明 |
|--------|:---:|------|
| 单章译文常驻 | ~40KB | 万字中文 UTF-8 ≈ 30KB + 结构；仅当前章 |
| 翻译中缓冲 | <100KB | 2~3 路并发 × 每块响应 ~10KB，完成后释放（局部变量） |
| 缓存落盘 | ~8MB 上限 | IndexedDB（磁盘非内存），LRU 200 章 |
| 布局缓存 | 不新增量级 | `novelTextLayoutCache` 是 LRU 有界；译文只是 key 多一个维度 |
| 渲染 | 零额外 | 虚拟滚动只渲染可见段（现有架构天然支持） |

**结论**：内存影响近乎为零。仅有的约束：① 译文段落数组不跨章节堆叠（系列切章按需加载）；② 翻译中间态（块结果）用局部变量，完成后置空。

## 13. 三性深入分析：高可维护性

### 13.1 模块边界（分层，各层可独立单测）

```
src/api/translate.ts          协议层：OpenAI 兼容请求、双模式（fetch/CapacitorHttp）、错误归一化
src/primitives/createNovelTranslator.ts  管线层：净化/分块/并发/保序重组/进度/取消（纯函数核心 + Solid 包装）
src/stores/translationStore.ts 状态层：key/模型/目标语言（secure-storage）、Signal 状态机
src/utils/translationCache.ts  缓存层：IndexedDB 读写、LRU、hash 失效
src/utils/localeConfig.ts      配置层：语言矩阵（纯数据，新增语言零代码）
src/utils/modelPresets.ts      配置层：模型预设（纯数据，含 R18 容忍度排序）
src/utils/prompts.ts           提示词模板集中管理（不散落组件）
```

### 13.2 状态机（Signal 驱动，避免命令式散落）

```
idle → translating(progress: {done/total, failed[]}) → done | partial(有失败块) | failed
                                    ↑_______ 补翻（断点续翻）______|
```

### 13.3 配置驱动原则

- **模型预设**：`modelPresets.ts` 纯数据（含 R18 容忍度字段）——服务商政策变化只改数据
- **语言矩阵**：`localeConfig.ts` 纯数据——新增语言只加一行
- **提示词**：`prompts.ts` 模板——翻译指令调整不碰代码逻辑

### 13.4 与项目既有约束对齐

- SolidJS store 模式（`createSignal` 顶层导出，不加封装层）
- Fluent 规范（设置 UI 用现有 `SettingsContent` 分组样式与 token）
- 测试硬约束：IO 边界（翻译请求成功/失败/429/政策拒绝路径全覆盖）、契约测试用真实 API 响应样例、静默降级必须 `console.warn`（如失败块回退原文时告警）
