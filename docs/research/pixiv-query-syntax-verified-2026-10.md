## 1. 结论：布尔语法由服务端解析，客户端只需透传

| 语法 | 输入 | 判别依据（结果集之间的关系） | 判定 |
|---|---|---|---|
| AND（空格） | `A B` | 结果集 **≠** `A OR B`（相等就说明服务端只取了首词） | ✅ 按 AND 解析 |
| OR | `A OR B` | 含两个词各自的命中（并集），且 **≠** AND 结果集 | ✅ 真并集 |
| 负号排除 | `A -A` | **自排除返回 0 条**（`A -A == ∅`） | ✅ 负号被解析 |
| 括号嵌套 | `A (B OR C)` | 结果非空且 **≠** 单查 `A` | ✅ 被解析 |
| 全角归一 | `ｒｏｓｅｍａｒｙ` | 与 `rosemary` 结果集**逐条相等**（**所有档位**） | ✅ 归一 |
| 大小写归一 | `RoSeMaRy` | partial / 不传档 == `rosemary`；`exact_match_for_tags` 档 **0 条** | ⚠️ **只在 partial / 不传档成立** |

对照组：脚本还跑一条「非法字面串 → 0 条」，用于确认**"返回 0 条"本身是有意义的信号**，而不是端点恒定返空。

## 2. 判别方法（本轮方法论要点）

- **判别一律落在结果集之间的关系上**（并集 / 交集 / 空集 / 逐条相等），**不靠单次结果的有无**。
  「这次有没有结果」是最弱的一种证据：空结果既可能是语法没被解析，也可能是检索词本来就没内容。
- `AND ≠ OR` 是排除「服务端只取首词」这一伪解释的**最小充分条件**——若只取首词，两者会给出同一集合。
- `A -A == ∅` 是负号生效的最小充分证据；反过来，`A -C == A` **不能**证明负号无效：
  实测 `A`（`Rosmontis`）首屏 30 条里带 `#Rosmontis` 标签的**有 0 条**，根本没有可排除的对象。
- **只看「结果前几条里有没有另一个词」会误判 `OR`**：并集里两个词的命中可能都落在首屏之外，
  于是 `A OR B` 看起来与单查 `A` 无异。判据必须是**集合是否相等**，不是单页里有没有出现过。
- 检索词用真实存在的标签（`Rosmontis` / `rosemary` / `明日方舟`），不手写自洽数据。

## 3. 覆盖面

- **端点**：`/v1/search/illust` 与 `/v1/search/novel` **都成立**。
- ~~**`search_target` 四档全部成立**~~：不传 / `partial_match_for_tags` / `exact_match_for_tags` / `title_and_caption`（**原句保留作历史留痕，已被下一条订正**）。
  ⚠️ **该行对「小说端 + `title_and_caption`」一格已于 2026-10-17 订正**（见 §4）：那一格不是「成立」，
  是**请求被拒**——`verify-query-syntax.sh` 对被拒响应只打印 `❌ ERR: …`，判别块取到的全是空值，
  即该组合**从未产生过任何可判别的结果集**，「四档全部成立」把它一并算进去属**过度断言**。
  其余各格（两端 × 可被接受的档位）仍成立。
- ⇒ 布尔语法与搜索目标档位**正交**：档位不破坏 `OR` / 负号 / 括号 / 全角解析，本仓多词请求
  发 `exact_match_for_tags`（历史行为）也不会让这些语法失效。⚠️ 该正交结论只在**能被接受的档位上**
  有取证面——小说端 `title_and_caption` 不在其中（§4）。

## 4. 增量实测（2026-10-17）：端点对 `search_target` 取值做**校验**，不是忽略

| 请求（`/v1/search/novel`，`word=東方`，`filter=for_ios`，`sort=date_desc`） | HTTP | 条数 | ids md5 |
|---|---|---|---|
| 省略 `search_target`（基线） | 200 | 30 | `0c104c0a` |
| `search_target=title_and_caption` | **400** | 0 | — |
| `search_target=partial_match_for_tags` | 200 | 30 | `c27a6bb5` |
| 未知参数名 `foo=bar`（对照） | 200 | 30 | `0c104c0a` |

**交错 2 轮，四格逐位一致**（§2 方法论：顺序采样会把时间漂移读成参数差异）。取证脚本
[`verify-novel-title-target.sh`](./verify-novel-title-target.sh)（本文同目录，**已入库、可复跑**），
前置与凭据纪律同 `verify-query-syntax.sh`（access_token 只经管道进 python，只回显长度）。

- **对照组是关键**：未知参数名 `foo=bar` 返回 200，且 ids md5 与省略参数时**完全相同** ⇒ 不是
  「服务端不认识这个参数名所以忽略」（那会是无害、可随手带上），而是**明确拒绝这个取值**。
  性质与用户端 `/v1/search/user` 对 `search_target` 的硬拒一致。
- **后果强度**：小说端 UI 对该档**置灰保值**，挡的不是「结果不准」这类体验问题，而是
  「**每一次小说搜索直接 400 失败**」。置灰逻辑哪天回归、请求层哪天开始真发这个参数，
  scope=novel 的搜索就整片报错，而不是退化成多几条结果 ⇒ **放宽它需要一次显式决策**，
  不能当 UI 细节顺手改掉。
- **取证边界**：上表 HTTP 码与条数**可复跑**（上面脚本），与 2026-10-17 那次未留脚本的一次性采样
  结论一致（同端点、同检索词、同组对照）。
- 副产品留痕（**不得当结论引用**）：同一采样窗口内，小说端 `partial_match_for_tags` 与省略参数
  的 ids md5 **不同**（`c27a6bb5` vs `0c104c0a`，条数同为 30）。这只是**单个窗口的一次观察**，
  既不足以断言映射方向正确、更不证明任何机制（「不传退化为纯字面匹配」仍未证实，见 §5 第 2 行）。
  要引用须先按 §2 方法论跨检索词、跨窗口复跑。

## 6. 对本仓的含义

1. **只加提示文案，不写客户端查询解析器**：客户端拼串/解析与服务端语义重复且会随服务端演进而漂移。
   落地面 = 搜索弹层输入框下方一行提示（spec §7.2）。
2. **文案不得承诺「大小写无关」**：大小写归一只在 partial / 不传档成立，`exact_match_for_tags` 档实测大小写敏感。
3. **档位不对称不在本文证明**：见 §5 第 2 行——本文只证明语法与档位在**能被接受的档位上**正交（§3 ⚠️），
   映射不对称是另一条证据链；本文只对「小说端 `title_and_caption` 被实测硬拒」（§4）这一个格子有直接结论。
