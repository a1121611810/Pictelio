# 顶层导航换维度与留存机制：外部证据与 Pictelio 调整方案

- 日期：2026-10-03
- 状态：**已成稿**（§5 为「聚焦取证」，非完整调研——见 §5 开头交代）
- 触发：产品判断「推荐 / 插画 / 小说 / 我的」这个切法**普通**、**粘性不够高**，要求换维度重新集成
- 明确排除：**不查同类项目**（Pixiv 客户端对比已做过，见 `competitor-*.md`，本次不重复）

---

## 0. 一句话结论

当前四个顶层目的地里有**三个是同一份上游推荐流的媒介过滤**（推荐/插画/小说同源），
而项目里**真正具备复访价值的资产（关注流、追更、稍后看、通知）全部沉在「我的」里当入口行**，
且**投递通道为零**（宿主无任何通知能力）。
⇒ 问题不在「tab 少」或「tab 排得不好」，而在**切分维度选错了**：按媒介切，而用户的复访动机是关系与状态，不是媒介。

## 2. 现状诊断（全部为【代码事实】，可复核）

### 2.1 四个顶层目的地的实际数据来源

| 目的地 | 路由 | 数据来源 | 性质 |
|---|---|---|---|
| 推荐 | `/recommended` | `/v1/illust/recommended` + `/v1/novel/recommended`，按 `create_date` 交叉合并 | **上游推荐，混合媒介** |
| 插画 | `/illusts` | `loadRecommended` 单源（`IllustList.vue:63-76`） | **推荐流 + 媒介过滤** |
| 小说 | `/novels` | `loadRecommendedNovels` 单源（`NovelList.vue:50-60`） | **推荐流 + 媒介过滤** |
| 我的 | `/me` | 本地状态 + 设置项 | 功能抽屉 |

- `NAV_TABS` 单点事实源：`packages/app-lynx/src/components/navTabs.ts:26-31`
- 推荐页混流：`packages/app-lynx/src/pages/Recommended.vue:98-110`（`merge: 'time-merge'`）
- 插画/小说页：`createMixFeed` 各自只挂一路 source
- 路由：`packages/app-lynx/src/router.ts:96-100,109`

**⇒ 结论：推荐/插画/小说不是三种需求，是同一批上游内容的两种切法 + 一次合并。**
换句话说，**顶层 4 个位置里有 3 个表达的是同一个维度（媒介），且是弱表达**（同一批内容少一半）。

### 2.2 导航载体不是常驻底栏，是两步手势的放射 FAB

- ADR-0120（accepted, 2026-08-30）**主动移除**各顶层页的 `<NavigationBar>`，把导航合并进右下角双层环 FAB
  （外环=导航 tab，内环=页面动作），见 `docs/adr/ADR-0120-app-lynx-radial-nav-fab.md`
- 现状挂载：`packages/app-lynx/src/App.vue:209-210`
- `NavigationBar.vue` 组件**仍存在但全仓无引用**（仅 `navTabs.ts` / `SubTabBar.vue` 的注释提到它）
- ⚠️ **已过期的登记**：`navTabs.ts:3,6` 仍写「各顶层页 import NAV_TABS 接入 NavigationBar」——ADR-0120 之后这句已不成立。
  这是本仓「登记会过期」纪律的一个实例（描述现状的句子在修完/改完后没同步）。

**⇒ 四个顶层目的地没有常驻的「我在哪 / 我能去哪」可视线扫过的面。**
每次换目的地 = 点 FAB + 点环项（两步），且 FAB 收起时**不显示任何 tab 标签**。

### 2.3 关系维度：能力已建好，但没有顶层出口（最大的一处闲置资产）

- `/following` 页**实现完整**（关注作者的插画时间线，`pages/Following.vue:1-6,67`）
- 但**无任何用户可达入口**——全仓唯一指向是 `router.ts:433` 的 `pictelioBenchNavFollowing`（benchNav 调试深链）
- 页内注释自陈：「本页非 tab 页，**放射 FAB 不显示**」
- 同时，插画页/小说页**各自内嵌**「推荐 / 关注」`SubTabBar`（`IllustList.vue:262-270`）
  ⇒ 「关注」这个关系维度**被降级成了页内二级切换**，而不是顶层目的地

**⇒ 项目已经拥有「关注流」这块完整能力（含分页、混流、置灰、榜单入口），却把它锁在二级。**

### 2.4 所有复访资产沉在「我的」当入口行

`pages/Me.vue` 的行序（模板行号）：

| 行 | 入口 | 性质 |
|---|---|---|
| 637 | 收藏 | 复访资产 |
| 647 | 追更 | 复访资产 |
| 6xx | 稍后看（含 count 角标） | 复访资产 |

**⇒ 业务入口与设置/调试项在同一页混排，7 个复访资产与 4 个调试项共享一个入口面。**
这是「结构普通」感受的直接来源之一：用户看不出这个 App 有什么可回来的东西。

各资产的真实能力边界：

| 资产 | 覆盖 | 持久化 | 投递 |
|---|---|---|---|
| 追更 `watchlistStore` | **仅小说系列**（`composables/useNovelWatchlistToggle.ts`） | 会话内 reactive cache + 弹窗询问 | **无** |

| 搜索历史 `searchHistoryStore` | 搜索词 | 上限 **10** 条（`:18-20`） | — |

⚠️ **追更只覆盖小说系列，插画侧没有任何「追系列/追作者更新」的对等机制。**

### 2.5 投递通道为零（最致命的一处）

- 全仓 Java **无** `NotificationManager` / `NotificationChannel`（grep 结果为空）
- `AndroidManifest.xml` 只声明 `INTERNET` + `ACCESS_NETWORK_STATE`，**无 `POST_NOTIFICATIONS`**
  （minSdk 28 ⇒ Android 13+ 设备必须显式申请该权限才能展示通知）

**⇒ 「我追了这个小说的系列」这个动作，在系统层面没有任何送达方式。**
用户追更后必须**自己想起来、自己打开 App、自己去「我的」翻到追更**才知道有没有更新。
一个没有回执的承诺，构不成复访理由。

### 2.6 没有「接着看」——且这是单引擎收敛时丢掉的能力

- app-lynx 侧**无浏览历史 store**（只有 `searchHistoryStore`，存的是搜索词不是浏览记录）
- **无阅读位置持久化**（`novelTranslateStore` 里的 `progress` 是 AI 翻译进度，不是阅读位置）
- 旧 WebView 客户端曾有 `historyStore`（ADR-0094「TanStack DB 浏览历史」），
  随 **ADR-0203**（WebView 客户端源码删除）一并消失

**⇒ 单引擎收敛（ADR-0203）顺带丢掉了浏览历史这项留存资产。当前无人记得这件事，因为没有人在跑那条链路。**

> ⚠️ CodeGraph 索引提醒：`codegraph status` 显示 `lastIndexed: 2026-09-29`、
> `pendingChanges: 0`，但 `codegraph query history` 仍返回已删除的
> `packages/app/src/stores/historyStore.ts` ⇒ **索引含已删除包的幽灵符号**。
> 节点 16155 / 边 54007（未归零，尚可用），但凡指向 `packages/app/**` 的结果**必须回文件系统复核**。
> 索引重建是用户决策，本次未执行。

### 2.7 没有任何度量能力

- 全仓无 analytics / 埋点 SDK / 启动计数 / DAU 统计
- 唯一的「埋点」字样是 AI 翻译模块预留的注释通道（`primitives/createNovelTranslator.ts:320`）

**⇒ 当前无法回答「改版后粘性有没有变好」。**
在没有任何基线的情况下改导航，事后无法判断是改对了还是改坏了——这会让后续每一次调整都变成赌博。

### 2.8 小结：四个顶层位置实际表达的东西

| 位置 | 名义 | 实际表达 | 问题 |
|---|---|---|---|
| 1 | 推荐 | 上游推荐（混合） | 唯一有信息量的位置 |
| 2 | 插画 | 推荐的插画子集 | 弱表达：同一维度、同一批内容 |
| 3 | 小说 | 推荐的小说子集 | 弱表达：同上 |
| 4 | 我的 | 设置 + 复访资产抽屉 | 把 7 个留存资产和 4 个调试项混在一起 |

**没有一个位置在表达「关系」（我关注的更新）或「状态」（我没看完的、我收藏的）。**
而这两者恰恰是复访动机最强的两个维度。

## 3. 载体约束：放射环的容量上限（【推算】）

任何「加第 5 个顶层目的地」的方案都要先过这一关。

### 3.1 现有几何（【代码事实】）

| 参数 | 值 | 出处 |
|---|---|---|
| 外环半径 `R_OUTER_VW` | `35`（= 131.25px @1vw=3.75px） | `GlobalFab.vue:56` |
| 环项圆直径 | `14.93vw`（56dp = 56px） | ADR-0121 决策 2 |
| 外环扫角 | `OUTER_START=-8°` → `OUTER_END=-88°`（共 80°） | `GlobalFab.vue:132-133` |
| 内环半径 | `20` | `GlobalFab.vue:57` |

### 3.2 环项中心距公式

```
角距 step = 80° / (n - 1)
中心距 d = 2 · R · sin(step / 2) = 262.5 · sin(step/2)   [px]
不重叠条件：d ≥ 环项直径 = 56px
```

### 3.3 代入现状

| n（顶层目的地数） | 角距 | 中心距 d | vs 56px 圆 | 结论 |
|---|---|---|---|---|
| **4（现状）** | 26.67° | **60.5px** | +4.5px | 勉强成立 |
| **5** | 20.00° | **45.6px** | **−10.4px** | ❌ **重叠 ~10px** |

ADR-0121 实测记录为 57.1px（与上式 60.5px 有差异，应为其测量口径不同）。
⚠️ 该 ADR 原文写「实测 35vw 时中心距 57.1px **> 56+4px** 间隙」——57.1 < 60，**这句不等式本身不成立**；
能成立的是「4 项不重叠」（57.1 > 56，间隙仅 1.1px）。**结论方向不变，但 ADR 的论证应修正。**

### 3.4 第 5 项需要多大的半径

```
要求 d ≥ 60px（56px 圆 + 4px 间隙）
2 · R · sin(10°) ≥ 60
R ≥ 60 / (2 × 0.17365) = 172.8px = 46.1vw
```

**⇒ 5 个顶层目的地需要把外环半径从 35vw 提到约 46vw（+32%）**，并重新验证：
与内环（R=20）的间距、是否探出屏幕底边（ADR-0121 曾因 `OUTER_END=-100°` 溢出过 7px）、
以及 4 个页面各自的 `usePage` 动作项是否还排得开。这是一次需要新 ADR + 原型 + 真机验证的改动。

### 3.5 由此得到的两条硬结论

1. **「加到 5 个 tab」在放射载体上不是免费的**，不能当作轻量改动顺手做掉。
2. **「4 个位置换语义」的成本远低于「4 改 5」**——`navTabs.ts` 是单点事实源，
   改 `path/name/labelKey` 即可，几何与 ADR-0120/0121 都不需要重解。
   ⇒ **换维度应当优先走「同样 4 个位置、换掉切分维度」这条路。**

## 4. 外部证据：非同类产品的顶层导航模式

> 完整报告：[`nav-ia-patterns-non-pixiv-2026-10.md`](./nav-ia-patterns-non-pixiv-2026-10.md)（664 行）
> 本章为整合后的结论，并附**独立复核**结果。

### 4.1 平台硬约束（【一手】，已独立复核）

| 平台 | 原文规则 | 对本项目的含义 |
|---|---|---|
| **M3** | "Navigation bars can have three to five destinations"；实现层 `BottomNavigationView` 硬封顶 5 | 数量上限 5，**4 未超限** |
| **M3** | "**Bottom navigation destinations should be of equal importance.**" | ⚠️ **推荐/插画/小说不等重要**——它们是同一批内容的三个视角 |
| **M3** | "Tabs share a common subject, whereas bottom navigation destinations are top-level and **disconnected from each other**"；对照表：`Tabs / Any level of hierarchy / 2+` | ⚠️ **「共享同一主题的并列数据集」在 M3 里叫 Tabs（页内二级），不叫顶级目的地** |
| **M3** | "Don't use more than five destinations" / "Don't use a bottom navigation bar for fewer than three" | 4 落在区间内，数量不是问题 |
| **Apple HIG** | "Use the **appropriate number** of tabs… it's generally easier to navigate among **fewer** tabs" | 软规则，倾向更少 |
| **Apple HIG** | "**Avoid overflow tabs.** The More tab makes it harder for people to reach and notice content on tabs that are hidden" | 不做「更多」溢出 |
| **Apple HIG** ⚠️ | "Make sure the tab bar is visible when people navigate to different sections of your app. **If you hide the tab bar, people can forget which area of the app they're in.**"（唯一豁免是模态层） | ⚠️ **「藏起导航」被现行 HIG 点名为失败模式** |
| **Apple HIG** | "Consider using a **sidebar within a tab**"；"show **no more than two levels** of hierarchy in a sidebar" | 顶层装不下时，**平台背书把次级维度放进 tab 内部**，深度上限两层 |
| **Apple HIG** | "Use a tab bar to support **navigation, not to provide actions**" | tab 不承载操作 |

> **一处必须纠正的流传说法**：业界常引「Apple 规定 tab 3–5 个」。
> **现行 HIG 文本中查无此原文**——3–5 是 **M3** 的数字，Apple 只有定性指引。
> （"five or fewer" 仅出现在 HIG 的 iPadOS *自定义 tab* 语境，不是 iPhone 通用规则。）
> 本仓若引用「Apple 3–5」会引错平台。

### 4.2 最关键的两条推论

1. **本项目的问题不是「tab 数量」，是「分组语义」。**
   M3 的判据不是「这东西重不重要」，而是「**它和其他顶级目的地是不是同一主题下的两个视角**」。
   按此判据：推荐/插画/小说 = **同一主题（Pixiv 目录）下的三个视角** ⇒ 属于 Tabs，不属于顶级目的地。
   这解释了为什么用户觉得「普通」——**从信息架构上，这三个 tab 本就不该并列在顶层**。

2. **导航不常驻有明文的外部反对意见。**
   HIG 明确点名「藏起 tab bar ⇒ 别人会忘记自己在哪」，唯一豁免是模态层。
   本项目 4 个顶层目的地全部藏在需两步展开的悬浮 FAB 内、收起时无任何标签 ⇒ 落在这条规则的射程内。
   ⚠️ 但这是 **ADR-0120 的有意决策**（收敛代码重复），**不是疏漏**。推翻它需要新 ADR，不是顺手改。

### 4.3 非同类产品的实际切法（【一手】样本）

| 模式 | 样本与实际顶层列表 | 结论 |
|---|---|---|
| **媒介下沉一级** | **eBookJapan**：トップ `ホーム / ジャンル / 新刊 / ランキング / 無料マンガ / セール`；小说与漫画题材（ライトノベル / マンガ雑誌 / 少女・女性 / 少年・青年）**全在「ジャンル」之下** | 同一 App 内的两种媒介，**主流做法是下沉一级，不是顶层分栏** |
| 同上 | **微信读书**：混排首页 | 同向 |
| **供给链独立才顶层分** | **哔哩哔哩**：`首页 / 番剧 / 直播 / 游戏中心 / 会员购 / 漫画 / 赛事`；而 电影/电视剧/综艺/纪录片 这些题材反而**压在首页 partition 里** | 顶层分媒介的前提是**媒介 = 独立供给链** |
| **拆成两个产品** | **LINE Manga vs LINE WEBTOON** | 同一资产不同媒介，厂商选择**拆产品而非加 tab** |
| **按用户角色分** | **Wattpad**：`Browse / Community / Write / Download app`（内部无媒介轴） | 另一条可行轴：**角色** |
| **收藏与账号并列** | **LINE Manga**：`毎日無料 / ストア / インディーズ / 本棚 / お気に入り / マイメニュー`——「本棚（书架）」「お気に入り」与「マイメニュー」**并列各自独立成项** | ⚠️ **收藏不寄生在「我的」里面** |

### 4.4 判定汇总（强/中/弱分级）

| 问题 | 判定 | 强度 |
|---|---|---|
| 同 App 内「文本 + 插画」是否顶层按媒介分栏？ | **否，主流下沉一级** | 强（2 个一手样本 + HIG 背书） |
| 何时才顶层分媒介？ | **供给链彼此独立时** | 中（1 个样本，仅 Web 端） |
| 同资产不同媒介怎么处理？ | **拆两个产品，不加 tab** | 强（两个官方站点） |
| 平台允许「次级维度塞进 tab 内部」吗？ | **允许且推荐**，深度上限两层 | 强（Apple 官方文档） |

> 若该专项报告后续交付，本节应以其为准复核。

### 5.1 追更 → 必须有回执（【一手】）

**LINE WEBTOON 官方帮助中心**（`help2.line.me/LINE_WEBTOON/android`，繁中）原文：

> 「如何將我喜愛的網路漫畫加入我的最愛：選擇一個漫畫，並按其集數列表右上角的 (+最愛) 鍵。
> **您就會在新集數上架時在 App 中收到推播訊息。**」

同页另有多处相关的官方表述：

| 机制 | LINE 官方表述 | 对我们的含义 |
|---|---|---|
| 追更 = 订阅更新 | 加入「最愛」→ **新集上架即收 App 推播** | 我们的「追更」只有写状态，**没有回执**（§2.5） |
| 推播可分类开关 | 「您可以在 [設定提醒訊息] 選單改變推播設定」 | 推播必须**可按类关闭**，否则等于骚扰 |
| 地区默认不同 | 「在美國境內『新作上線』及『公告&活動』推播通知**自動轉為關閉狀態**」 | 推播默认值应随地区/用户偏好走，不是全开 |
| 关注艺人也会推 | LINE Music 帮助中心：「Updates: You'll receive the latest information about **the artists you follow**」 | 「关注 → 推播」是同族机制，可一并设计 |

**⇒ 判定（强）：「加入追更」与「收到更新通知」在成熟产品里是**同一个动作的两半**，
不是两个功能。缺了后半，前半就只是一个本地布尔标记。**

### 5.2 「我的东西」应当是一个聚合面（【一手】，且直接印证 §6 的「书架」）

LINE WEBTOON 帮助中心「如何管理我的 Webtoon 紀錄」原文：

> 「在主畫面下方 **[我的漫畫]** 進入 [我的漫畫] 頁面。您可以在這個頁面找到
> **所有最近看過的漫畫**、管理**我的最愛**、檢查**下載**和觀看留言活動紀錄。」

暂存下载同样收在同一条路径下：「您可以在 [我的漫畫>暫存] 管理您的暫存下載。」

**⇒ 一个「我的漫画」面同时承载：最近看过 + 我的最爱 + 下载 + 活动记录。**
这与 §4.3 LINE Manga 把「本棚 / お気に入り」与「マイメニュー」**并列**、
以及 §2.4 我们把 7 个留存资产塞进「我的」形成直接对照。

**⇒ 判定（强）：「最近看过 / 我的最爱 / 下载」这类个人资产，主流做法是聚合成一个面，
而不是散落在设置页的行里。** —— §6.1 提出的「书架」不是发明，是把这个既有惯例补齐。

### 5.3 「接着读」是独立能力，且需要位置持久化（【一手】）

**Kindle / Whispersync**（Amazon 设备手册与帮助页原文，经 manualslib 镜像与 Amazon UK 帮助页取得）：

> 「Amazon's Whispersync technology keeps track of the **last reading location** in each book.
> For example, you can read a few pages using the Kindle application on your iPhone, iPad, or
> Android device and then **pick up right where you left off** when you return to your Kindle.」

> 「Sync automatically backs up and saves data from your Kindle devices and apps, including your
> **reading position**, notes, and highlights… Some features are unavailable, including
> **sharing your reading position across devices**」（关闭同步后的功能缺失清单）

**LINE WEBTOON 官方帮助中心**「同步閱讀紀錄」：

> 「同步閱讀紀錄…以用戶登入帳號為基準…保存以下的紀錄：作品目錄內**閱讀過的話次紀錄**、
> 我的漫畫 > **最近看過的** > 閱讀作品紀錄」

**⇒ 判定（强）：「接着读」不是 UI 上多一个按钮，而是**位置持久化 + 一个聚合入口**两件事。
我们的项目两件都没有**（§2.6：app-lynx 无浏览历史、无阅读位置持久化，
旧 WebView 客户端曾有、随 ADR-0203 丢失）。**

### 5.4 无社交图 / 无 UGC 场景下的适用性（按本项目条件过滤）

| 机制 | 适用性 | 依据 | 对本项目的现状 |
|---|---|---|---|
| **追更/订阅 + 推播** | ✅ 适用（无社交图亦可） | LINE WEBTOON 一手 | 追更有、**推播无**（§2.5） |
| **接着读 / 阅读位置** | ✅ 适用 | Kindle、WEBTOON 一手 | **完全没有**（§2.6） |
| **个人资产聚合面** | ✅ 适用 | LINE WEBTOON「我的漫畫」一手 | 散落在「我的」行里（§2.4） |
| **关注流（订阅 feed）** | ⚠️ **部分适用** | 需要「关注」关系存在；本项目有 `/following` 能力（§2.3），但**关系本身来自 Pixiv 侧**，不是本项目生产的社交图 | 能力闲置 |
| 每日打卡 / streak | ❌ 不建议 | 强推力但**依赖连续性焦虑**，与「打开看看」的低承诺场景冲突 | 未做（**本报告无一手证据支撑引入**，见 §8.1） |
| 社交证明 / 评论区驱动 | ❌ 不适用 | 本项目无 UGC、无评论（ADR-0025 已移除评论系统） | 不适用 |
| 作者创作侧入口 | ❌ 不适用 | M3/HIG：导航不承载操作（§4.1） | 不适用 |

### 5.5 反面证据：本节未取得的证据（重要）

- **未取得**任何厂商自述的「某机制使 DAU 提升 X%」类一手数据。本节**不能**支撑
  「做了这些留存就会涨」的说法。
- **未取得**关于推播疲劳的厂商一手量化研究。本节只能说明
  「成熟产品把推播做成可分类关闭、且地区默认不同」（LINE 官方文本），
  **不能**据此论证推播的收益。
- **未验证** streak / 打卡类机制在「无社交图、低承诺」场景的效果——按 §8 的口径，
  **标为未证实，不作为建议依据**。

## 6. 调整方案：把顶层从「媒介维度」换成「关系 + 状态维度」

### 6.1 换维度的具体动作（一句话）

**外层 4 个位置从「按媒介切」改成「按用户要回答的问题切」，把媒介降为页内二级 tab。**

| 层 | 现状 | 建议 | 依据 |
|---|---|---|---|
| **顶层** | 推荐 / 插画 / 小说 / 我的 | **发现 / 关注 / 书架 / 我的** | §4.1 M3「同主题的并列视角属 Tabs」+ §4.3 LINE Manga「收藏与账号并列」 |
| **页内二级** | 插画/小说页有「推荐/关注」二级 | **发现页内加「全部 / 插画 / 小说」二级**（复用现成 `SubTabBar`） | §4.1 HIG「sidebar within a tab」+ M3 Tabs 定位 |
| **投递** | 无 | **新增通知通道**，让「关注/追更」有回执 | §2.5（当前为零） |

**新顶层各自回答的问题：**

| 位置 | 回答用户的问题 | 数据来源 | 是否需要新建 |
|---|---|---|---|
| **发现** | 「有什么新的」 | 现 `/recommended`（混合）+ 现 `/illusts` `/novels` 降为二级 | ❌ 全部已有 |
| **关注** | 「我关注的人/作品更新了什么」 | 现 `/following`（+ 小说追更新） | ❌ **能力已完整，只缺入口** |
| **书架** | 「我存的、我没看完的」 | 收藏 + 稍后看 + 追更 + 下载 + **继续读**（需新建历史） | ⚠️ 需新建聚合页 + 重建历史 |
| **我的** | 「账号与设置」 | 通知 / 主题 / 下载管理 / 诊断 | ⚠️ 瘦身 |

### 6.2 为什么这个方案成立（三条外部依据 + 一条内部事实）

1. **它符合 M3 的分组语义**（§4.1）：四个位置互不重叠、**同等重要**、彼此 top-level disconnected；
   而插画/小说作为「同一目录的两个视角」下沉成 Tabs，正是 M3 对这组数据的指定形态。
2. **它符合平台对「深层 IA」的官方背书**（§4.1）：HIG 明确允许次级维度放进 tab 内部，**上限两层**。
   建议形态是 `发现（二级：全部/插画/小说）→ 作品详情`，恰好两层，不越界。
3. **它符合非同类产品的实际做法**（§4.3）：eBookJapan 把小说与漫画题材下沉一级；
   LINE Manga 把「本棚/お気に入り」与「マイメニュー」**并列**而非嵌套——对照之下，
   我们把 7 个留存资产全部塞进「我的」，是这个结构里最偏离主流的一处。
4. **它释放的是已有资产，不是新建需求**（§2.3）：`/following` 页实现完整（含分页/混流/榜单入口），
   却只有 benchNav 调试深链可达。**当前 4 个位置里没有一个在表达「关系」维度。**

### 6.3 明确不推荐的两条路

| 不推荐 | 理由 |
|---|---|
| **加第 5 个顶层目的地** | §3.4【推算】：5 项时环项中心距从 60.5px 掉到 45.6px，**小于 56dp 圆直径，必然重叠**；需把 `R_OUTER_VW` 从 35 提到约 46vw（+32%），并重验内环间距与探底（ADR-0121 曾因此溢出 7px）。成本远高于「4 个位置换语义」。 |
| **直接推翻 ADR-0120 加回常驻底栏** | HIG 确实点名「藏起导航→忘记自己在哪」（§4.1），但 ADR-0120 是**有意决策**（收敛 4 页重复的 NavigationBar+内联 FAB）。若要推翻需新 ADR + 重新评估收敛收益。**建议先做 §6.1——它不依赖载体变更。** |

## 7. 落地顺序与前置条件

### 7.1 分期（按「是否依赖新能力」切，不按工作量切）

| 期 | 内容 | 新后端？ | 推送？ | 依赖 |
|---|---|---|---|---|
| **P0** | 顶层换维度：媒介降为二级、关注提为顶层、我的瘦身 | ❌ | ❌ | 改 `navTabs.ts` 单点 + FAB 可见性门 + `SubTabBar` 复用 |
| **P0.5** | **最小本地度量**（见 §7.2） | ❌ | ❌ | 与 P0 同期 |
| **P1** | 书架页：聚合四类资产 | ❌ | ❌ | 新页面 + 迁移提示 |
| **P2** | **重建「继续读」**（浏览历史 + 阅读位置） | ❌ | ❌ | 需新建（ADR-0203 已删旧实现） |
| **P3** | **通知投递**：追更新/关注更新送达 | ❌ | ✅ | `POST_NOTIFICATIONS` 权限 + 新原生模块 + 周期任务 |

**P0 的正当性不来自「它会提升留存」**（那是个待验证假设），
**而来自「它符合 M3 的分组语义与 HIG 的深层 IA 指引」**——这是外部标准，不是留存赌注。
留存假设要靠 P0.5 的度量来验。

### 7.2 P0.5 度量：为什么必须与 P0 同期

§2.7：**当前全仓无任何埋点/启动计数/DAU**。
⇒ 不先建度量，P0 之后**无法判断有没有变好**，后续每一次调整都退化成赌博。

最小可行方案（零服务器、隐私友好）：

| 指标 | 口径 | 落点 |
|---|---|---|
| 复访间隔 | 相邻两次启动的时间差分布 | 本地键，随现有备份同步 |
| 各目的地触达率 | 4 个顶层各自被切入的次数占比 | 本地计数 |
| 二级媒介使用占比 | 发现页内 全部/插画/小说 各被选次数 | 本地计数 |
| 书架进入率 | 进入书架页的比例（衡量「存了但没回来看」） | 本地计数 |

⚠️ 全部**只存本地计数与时间戳**，走现有 `prefs` seam 与备份通道，**不上传任何用户行为**。
这与本仓现有的隐私取向一致（无第三方 SDK）。

### 7.3 风险与已知失效面（必须先认领）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **关注页冷启动空态** | 关注作者少的用户看到空页面，观感差（TikTok Friends Tab 的同族问题，§4.3） | 必须有空态引导（去推荐关注 / 浏览榜单），不许裸空列表 |
| **老用户找不到收藏** | 书架聚合会改变入口位置 | 「我的」保留收藏/稍后看次级入口 + 一次性迁移提示 |
| **媒介入口变深** | 找小说从「1 步」变「2 步」 | 二级 tab 常驻可见；深度仍在 HIG 两层上限内 |
| **P0 无度量即上线** | 改完不知道好不好 | P0.5 与 P0 同期，不拆 |
| **ADR-0120 被实质架空** | 若后续加回常驻底栏，需正面处理收敛收益 | 记录在 §8 待决问题，不静默绕过 |

### 7.4 P0 的实际影响面（已核查，非推测）

改动 tab 集合会牵动以下位置（`grep` 实测，非估算）：

| 位置 | 性质 | 说明 |
|---|---|---|
| `components/navTabs.ts` | 事实源 | 改 `name/path/icon/labelKey` |
| `stores/globalFab.ts` + `globalFab.test.ts:107` | **硬编码四 tab 名** | 测试直接断言 `["recommended","illusts","novels","me"]` |
| `primitives/createGlobalFab.ts` + 其单测 `:205,211` | 深模块 | 用 `'novels'` 做 select 用例 |
| `i18n/locales/{zh-CN,en}/misc.ts` | 双语 | `navTabs.*` labelKey 需增删 |
| `tests/unit.test.ts:272` | 路由表断言 | 需同步新路由 |
| `tests/{tagMuteTemplate,meNotificationsTemplate,md3GuardScans}.test.ts`、`hardcode-whitelist.json` | 门禁 | 扫描 `navTabs` 字面量，改名可能触发门禁 |
| **E2E a11y 标号** | ⚠️ **跨端契约** | ADR-0120 已记录「Appium/E2E 断言标号需同步」；`a11yLabel` 目前钉住中文 |

⚠️ 最后一类是**安卓 E2E 不进 CI**（ADR-0084）——**改 tab 名不会变红**。
按本仓纪律（E2E 失效是静默的），P0 合并前需手工重跑受影响的 android-e2e spec，
否则会留下一批「看着绿、其实坐标/标号已失效」的断言。

### 7.5 需要决策/新 ADR 的事项（本报告不越权决定）

1. 顶层是否最终定为 4 个（推荐）还是 5 个（需重解环几何 + 新 ADR）。
2. 「书架」是否并入「我的」（保持 4 个位置但语义不同）——这会更保守，但无法释放关系维度。
3. 通知投递的形态：本地周期拉取 vs 服务端推送（后者需服务端，隐私与成本另议）。
