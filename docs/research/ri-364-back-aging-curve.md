# RI-364 B 部分第一阶段单实验：返回延迟会话老化曲线

- issue: a1121611810/Pictelio#364（B 部分），地图 #361，实验对应 `docs/research/real-interaction-audit.md` 场景 3
- 分支 `fix/ri-365-coldstart`（c7e64f67），versionName 4.32.0（含 FT-1A 返回过渡 + FT-2 splash 改造），emulator-5554，已登录
- 目的：剥离「两轮代码不同」混杂变量，在同一构建上模拟老化操作序列，测详情→home 系统返回延迟是否随会话使用爬升（体检：旧会话 1.48-1.82s vs 新会话 184-233ms）

## 协议

- **checkpoint 0（新会话基线）**：`am force-stop` → 冷启动 → 首页首卡图就绪 → back 录屏 3 rep。
- **老化单元**：打开详情（tap 首卡 (415,560)）→ 停 2s → back；每 4 单元后：home 快甩滚动 2 屏 + force-stop → 冷启动等就绪。共 12 单元（checkpoint 4/8/12）。
- **每个 checkpoint**：同协议 3 rep back 录屏（录屏起 → sleep 1s → `input keyevent 4` → 5s 停录 → `analyze_rec.py`）。

### 测量口径（按实测帧序列修订）

任务书预期签名（预位移帧 → 静止保持段 → 17 帧退出动画 → home 落定）**未在本环境复现**：
实测 VFR 录屏签名 = 静止详情页（t=0）→ **单帧切换**（home 完全落定，diff≈56.5）→ 静止。
无预位移帧、无退出动画帧序列、无可分离的静止保持 gap（`ck0_rep1` 逐帧核验：f1=详情图就绪页，f2=home 落定帧）。

因此采用实测口径：

| 量 | 定义 |
|----|------|
| **总时长** | home 落定帧 pts − 1000ms（脚本 sleep 1s 后注入 back；含恒定 adb `input` 注入延迟，各 checkpoint 同口径可比，与体检场景 3 协议一致） |
| **静止保持段（裸冻结）** | 本签名下无中间帧可分离；若老化冻结出现，预期表现为落定帧后移/多帧+长 gap，以 checkpoint 间总时长爬升判读。单帧切换时记「—（单帧切换）」 |

## 曲线判读

```

260 ┤
240 ┤        ● 242    ● 235
220 ┤  ●219            ●226  ●237
200 ┤ ●209 ●206               ●213

    └─────────────────────────────
      ck0     ck4     ck8     ck12
     (rep1/rep2/rep3 三点并列)
```

- **曲线平坦**：四组 checkpoint 中位数 219 / 242 / 226 / 213ms，全程单值 ≤319ms（ck4_rep3 为最高离群），无随老化单元数的爬升趋势。
- **判据核验**：任一 checkpoint 静止保持段 >500ms = 复现 → **未发生**（连 rep1 那次完整过渡捕获的内部过渡也只有 315ms、无 >200ms 冻结 gap）；全程 <400ms 平坦 = 本序列不复现 → **成立**。
- 结合 ck8_rep1 校准（back 输入在 mp4 时基 ≈910ms），真实 back→home 落定 ≈ 270-330ms 且四组同量级，与体检「新会话」184-233ms 一致，远离「旧会话」1.48-1.82s。

## 结论

**本实验在本构建（4.32.0，fix/ri-365-coldstart）上未复现返回延迟随会话使用爬升**：12 个老化单元（详情进出）+ 3 轮快甩滚动 + 3 次 force-stop 冷启动后，系统返回（详情→home）延迟保持平坦（中位 213-242ms）。证据强度：中——单模拟器、单网络环境、老化序列固定（同首卡、固定时长），阴性结果排除的是「本协议模拟的老化」这一条件。

对 #364 归因的含义：体检「旧会话 5-8x 劣化」无法由「同一构建内的常规使用累积」解释，混杂变量需在以下候选中继续剥离（归因阶段实验）：
1. **重装/跨版本迁移**：体检旧会话经历多轮 force-stop/重装（且两轮代码不同），持久层（浏览历史 TanStack DB、缓存 LRU、设置迁移）从零重建 vs 增量累积的差异；本实验 force-stop 3 次未复现，指向重装/迁移路径而非进程内累积。
2. **更新弹窗**：体检旧会话存在 StartupUpdateDialog 交互路径，本实验未触发。
3. **会话内容量**：本实验固定打开同一首卡、home feed 始终为同一缓存内容；体检旧会话浏览内容更杂，home remount 需重排的 DOM/图片更多。固定首卡可能让 remount 路径吃满缓存红利，是本实验最主要的盲区。

## 局限

- **force-stop 周期性清零进程内状态**：若老化主要存在于单进程生命周期（JS 堆碎片、Query 缓存累积），本协议每 4 单元 force-stop 会掩盖爬升；但体检旧会话同样经历 force-stop 仍测得劣化，故该局限不推翻阴性结论。
- **adb `input` 注入延迟（~100-300ms，恒定）** 计入「落定帧−1000ms」口径；各 checkpoint 同脚本同口径，相对比较有效。ck8_rep1 完整帧序捕获给出输入时刻 ≈910ms（mp4 时基）的独立校准。
- **VFR 编码器抽样运气**：多数 rep 只捕获单帧切换（过渡期间帧未落盘），ck8_rep1 捕获完整过渡，证明编码器行为是随机的；单帧切换不等于过渡为 0ms，但落定帧时刻是可靠的。
- 模拟器时间盒内未复现体检网络环境（代理波动、CDN 差异）。
