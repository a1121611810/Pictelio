## 到达路径（点击序列）

`adb` 打不进 Lynx 输入框（弹层由 JS 状态驱动、`input text` 无稳定落点），且 ADR-0133 决策 1 明确
搜索弹层**无 URL、无 deep link**（`searchSheetStore` 全局单例）。因此预填入口只能靠真点击走通：

```

→ 搜索弹层自动带词并发起搜索
```

取证时用的检索词：`ドールズフロントライン`（图 01/02/07/08/09/10/11）与 `Lumine`（图 03/04/05）。

## 逐条证据

### 1 — 搜索范围四档 + 用户档隐藏排序/筛选

- **图 01**（`01-illust-4tabs-sort-filter.png`，10:11，插画档）：scope 栏**四枚** chip 依次
  `全部` / `插画` / `小说` / `用户`，`插画` 为选中态；其下**排序段**三枚 `最新`(选中) / `最早` / `热门` 完整在列；
  再下**筛选开关行**（`筛选` + 右侧 `^` 展开箭头）；再下**折叠区**（展开态）依次 `匹配方式` / `期间` / `收藏数`。
- **图 02**（`02-user-4tabs-sort-filter-gone.png`，10:11，用户档）：scope 栏仍是同样四枚 chip（`用户` 选中），
  **其下只剩空态文案 `没有找到相关内容，试试换一个关键词`（该检索词在用户端无命中）** ——
  排序段、`筛选` 开关行、折叠区**三段整段不存在**，不是置灰、不是折叠，是未渲染。
- 两图 scope 栏的 chip **数量与顺序逐字一致**（都是 `全部` / `插画` / `小说` / `用户` 四枚）——
  变的只是选中项，说明「用户」是**常驻第四档**而非条件渲染出来的。
- **图上观察（不下判定）**：scope 栏的选中底色实测 `(58,72,87)`（灰蓝），
  与排序段 / 匹配方式 chip 的选中底色 `(13,74,115)`（饱和蓝）**不同**。此差异在全部截图里一致出现，
  故不是渲染抖动；是否属有意区分需对照设计稿 / ADR，本记录**不主张**它是缺陷。

### 2 — 用户结果真实渲染

- **图 03 / 图 04**（`03-user-results-avatars.png` 10:16、`04-user-results-scrolled.png` 10:17，检索词 `Lumine`，用户档）
- **头像是真实加载图像，不是灰底占位**：头像圆形区域逐行像素采样为
  `(197,153,255)` / `(252,208,130)` / `(245,236,219)` / `(206,164,124)`（图 03）、
  `(240,221,196)` / `(246,233,208)` / `(220,191,152)`（图 04）—— 多彩、逐行不同，
  与「同一张占位图」的等值特征相反。（`(197,153,255)` 即任务简报所举的采样值，本轮独立复现一致。）
- **两行文字齐全**：全分辨率裁图可见 `lumineko arts`（大字白）+ `luminaura`（小字灰）、
  `Luminea` + `user_rfzp5428`、`Lumine 💛` + `user_akdv7835` —— name 与 account 各一行、无截断。
- **缩略图在行右侧、与文字块同行**（不是行下方）：每行右侧固定 3 个等宽圆角方形槽位，最右是 `查看 ›`。
- **诚实标注（未能确认）**：截图时刻部分槽位仍呈**纯黑**（图 03 第 1 行前两槽 + 第 3、4 行全部三槽；
  图 04 第 2 行全黑、第 3 行仅中间一槽、第 4 行全黑）。
  **本记录不判定**这是「该用户无作品」还是「懒加载未完成」—— 静态截图无法区分，需另开设备 spike。
  可判定的是：**槽位数与位置在所有可见行中稳定为 3，已加载的槽位是真实图像**。
- 稳定性：切到用户档后**另采两帧**（同一状态连采），两帧 MD5 相同（`9fe406c1…`），
  结果集在该采样间隔内已 settle。
  **诚实标注**：该两帧**未入库**——原始文件在 `/tmp` 易失，仓库内**不可复核**，此处只记 MD5 供对照。
  且其 MD5 恰等于图 03（`03-user-results-avatars.png`，见末尾复核表），即三帧字节完全相同：
  状态确实是 settle 的，但这句稳定性结论本身**没有可按图索骥的入库证据**，

### 3 — 匹配方式三枚 chip 的文案

- **图 07**（`07-illust-chips-titleAndCaption.png`，10:11，插画档）：折叠区首行标题 `匹配方式`，
  其下三枚 chip 全分辨率逐字可读为 **`标签部分一致`** / **`标签完全一致`** / **`标题·说明`**（分隔符为中点 `·`，非 `・`/`/`）。
  该图 `标题·说明` 为选中态（蓝底白字）——顺带钉死了「选中态长什么样」，供第 5 条比对。

### 4 — 语法提示行的条件渲染

- **图 05**（`05-syntax-hint-with-keyword.png`，10:15，输入框有词 `Lumine`）：
  输入框正下方一行 **`空格=与 · -排除 · OR=或 · ( )`**（分隔符为中点，两侧带空格）。
- **图 06**（`06-syntax-hint-cleared.png`，10:12，输入框已清空、显示占位符 `输入标签 / 关键词`）：
  **该行消失**，原位置换为 `搜索历史` 段标题 + 空态 `输入关键词开始搜索`。
- ⇒ 提示行的显隐**确实以「输入框有关键词」为条件**，不是常驻。
- **弱旁证（不下判定）**：图 06 的 `搜索历史` 为空态，而此前已执行过多次带词自动搜索

  故**不能**据此反证「手动提交路径会写历史」。

### 5 — 小说档 chip3 置灰保值（三段独立证据）

先说清 chip 的四种像素态（本轮逐点取色实测，可当场复核；取样点见图 07/08/10 的 chip 行 y≈872–928）：

| 态 | 底色 | 文字 | 出处 |
|---|---|---|---|
| 选中（可用） | `(13,74,115)` 饱和蓝 | 白 | 图 07 chip3 |
| 未选中（可用） | `(39,42,47)` 中性深灰 | 白 | 图 07 chip1 |
| **不可选 + 有保值** | `(12,39,57)` 深蓝灰（明显偏蓝，B≫G≫R） | **灰** | 图 10 chip3 |
| 不可选 + 无值 | `(22,26,30)` 近中性深灰（R≈G≈B） | 更暗灰 `(84,89,94)` | 图 08 chip3 |

四态两两像素可区分 —— 尤其是 `(12,39,57)`（明显蓝调）与 `(22,26,30)`（近中性）这一对，
肉眼也分得开。**这是下面三段证据能成立的前提**：若「保值态」与「普通置灰态」像素相同，
第 5 段就无法区分「值还在」与「值被清了」。

**① 拦截成立（点置灰 chip3 不改画面）**

- 前帧 **图 08**（10:10，小说档，`标签部分一致` 选中 = 蓝底，`标题·说明` 纯灰置灰，徽标**无**）
- 操作：`adb shell input tap` 打在置灰的 `标题·说明` chip 上
- 后帧 **图 09**（10:10）
- **两帧 MD5 均为 `d2cbed9d3b24c5e4867246b60e19f69a` —— 字节完全相同。**
- **为什么这样才算数**：① 必须先把选中态挪到 chip1 —— 点**已选中**的 chip 画面本来就不变，
  那只证明幂等，证明不了拦截；现在点的是**未选中且置灰**的 chip3，若 tap 被放行它必然变成图 07 那样的
  蓝底白字选中态，画面一定变。② 字节相同比「看起来没变」强：任何像素级差异（含抗锯齿、徽标、
  状态栏时钟）都会让 MD5 分叉 —— 事实上状态栏时钟正是这类比对的天然混淆项，用 MD5 恰好把它一并排除。
- **独立复现**：另有一组同结论的帧（10:10，小说档、chip3 已有保值态），点其置灰 chip3 前后
  MD5 同为 `d660fdc1f65c4b58f9532c3e00d17b65`。该组**未入库**（证明的是同一条行为，且原始文件在 `/tmp` 易失），
  此处记录其 MD5 供对照。

**② 值未被清（跨档保值）**

- 前帧 **图 07**（10:11，插画档，`标题·说明` 蓝底白字选中，筛选徽标显示 `1`）
- 操作：切 scope 到 `小说`
- 后帧 **图 10**（10:11，小说档）：chip3 底色变为 `(12,39,57)` 蓝底 + **灰字**（保值不可选态），
  **筛选徽标仍为 `1`**（未被清零）
- **为什么这样才算数**：若切档时清值，`筛选` 徽标会消失（图 08 就是徽标消失的样子）；徽标仍是 `1`
  ⇒ 值仍在 store 里，只是当前档不可用。
- **精确性提醒**：chip 行下方那行 **`「标题·说明」仅插画范围可用（已设的值会保留）`** 是**范围说明文案**，
  在图 08（**无值**时）同样显示 ⇒ **它是常驻提示，不是保值指示器**。保值结论只由 chip 视觉态 + 徽标计数承担。

**③ 精确复原（切回不回落）**

- 操作：从图 10（小说档）切回 `插画`
- 后帧 **图 11**（10:11，插画档，`标题·说明` 蓝底白字选中，徽标 `1`）
- **图 11 与图 07 的 MD5 均为 `2ad1f1b2f6e9888ce37b8fd0fbd73975` —— 字节完全相同。**
- **为什么这样才算数**：若回落成 `partial`，chip1 会变蓝底、chip3 退回未选底、徽标计数也会变
  （对照图 01：chip1 选中且徽标**无**）—— 三处都会改画面。字节相同 ⇒ 选中态被**精确复原**，未回落。
- **弱旁证**：小说档 → 插画档切回时，chip1 `标签部分一致` 的选中态同样保值（图 08 chip1 选中 → 图 01 chip1 仍选中）。

## 设备侧证明不了什么（端点级取证的边界）

设备上**只能**证明「用户档把排序段与筛选区从 UI 上撤掉了」。
设备上**不能**证明「`/v1/search/user` 忽略 `sort` 参数」—— UI 根本没发这个参数，
两件事在设备上不可区分。

端点级结论（sort 三档逐位相同等）的一手实测在 **`docs/research/verify-search-user-api.sh`**，
属另一份证据，**不在本记录范围内**。引用「用户端无排序」时请指向该脚本，不要指向本文件。

同理，本文件对 `/v1/search/user` 的 `search_target` / `merge_plain_keyword_results` 行为**一个字都没验**。

## 复现命令

```bash
# 1. 起模拟器（-no-window 无头；截图走 adb；命令行逐字取自本轮实际运行的那条）
~/Library/Android/sdk/emulator/emulator -avd pictelio_low -no-window -no-audio \
  -no-boot-anim -gpu swiftshader_indirect -port 5554 > /tmp/emu.log 2>&1 &
adb -s emulator-5554 shell getprop sys.boot_completed        # 期望 1
adb -s emulator-5554 shell wm size                            # 期望 720x1280

# 2. 改过 JS 就必须重打 APK（无热更新）
pnpm build:android-host
adb -s emulator-5554 install -r \
  packages/android-host/android/app/build/outputs/apk/debug/app-debug.apk

# 3. 起客户端（不要传 dev refresh token，会覆盖设备登录态）
adb -s emulator-5554 shell am force-stop io.pictelio.app
adb -s emulator-5554 shell am start -n io.pictelio.app/.LynxActivity

# 4. 点击序列：发现页 → 插画 → 作品详情 → 点标签（openSearch 自动带词并搜）
adb -s emulator-5554 shell input tap <x> <y>     # 逐步 tap，无 deep link 可用
adb -s emulator-5554 exec-out screencap -p > shot.png

# 5. 比对同一断言时，用 MD5 而不是肉眼
md5 -q before.png after.png
```
