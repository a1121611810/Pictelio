# 层级改由表面色调表达 —— 用户视角规格（2026-10-01）

> **决策依据（唯一事实源）**：[`ADR-0212`](../adr/ADR-0212-tonal-elevation-surface-over-shadow.md) 的 8 条决策。

## Problem Statement

### 用户看到的现象

**界面的空间感是扁平的 —— 所有东西都浮着同一种灰影子。**

用户翻列表页时看到的是 MD2 时代的做法：一屏几十张白色卡片，每一张都拖着一条同样粗细、同样灰度的影子，贴在灰色的页面底上。页面像一堆叠起来的贴纸，看不出哪一层在上面、哪一层是底；真正应该浮起来的东西（悬浮按钮、弹出菜单）和应该贴在页面上的东西（列表行、卡片）用的是**同一种**抬升方式，于是两者之间的前后关系被这种重复的影子**抹平**了。

这个缺陷沿三个方向同时伤害体验：

**1. 浏览列表时：层级靠重复的影子表达，反而互相削弱。**

用户在推荐流、关注、收藏、书架、通知、设置等页面滑动，看到的卡片、列表行、设置项**全部**浮着同款影子。MD3 里这些元素属于「贴在页面上」的类别，它们的层级本来就该由底色深浅来说明；现在底色已经在做这件事了，影子又把同一个信号用另一种语言重复了一遍。第二遍没有增加信息，只是把界面推回了旧式投影的观感。实测：全仓 68 处 `box-shadow` 类令牌消费里，**53 处集中在最低一档**，且**全部**是贴面元素——最高的两档（悬浮专用）只占 15 处。

**2. 加载中：假数据卡浮着真阴影，是加载态里最刺眼的粗糙来源。**

用户点进任何列表页，数据到达之前看到的是一排「假卡片」。这些占位块为了模仿真实卡片，**连影子一起模仿了**——实测 7 个声明点展开成 **42 个渲染实例，同帧同时可见**。后果有三个，每一个用户都遇到过：加载中的占位块看起来像「已经有内容了」，用户分不清是在加载还是在看；整屏方块浮着同款影子，视觉噪声比内容本身还强；数据落定的那一刻，**42 个方块同时往下陷**，一次突兀的整体跳变。

**3. 按压时：靠「卡片陷下去」反馈，而不是「有反应」。**

用户按下刷新菜单项、按住悬浮主按钮时，界面的反馈是**阴影变浅**（元素看起来陷进页面里），而不是元素本身发生变化。观感是「卡片变暗 / 陷下去」，不是「我按到了它」。更麻烦的是这个反馈**在不同底色的元素上不一致**：有的元素按下时底色会变、影子也会变，有的只变影子。根因是同一个机制被当成了两种语言——阴影本该说明「这个元素浮多高」，现在被拿来说明「我正按着它」。实测有 **5 处**元素把阴影档位当按压反馈用。

**4. 内容受限遮罩：半透明压暗之上又叠一层影子。**

命中内容限制的小说 / 插画，用户看到的是一张半透明压暗的遮罩卡，遮罩之上还浮着一条影子。同一个「这里被挡住了」的信号被表达了两遍。

### 为什么这不是审美偏好而是缺陷

- **同一个层级信号被表达两遍，第二遍用的是错误的语言。** 贴面容器的底色已经是全仓使用最广的贴面档位（实测 87 处消费），MD3 的五档表面色调本身就是「用明度分档表达层级」的手段。再叠一层投影不是加强，是干扰。
- **「零阴影」在项目里过去不是一个可表达的选项。** 最底档的令牌被定义为「无」，却零处消费——所以「贴面元素应该没有影子」这件事在项目里**没法被写出来、也没法被搜到、也没法被门禁守住**。它不是「不写就对了」，是「写错不会失败」。这正是把意图从「减少写法」换成「让写错能失败」的原因。
- **高层两档的使用没有问题，问题全集中在最低档。** 实测的 15 处高层消费（5 处菜单项 / 环层 + 10 处 snackbar、底部弹层、居中对话框、悬浮按钮、文本选择工具条、悬浮条）**分配是对的**，且 9 类悬浮界面里绝大多数现状已经正确。缺陷 100% 集中在 53 处最低档。**本改造只动错的部分，不重排全站。**

## Solution

### 一句话

**把「这个元素浮不浮」从阴影改回由底色深浅来说：贴面元素不再有影子，浮在页面上的东西继续有影子。**

### 用户能感知到的变化

1. **列表变干净了。** 滑动任何列表页，卡片和列表项不再拖着重复的影子；层级改由卡片底色与页面底色的深浅差来说明。翻页时视线落在内容上，而不是落在一堆影子上。
2. **加载中不再浮着一堆方块。** 骨架块与它即将替换的真实卡片**同色调、不抬起**。数据落定时不会发生「整屏方块同时陷下去」的跳变；加载中的占位也不会再被误认为已加载的内容。
3. **按压有反应，而不是卡片变暗。** 菜单项与悬浮按钮按下时，元素自身的底色或深浅发生变化，**影子不再参与状态表达**。不同底色的元素按下反馈从此是同一套机制。
4. **浮层与底层分得清。** 底部弹层、居中对话框、弹出菜单、消息条、文本选择工具条、悬浮按钮继续**浮在**内容之上——这 9 类悬浮界面里现状已经正确的部分**一个都不动**，本改造只清理该清理的。

### 用户看不到、但同样重要的部分

- **「零阴影」从此是一档。** 贴面元素要显式写出「无阴影」，而不是「不写」。于是「有人给贴面卡片加了一条影子」这件事在代码里**可被搜到、可被门禁拦下**。
- **不依赖任何未验证的引擎能力。** 多层阴影在真机上到底能不能逐层渲染，目前**未取证**。本改造**净删除阴影、不新增**，所以探针的两种结论下改动**都已经做完、都不需要回滚**：若多层生效，删完后界面变平——那正是目标形态；若多层不生效，删完后界面不变——等于白删但无害。**唯一的差别是「辅助手段」的权重，方案本身两种情况都成立。**
- **两个最高档保持关闭。** 最高两档是**外推数值**（非官方一手表），且在本项目的界面清单里没有落点，现在消费它等于为了用令牌而造组件。它们的**解封条件**已经写死在决策 4 里，将来要开必须先满足条件，而不是「看着差不多就用」。

### 改造范围一览

| 类别 | 处数 | 改完是什么样 |
|---|---|---|
| 贴面卡片 / 列表项 | 37 | 无影子，层级由贴面色调承担 |
| 骨架屏占位块 | 7 声明点 / 42 渲染实例 | 无影子，**底色不变**（与真实卡同档） |
| 内容限制遮罩 | 2 | 无影子（半透明压暗已提供分离） |
| 错误徽标 | 1 | 无影子（色调抬升已完成） |
| 非 utility 通道的阴影声明 | 1 | 删除该条声明 |
| 按压反馈用阴影 | 5 | **删除**该通道，改走既有状态层 / 透明度手段 |
| 悬浮类界面（菜单项 / 弹层 / 对话框 / FAB / snackbar / 工具条 / 导航条等） | 15 | **不动**（现状已正确） |
| 改造后总余额 | **15 处** | 全部是悬浮元素 |

## User Stories

> actor 取真实用户角色；编号连续。每条都是**用户可验证**的外部行为，不含实现细节。

### A. 浏览列表（最常见路径）

1. As a **刷推荐流的漫 reader**, I want 滑动时卡片靠底色深浅分层而不是靠一堆重复的灰影子, so that 我的视线落在作品上而不是落在一堆卡片边缘上。
2. As a **在关注 / 收藏 / 书签 / 书架间切换的追更用户**, I want 这几个页面用同一套「贴面不浮起」的观感, so that 换页面时我的空间感是连续的、不会突然觉得某个页面的卡片浮在空中。
3. As a **打开他人主页的访客**, I want 作品网格与页面下方的列表卡层级表达一致, so that 我能分清「这是作品」和「这是信息行」而不是看到两种高度的卡片。
4. As a **打开设置页做一次设备维护的用户**, I want 设置项卡与其它设置卡一样干净、不浮着, so that 设置页看起来像一个连续的列表而不是 11 块拼起来的板子。
5. As a **在长列表里快速滑动找某一页的读者**, I want 屏幕里几十张卡片之间没有互相干扰的投影边缘, so that 快速滑动时我的眼睛不会被「边缘噪声」反复拉扯。
6. As a **看内容受限作品的读者**, I want 遮罩把受限内容明确压住, so that 我一眼知道「这里被挡住了」而不是把它当成一张有厚度的卡片。

### B. 加载中

7. As a **首次进入任意列表页的用户**, I want 加载占位块与真实卡片同色调、不浮起, so that 我不会把「正在加载」误读成「内容已经在了」。
8. As a **在弱网下等待列表加载的用户**, I want 一屏占位块不再拖着同款影子, so that 加载态的视觉噪声低于内容本身、我不会觉得屏幕卡住了。
9. As a **在加载完成的瞬间观察界面的用户**, I want 占位块被真实内容替换时底色不发生跳变, so that 页面不会「整屏往下一陷」——那一下看起来像出错而不像加载完成。
10. As a **用推荐流加载的用户**, I want 走共享骨架组件的那条路径保持现在的样子, so that 「已经清理干净」不会被一次「顺手统一」改回带影子的形态（这条是**防回归**故事）。

### C. 按压任意可点元素

11. As a **下拉刷新并按下菜单项的用户**, I want 按下时元素底色变化, so that 我得到「按到了」的反馈，而不是看到菜单项往页面里陷。
12. As a **按住悬浮主按钮的用户**, I want 按钮整体变淡一点, so that 我得到「按住了」的即时反馈，而不是看到它的影子消失。
13. As a **点击任意列表行的用户**, I want 点击反馈不表现为「这一行暗下去 / 陷下去」, so that 界面不会在按下瞬间看起来像损坏。
14. As a **在暗色模式下点按任意元素的用户**, I want 按压反馈同样可见, so that 暗色下我不会误以为点击没生效。

### D. 打开各类浮层（这 9 类悬浮界面现状基本正确，故事多为**保持**）

15. As a **阅读长篇的用户**, I want 底部弹层明确浮在列表之上, so that 我知道它是临时的、盖住了当前内容。
16. As a **被追问是否加入追更的用户**, I want 居中对话框明显压在最上层, so that 我不会把它和背后的弹层混为一谈。
17. As a **下拉刷新的用户**, I want 弹出菜单项浮在列表之上、不与列表糊在一起, so that 我能看清菜单的边界。
18. As a **看到操作消息的用户**, I want snackbar 在底部清晰可读、不与底栏视觉混淆, so that 我不会漏掉提示。
19. As a **选中小说正文一段的用户**, I want 文本选择工具条浮在选中文本之上, so that 我能看清可点的操作。
20. As a **需要随手回到顶部 / 刷新的用户**, I want 悬浮按钮浮在列表之上, so that 它不会被下面的卡片盖住。
21. As a **看顶部导航的用户**, I want 导航条与内容之间没有多出来的投影, so that 顶栏读起来是稳定的横条而不是浮在半空的一块。

### E. 暗色模式

22. As a **夜间使用手机的用户**, I want 暗色模式下贴面卡片与页面底色的层次依然可辨, so that 卡片不会和背景糊成一片。
23. As a **夜间打开弹层 / 对话框的用户**, I want 浮层在暗色下仍然能从背景里浮起来, so that 我知道它是盖在内容上的。
24. As a **夜间看到受限内容的用户**, I want 遮罩的压暗效果在暗色下依然成立, so that 我知道那里被挡住了。

### F. 减弱动效偏好

25. As a **开启了系统「减弱动效」的用户**, I want 骨架屏的占位动画照旧停摆, so that 本次清理不会破坏我已经关掉的动效。
26. As a **开启了「减弱动效」的用户**, I want 界面不因为这次改动出现任何新的动画, so that 我的偏好设置依然被尊重。
27. As a **开启了「减弱动效」的用户**, I want 骨架动画停下来之后占位块也不会因此看起来「浮起来」, so that 少了一层动态对比之后占位块不会变得更粗糙。

### G. 维护者（防止缺陷再次长回来）

28. As a **维护者**, I want 新增一张贴面卡片却顺手带上阴影时门禁立刻报红, so that 意图是「写错能失败」而不是「靠 review 记得」。
29. As a **维护者**, I want 全局搜索最低档阴影令牌时搜不到任何生产消费点, so that 「零阴影」是一个可搜索的档位而不是「什么都没写」。
30. As a **维护者**, I want 在真机上能一眼判断「哪层浮、哪层贴」, so that 即使某台设备完全不渲染阴影，层级仍然成立。
31. As a **维护者**, I want 不需要先等某个引擎能力探针出结论就能完成这次改造, so that 改造不会被一个未验证的引擎问题卡住。

## Implementation Decisions

> 翻译 ADR-0212 的 8 条决策。**不写具体文件路径与代码片段**——实现定位一律回查对应决策。

### 决策 1 → 判据只有一条：这个元素是「贴在页面上」还是「浮在页面上」

贴面 → 由表面色调表达层级，允许阴影档 **0**；悬浮 → 色调 + 阴影，按上表取档。「允许阴影档」是**上限，不是目标值**。

| UI 类别 | 表面色调档 | 允许阴影档 | 现状判定 |
|---|---|---|---|
| 页面底层 | `surface` | 0 | 已正例 |
| 顶部导航条 | `surface-container` | 0 | **已正例** |
| 贴面列表项 / 卡片（静止） | `surface-container-lowest` | **0** | ❌ 待清理（现存最低档消费的主要来源） |
| 骨架屏占位块 | `surface-container-lowest` | **0** | ❌ 待清理 |
| 悬浮卡片（抬起 / 选中态） | `surface-container-high` | 2 | 当前无独立消费点 |
| 菜单项 | `surface-container-high` | 2 | **已符合** |
| 底部弹层 | `surface-container-high` | 3 | **已符合** |
| 居中对话框 | `surface-container-high` | 3 | **已符合** |
| 悬浮按钮（主按钮 / 环层） | `primary-container` | 3 / 2 | **已符合** |
| snackbar | `inverse-surface` | 3 | **已符合** |
| 悬浮条 | `surface-container-high` | 3 | **已符合** |
| 文本选择工具条 | `surface-container-high` | 3 | **已符合** |
| 小徽标 / chip | `surface-container-high` | **0** | ❌ 待清理 |
| 内容限制遮罩 | `scrim` | **0** | ❌ 待清理 |

**表读法**：带「已符合」的行**一个都不动**。本决策的价值是把「对」的部分钉成规则、把「错」的部分圈出来，**不是重排全站**。

**⚠️ 骨架屏为什么不升到中间那档色调**：贴面主力的最低色档是全仓使用最广的底色，骨架屏的正确形态是**与它将要替换的真实卡片同色调**。若给骨架换一个色档，数据落定时会出现一次额外的色调跳变——那是往粗糙上再加一刀。色阶断档另按决策 5 处置。

### 决策 2 → 阴影预算是上限；零阴影必须**显式**写出来

1. 贴面元素（贴面卡片、骨架屏、徽标、遮罩）**上限 = 0**，即最低档（值为「无」）。
2. 该档**不是「什么都没写」，是必须显式写**。显式写 0 才有可搜索、可门禁的口径——意图不是减少写法，是**让写错能失败**。
3. 悬浮元素按上表取档，**不得越档**（该取 3 的不许写 4）。
4. 降档时**优先删声明**，不优先改写成 0（两者渲染等价）。
5. **例外仅一处**：同一元素有静止档与 `active:` 档的成对表达时，写 0 才能表达「静止无阴影」这个事实。
   > ⚠️ **本批 5 处按压反馈不落进这个例外**：它们要删的是 `active:` 那一档，静止档（2 或 3）原样保留，**不存在「两档塌成同一档」**。
   > 因此这 5 处**一律删除** `active:` 声明，**不得**改写为最低档——`active:` 档写成「无」等于「按下时影子消失」，仍然是**用阴影表达状态**，且直接违反复核判据第 2 条（该判据按字面覆盖**全部**档位，含最低档）。

### 决策 3 → 最低档 53 处的逐类裁定

| 类别 | 处数 | 处置 | 理由 |
|---|---|---|---|
| 贴面列表项 / 卡片 | 37 | → 0 | 层级已由贴面色调表达，影子是第二信号 |
| 骨架屏占位块 | 7 声明点（42 渲染实例） | → 0 | 见决策 7 |
| 内容限制遮罩 | 2 | → 0 | 半透明压暗已提供分离，影子是冗余 |
| 错误徽标 | 1 | → 0 | 色调抬升已完成 |
| 非 utility 通道的阴影声明 | 1 | → **删除该条声明** | 同上；该卡片是贴面卡 |
| 按压反馈 | 5 | → **删除（换手段）** | 见决策 6 |

**结果：最低档余额 = 0**，全站余额 68 → **15**（5 + 10）。**净方向是删除 `box-shadow`，不是新增**——这个方向性事实是决策 8 全部独立性的来源。

### 决策 4 → 最低档立即消费；最高两档明确不用（含来源等级）

| 档位 | 来源等级 | 裁定 |
|---|---|---|
| level 0（值为「无」） | **官方一手**（MD3 定义 level 0 为无阴影），非外推 | **立即消费**：44 处贴面元素 + 2 遮罩 + 1 徽标 = **47 处显式零阴影**（另 1 处非 utility 通道走删声明） |
| level 4 / 5 | ⚠️ **外推**，非官方一手表 | **暂不消费** |

**「外推」必须随引用同行登记**：这两档的定义行带「外推」标记，数值按该文件段首的可复算规则接续而来，**不是官方一手值**。任何汇总文档引用它们时必须带上这个来源等级。

**为什么暂不消费而不是「留着备用」**：① 最高两档在本项目的界面清单里**没有落点**，现在消费它就必须新造一个比现有悬浮层更高的组件，那是**为了用令牌而用令牌**；② 外推档 + 零消费 = 事实上的安全状态——定义留在令牌文件里当**能力储备**，用它渲染用户可见界面则超出证据支撑；③ 令牌**在位**与令牌**在用**是两件事，本决策只区分、不推翻上游「六档全部定义」的要求。

**解封条件（须同时满足，缺一不解封）**：多层阴影探针**阳性**（证明多层渲染在真机可用）；出现一个**确实需要高于现有最高悬浮度**的界面（须写明它为什么不是底部弹层 / 对话框）；真机截图对比确认观感可接受。届时**先补最高色阶的色调档位**（该档已有 28 处消费，是现成的最高色阶），再开阴影档——仍是主在前、辅在后。

### 决策 5 → 表面染色**不承载**层级（色阶断档只登记、不选边）

**先纠正一个可能的误读**：MD3 官方口径是「elevation 每级主要由 surface tint 表达」。**本项目不能照字面执行**，原因是可复算的——**14 套色板里表面染色与主色逐个取同值**（复算命令见 §Further Notes）。两者信息量完全相同：「加染色」和「加主色」在本项目是同一个颜色。MD3 之所以能用染色表达层级，是因为染色强度随 level 递增；本项目的染色是**单一值**，没有强度阶梯，套上去只会得到「所有层级染同一种蓝」，**表达不出层级差**。

因此：

- **本项目的「主」= 表面容器五档的明度分档，不是染色。**
- 表面染色的职责**收窄为「状态层式叠加」**：现存唯一消费是一处 8% 叠加（对齐 hover 层），**保留、不动**。
- **禁**把表面染色当层级手段用在卡片 / 弹层上（会用同一种蓝**抹平**层级，与本改造目标相反）。

**色阶断档的处置**：中间那一档色阶在令牌文件里 14 套色板**全部有定义**、Tailwind 键也已注册，但**全仓 0 处消费**（连它唯一的兼容别名引用也 0 消费）⇒ **实为死令牌**。本改造**不新增它的消费点**，只登记两个**互斥**候选处置、**均不在本范围内**：

- **候选甲**：把贴面卡从最低档迁到该档（对齐 MD3「卡片用该档」的官方落点）——属**色调迁移**，会改全站观感，需独立票据 + 截图回归；
- **候选乙**：确认只用四档后，**删掉该死令牌**及其 Tailwind 键与兼容别名引用。

**不选边**——两个候选都会改动决策 1 表里已钉住的档位映射，超出「消费口径」的范围。登记在此以免它被当成不存在。

### 决策 6 → 按压反馈与阴影分离（语义收口）

**硬约束：禁写 `active:shadow-[var(--md-elevation-*)]`（含最低档）。** elevation 档位是**高度**语言，不是**状态**语言；状态反馈走状态层，不走阴影。

按底色分三种处置：

| 元素底色 | 现有按压反馈 | 处置 |
|---|---|---|
| 菜单项 ×3（`surface-container-high`） | 已有 `active:bg-layer-pressed-on-surface` | **仅删除** `active:shadow-…-1`，状态层保留 |
| 列表悬浮按钮（`primary-container`） | 已有 `active:bg-layer-pressed-primary` | **仅删除** `active:shadow-…-1` |
| 悬浮主按钮（`primary-container`） | **无任何状态层** | 改用 `active:opacity-80` |

**为什么主按钮不能用状态层**：状态层令牌在项目里实测只有 5 个 role，**`primary-container` 不在其中**。给不存在的档位硬套一个是最典型的**静默错色**。而 `active:opacity-*` 在项目里**已有先例**（多页在用），该按钮自身的忙碌态也已经在用透明度降级 ⇒ 取站内既有手段，**不新造**。

> ⚠️ **`primary-container` 档状态层缺失是令牌层的真实缺口**，登记在此。补齐它属于**新增令牌**，**不在本改造范围**。

**⚠️ 两个待真机验证项（不得跳过，回填前按「待验证」处理）**：

1. `active:opacity-*` 在 Lynx `:active` 下**是否生效**。上游已证实**伪类匹配本身**可用（`active:bg-primary` 真变色），但 `opacity` 属性是否响应 `:active` **未单独验证**。探针设计与决策 8 同批采。
2. `active:bg-layer-pressed-primary` 画在 `primary-container` 底色上的**观感**。上游已实证 Lynx 的 `background-color` 是**替换**语义，alpha 层会替换掉底色。该组合**现网已在用**，本改造只删阴影不动它，但**观感未经真机取样**。

### 决策 7 → 骨架屏专项（7 声明点 / 42 渲染实例，最优先）

本项目的骨架屏有**两种形态，只有一种带影子**：

- ✅ **共享骨架组件形态**（推荐列表流）—— **组件内无 `box-shadow`，天然合规**。它是本仓现成的**正确先例**。
- ❌ **内联 `v-for="n in N"` 形态**（各列表页的假数据行）—— 7 个声明点**全部**带「贴面底色 + 最低档阴影」。

**处置**：

1. 7 个声明点的阴影档 → 最低档（**显式写 0**；理由见决策 2 规则 4：同骨架内重复的声明点，逐点改动最直观）。
2. **底色保持不变**（决策 1 已论证：与真实卡同档，避免色调跳变）。
3. **共享骨架组件不动**——它已经是目标形态。
4. **收敛手法**：根因是「内联骨架块逐页各写一遍，抄了列表行的阴影没抄对」。短期 7 处机械改写；**长期建议**让内联骨架行也收敛到共享组件，**但组件化重构不在本范围内**（会改渲染树结构，触及既有的三态互斥约束）。

**为什么这条最优先**：42 个渲染实例**同帧同时可见**，是加载态里最刺眼的粗糙来源；改动是**纯删除**、零新增声明、零跨组件影响。

### 决策 8 → 多层阴影的引擎约束：探针设计 +「主」不依赖它

上游留下一条**未验证**的引擎约束（多层 `box-shadow` 的支持度未知）。本改造**正面处理**它：给出可执行取证方案，并**明确本改造不建立在这个未验证能力之上**。

**探针设计**：必须把「多层是否被解析」与「CSS 变量是否被解析」这两个变量**拆开**，否则结论不可归因。四个色块**同屏同批**：

| 探针 | 声明 | 角色 |
|---|---|---|
| **P1** | 单层字面量阴影 | **阳性对照**——证明引擎能渲染阴影、证明采样方法有效 |
| **P2** | 双层字面量（等于 level-1 配方） | 测「多层」 |
| **P3** | 经变量的双层 | 测「多层 × 变量」 |
| **P4** | 「无」（最低档的值） | **阴性对照**——证明「无阴影」确实渲染为无 |

**判读表**：

| 观测 | 判读 | 对本决策的影响 |
|---|---|---|
| P1 有影、P2 有影且**第二层轮廓可辨** | 多层生效 | 「辅」可用，权重不变，仍以「主」为准 |
| P1 有影、P2 **无影** | 多层被整条丢弃 | 「辅」在真机完全失效，层级 100% 由色调承担 |
| P1 有影、P2 **仅第一层轮廓** | ⚠️ **只取第一层** | **最危险的一种**：元素「看起来有阴影」，但高档位的第二层配方静默丢失 ⇒ 档位间差异被压缩，「辅」传递不出可分辨的层级 |
| **P1 也无影** | 阴影整体不生效 | 「辅」全站失效 ⇒ **「主」不受影响** |

**P1 是强制阳性对照**：若 P1 也不亮，「什么都没发生」无法区分「多层不支持」与「阴影整体不支持」——上游首版探针正踩过这个坑（探针本身没有事件处理器，三个探针全阴，若就此收工会得出错误结论）。**判据必须自带阳性对照**，沿用该纪律。

**取证方法（避免上游记录过的取样坑）**：

1. 阴影是**投影**，**不能采元素中心像素**（那是底色）。在每个色块**正下方偏移 `blur + spread` 处的水平扫描线上取最小亮度**——投影最深处即最暗点。
2. **必须同时留截图**作为佐证。上游曾因「取样点未落在按钮填色区」记下一条**不可信的绝对像素**并撤稿 ⇒ **单点数值只作辅助，截图才是判据**。
3. `light` 与 `dark` **两套色板各跑一次**（暗色下阴影 alpha 的观感不同）。
4. 4 色块**一次采完**，不跨批次（避免设备亮度 / 环境光差异混入）。

**「主」不依赖该能力（三条独立理由）**：

1. **「主」= `background-color`**，这是本项目已被反复证实可用的通道——上游真机证据里 `bg-*` **每一次都真的改变了颜色**。决策 1 的映射表**整张表都是底色**。
2. **本改造净方向是删除 `box-shadow`，不是新增。** 探针无论判「生效」还是「不生效」，决策 3 / 6 / 7 的改动**都已经做完了、都不需要回滚**：
   - 若多层**生效** ⇒ 删完之后观感变平，这正是 MD3 的目标形态；
   - 若多层**不生效** ⇒ 删完之后观感**不变**，等于白删但无害。
   **两种结果下本改造都成立，只有「辅」的权重不同。**（见 §Further Notes「结论无关性」）
3. **唯一可能新增阴影的地方（最高两档）已被决策 4 显式推迟**——且解封条件的第一条就是这个探针阳性 ⇒ **新增路径默认关闭**。

**结论**：探针是**为「辅」定量**的，**不是方案成立的前提**。

## Testing Decisions

### 0. 什么样的测试算好（本改造的判准）

- **只测外部行为。** 本改造的外部行为只有两类：**令牌消费点集合**（可搜索的声明面）与**真机渲染出的像素**。不测内部 helper 的实现细节。
- **每条判据自带阳性对照。** 若一个判据在「什么都没发生」时也通过，它就分不出「不支持」与「没生效」——上游首版探针的首版假阴性就是这么来的。
- **每条判据配一个反事实，且反事实要喂两种换皮形态**（空白换皮、引号换皮、CSS 位置 vs 类名位置），避免单形态门禁 fail-open。
- **抽取器自身必须被测。** 正则塌陷后全称断言会**静默恒真**（最危险的假绿形态）。每条规则都要有「扫描面非空 / 命中数 ≥ 下界 / 扫描确实跑在真实目录上」这类自证。
- **真机像素的期望值必须可溯源。** 断言指向独立来源（官方令牌值、色板定义），**禁自洽反推**。

### 1. 本技术栈的第三类失败模式 ⇒ 为什么必须是**双层**

除「构建过 / 类型过 / 单测过」之外，本栈存在**第三类**失败模式：**以上全绿、产物里确实有该 CSS 规则、真机却渲染为空。**

**静态手段在原理上抓不到它。** 对「删阴影」这类改动尤其致命：

- **删对了没有奖励**——门禁全绿不告诉任何人这次删对了；
- **删错了看不出来**——若把**该留**的悬浮层阴影一并删掉，静态门禁只会更绿，而那个元素会**静默地**失去它唯一的抬升线索，融进背景里。

因此本改造的门禁是**两层**：

- **第一层：静态门禁**（进 CI）——守住「消费点集合」不回流；
- **第二层：真机像素门**（手动按需，**不进 CI**）——守住「真机上层级仍然可辨」。

### 2. 第一层：静态门禁（落为既有 MD3 门禁宿主的规则 9）

**仓内既有先例**：既有 MD3 门禁文件已积累规则 1–8（MD2 缓动不得回流 / 未接令牌圆角不得回流 / 正文自选行高不得回流 / 状态层不得用预计算实色 / 旧语义别名不得回流 / 禁裸 `:focus` / 禁裸图标字形 / 禁组件内声明 `@font-face`），其既有纪律直接沿用：**每条规则须有反事实 + 抽取器自身有效**，反事实喂**两种换皮形态**。上游 ADR 的复核判据已指定本组判据挂在该文件的规则 9。

**每条判据 + 它抓不到什么**（AGENTS.md「门禁冻结线」：假绿比没门禁更糟，**失效面必须显式登记**）：

| # | 判据 | 抓什么 | **已知失效面（抓不到什么）** |
|---|---|---|---|
| 9.1 | 贴面零阴影：带贴面底色的骨架块 / 列表行容器**不得**带任何非零阴影档 | 决策 3 的 48 处回流 | ① `.ts` 全文与 `.vue` 的 `<script>` 块内**拼接的类名**是盲区（上游已登记的既有结构性边界）；② 抓不到「本该删声明却写成 0」的美学问题——两者渲染等价、静态不可判；③ **抓不到引擎端变量未解析**：写了 0 但真机若不认这个档位，无人在静态层发现 |
| 9.2 | `active:shadow-[var(--md-elevation-*)]` 命中数必须为 **0**（**含最低档**） | 决策 6 的 5 处回流 | ① 抓不到「用 `active:opacity` 表达了错误语义」——手段合法性 ≠ 观感正确；② **抓不到真机 `:active` 是否触发**（决策 6 待验证项 1）；③ 抓不到替换写法绕过字面（如运行时拼类名） |
| 9.3 | 扫描面**必须同时覆盖 `<style>` 块内的 CSS 声明** | 非 utility 通道的阴影声明（既有反例：某玻璃卡组件的 scoped 声明） | ① **注释里的提及会误报**：实测已有一处 `<style>` 注释以正文形式提到 `box-shadow`，**必须先剥注释**再判；② 抓不到「同一属性由多个声明叠加 / 继承而来」的情形——只能扫**声明** |
| 9.4 | 最高两档消费处数必须为 **0** | 决策 4 的解封绕过 | ① **抓不到绕过令牌直写字面量阴影**（如 `shadow-[0_2px_4px_rgba(...)]`）——这是本条的真实漏口，需靠 code review 或另设判据补，**本 spec 不假装它已被覆盖**；② 抓不到「令牌键被改名导致类名整体失效」 |
| 9.5 | 最低档消费处数必须 **≥ 1** | 令牌闲置（延续上游「死代码应删」原则，**反向**要求它不被闲置） | ① 抓不到「数量达标但分布错了」（比如 47 处里混了不该显式写 0 的场合）——只有总数维度可判 |
| 9.6 | 最低档在生产 `.vue` 的消费处数必须为 **0** | 决策 3 余额钉零 | ① 抓不到「把错误档位写成别的档位」——例如本该归零却写成中档，判据 9.4 只管最高两档；② 抓不到 Tailwind 档位键被删导致类名不产声明的**反向**失效 |
| 9.7 | 真机探针的四判读结论**必须回填**到上游 ADR 的决策 8，并注明设备 / 色板 / 日期 | 流程门禁，防止未验证结论被当既成事实引用 | ① **抓不到结论本身对不对**——它是流程门禁不是正确性门禁；② 抓不到「回填了但引用方仍在别处转述旧结论」，需靠文档纪律 |

**本组门禁的共性失效面（一句话登记）**：**全部 7 条都在静态层，对「真机渲染为空 / 渲染与声明不一致」零覆盖**。这正是第二层存在的理由。

### 3. 第二层：真机像素门（手动按需，不进 CI）

**仓内既有先例**：仓内已有一套真机截图矩阵管道 —— 采集脚本（`capture-md3-matrix.sh`，1230 行）+ 证据表生成器（`scripts/md3-matrix-inventory.py`，150 行），并且**生成器本身有行为门禁**（`md3MatrixInventory.test.ts`，372 行，登记了 11 个变异，含一个「无效变异」被如实登记为无效）。本改造**复用这条管道**，只新增一条测量，不新建采集体系。

**关键设计：断言「主」，不断言「辅」。**

> 像素门要测的不是「阴影还在不在」——那取决于一个**未验证**的引擎能力，测了只会得到一个**不稳定的门禁**。
> 要测的是：**悬浮元素与它背后的底色之间存在可测的明度差**。
> 只要这个差存在，层级就成立——**无论引擎渲不渲染多层阴影**。这正是决策 8 两种结论都能通过的原因，也是本改造可以不等探针就上线的技术根据。

**新增测量的形态**：

1. 在采集矩阵里，**明暗两套色板各取一组页面**（两套都必须测：暗色下阴影 alpha 的观感不同，且「明度差」判据在暗色下更关键）；
2. 对每类悬浮界面，取**元素底色区**与**紧邻的背景底色区**两点，比对亮度差 → 断言「可分辨」；
3. 对每类贴面元素，断言其底色与**页面底层**之间存在**稳定的、非零**的色调差（这是删掉影子之后层级仍然成立的唯一保证）；
4. **截图才是判据，数值只作辅助**——沿用决策 8 的取证纪律（上游曾因取样点落空而撤稿一次）。

**第二层的已知失效面（必须登记）**：

- ① **抓不到「阴影被删了但色调差也不足」**——若某处贴面卡片的底色被同时改掉，两点采样可能仍在阈值内通过；**唯一可靠的兜底是 review 与 9.1 的底色档位判据**；
- ② 抓不到非采样点的观感：影子的**脏边**、多层的**叠影浑浊**、观感上的「浮得过多 / 过少」；
- ③ 抓不到**跨设备一致性**——像素门在单台设备单次采样上跑，**不能**证明所有机型一致（这是它替代不了 E2E 与人工观感的地方）；
- ④ 抓不到**时序 / 交互态**：按下瞬间、长按态、弹层动画过程中的画面，本测量取的是稳态帧；
- ⑤ **它不是 CI 门禁**——不进流水线 ⇒ 一次绿灯**不代表**它这次真的跑过。执行记录必须留档（沿用证据表生成器的「不一致时退出码非 0」纪律）。

### 4. 30% 规模线自检（AGENTS.md 硬约束：单个门禁文件不得超过其被测对象的 30%）

| 项 | 实测值 |
|---|---|
| 被测对象（生产 `.vue` 语料） | **76 个文件 / 15334 行** |
| 30% 上限 | **4600 行** |
| 门禁宿主现状 | **1322 行 / 70 个 `it`**（≈ 被测对象的 8.6%） |
| 规则 9 预算 | 7 条判据 ⇒ **净增上限 400 行 / 约 11 个 `it`**（合计 1722 行 ≈ **11.2%**） |

**预算纪律**：规则 9 若预计超过 **400 行净增**，必须**拆成独立门禁文件**，不得继续堆进既有宿主。单文件逼近 **4600 行**（= 4600/15334 的 30%）即触发「停止加码」，先回答「我是在防回归，还是在给回归创造就业」。

**自检结论**：本设计的门禁增量（400 行）**远在规模线内**，且每条判据都必须带反事实 + 抽取器自证——这些是**判别力**的必要成本，不是加码。若实施中某个判据膨胀到需要大量白名单才能过，**应怀疑判据本身过严**，而不是加白名单。

### 5. 什么**不**算好测试（本改造的负面清单）

- ❌ 断言「某个组件的 `class` 属性等于某个字符串」——那是快照，不是外部行为；
- ❌ 断言「删掉了 N 处阴影」——N 是本改造的**结果**不是**行为**，且会随合法的零星调整破裂；
- ❌ 为了让像素门转绿而**调低**明度差阈值——先问「用户是否真的分不清」；
- ❌ 引入「多层阴影可用/不可用」的静态断言——**那是探针的结论，不是代码能保证的事实**（见 §Out of Scope）。

## Further Notes

### 分批落地、分批回归（**硬要求**）

本改造**不是**唯一落在这一批 UI 上的变更——**排版变更**与**缓动变更**与它**同批重叠**。

> **必须分批落地、分批回归。** 三者一次性合并落地将**无法归因**：用户或我们看到「界面变了」，但说不清是变平了（层级）、字变了（排版），还是动效变快了（缓动）。**归因不了就没法回归**——下一次出问题时，无人能判断是哪一批引入的。

**因此**：

1. **单独一批、单独提交、单独回归**。提交信息须标注这是层级改造，**不得**与排版 / 缓动改动混入同一次提交；
2. 每批落地后**立即**跑该批的静态门禁 + 真机像素门**并留档**，不要攒到最后一起验；
3. 真机像素门的**截图对比必须在固定色板 + 固定页面 + 固定设备亮度下采**（决策 8 取样纪律第 4 条），否则「变平了」与「设备亮度变了」分不开；
4. 回归时若发现「界面变平」超出预期，**先查是不是把不该删的悬浮层阴影也删了**（决策 3 的 15 处余额是否还在），再查色调档位。

### 结论无关性（本改造最大的实施风险缓释）

**本改造净删除 `box-shadow`、不新增。** 因此：

> 多层阴影探针的**两种结论下，改动都已经做完、都不需要回滚**。
> - 若多层**生效** ⇒ 删完后界面变平，**这正是 MD3 的目标形态**；
> - 若多层**不生效** ⇒ 删完后界面**不变**，等于白删但无害。
> **两种结果下本改造都成立，唯一的差别是「辅」的权重。**

**推论（写给实施者）**：**不要**把本改造的合并条件挂在探针结论上。探针只决定「辅助手段」值多少权重，**不决定本改造该不该做**。把探针当阻塞项是误用——那会让一个**已完成的正确改动**被一个**不影响其成立性**的问题无限期挂起。

### 数字口径差异登记（不掩盖）

| 项 | 上游写法 | 本 spec 采信 | 依据 |

### 顺带发现的文档缺陷（登记，本 spec 不修）

实测发现：仓内**已有一处组件的 `<style>` 注释**以正文形式写着「MD3 表达层级的主要手段是给表面染上主色（surface tint），box-shadow 仅为辅」。

**该表述与上游决策 5 直接矛盾**——决策 5 已用可复算的事实钉死：本项目的表面染色与主色**14 套色板逐个同值**，是单一值、没有强度阶梯，**不承载层级**；本项目的「主」是表面容器五档的明度分档。

**后果有两条，都与本改造同批解决**：

1. **认知层面**：留在代码里的注释会把后来者引回 MD3 官方字面口径，正是决策 5 要纠正的那个误读；
2. **门禁层面**：它同时是 9.3「先剥注释再判」的**真实反例锚点**——任何按 `box-shadow` 字面扫 `<style>` 块的判据都会在这里误报。

**建议**：随本改造的一个独立小票修正该注释为决策 5 的口径。**本 spec 不修改任何源码**。
