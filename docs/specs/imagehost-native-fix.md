# spec: 图床下载源下沉 Java + 缓存键恒官方（native 图床修复）

> 2026-09-06 · 依据 [ADR-0143](../adr/ADR-0143-imagehost-download-source-java-sink.md) · 术语见 `packages/app/CONTEXT.md`「图床」（下载源 / 缓存键 / 源无关命中）

## Problem Statement

用户在设置里配置了图床（镜像站）并选择了负载模式，但在 Android 原生端图片**完全没有走图床**：列表、详情、动图的出图路线与图床开关毫无关系。镜像站本可让用户在没有代理/VPN 的环境下看图，这个承诺从未兑现；预取路径虽然尝试走镜像，但下载的字节被写进显示层永远读不到的缓存条目，白白浪费流量。

## Solution

把「一次下载从哪个渠道取数」的决策收敛到双引擎共享的 Java 下载层：图床开启时，缓存未命中的图片与动图 zip 自动从用户配置的镜像获取（失败自动回退官方一次）；缓存条目一律以官方 URL 寻址，因此**换源、开关图床、换镜像都不会让已缓存图片失效**。负载均衡、最快 IP 等模式在原生端真正生效；Lynx 引擎自动继承 WebView 侧配置的图床。

## User Stories

1. As 一个无代理环境的原生用户，我开启了图床后，列表 Feed 的封面图能从镜像加载出来，所以我不用梯子也能刷图。
2. As 一个原生用户，我进入作品详情页时，大图能从镜像加载，所以看图全程不依赖我的网络环境。
3. As 一个原生用户，我打开动图作品时，zip 帧包能从镜像下载并正常播放，所以动图也免梯。
4. As 一个 Lynx 引擎用户，我在 WebView 端配置过图床后，Lynx 端的图片与动图 zip 自动走同一图床，所以切换引擎不丢失免梯能力。
5. As 一个使用「单一图床」模式的用户，我选中的镜像被一致地用于所有下载，所以行为可预期。
6. As 一个使用「负载均衡」模式的用户，每次下载按权重随机选择镜像，所以流量按我的意愿分摊到多个镜像。
7. As 一个使用「最快 IP」模式的用户，探测出的最快镜像真正用于后续下载，所以模式选择不再是摆设；探测过期后自动退回负载均衡，所以探测故障不会卡住出图。
8. As 一个使用「并发请求」模式的原生用户，我看到明确的「仅 Web」标注，且原生端以负载均衡语义运行，所以不会误以为并发在原生生效。
9. As 任何一个用户，我看过的图片在切换图床、换镜像、关闭图床后再次出现时**直接命中缓存**（秒开、零网络请求），所以换源不浪费流量也不拖慢体验。
10. As 一个用户，同一张图无论从哪个来源首次加载，缓存里只有一份，所以磁盘占用与缓存管理页数据保持干净。
11. As 一个镜像临时挂掉的用户，下载自动回退官方重试一次，所以镜像故障退化为「回到原有路线」而不是图片全黑。
12. As 一个把图床配置改坏（或存储损坏）的用户，应用表现为图床关闭并给出可见告警，所以不会白屏、不会崩溃、问题可诊断。
13. As 一个浏览详情页的用户，预取提前拉取的图片在渲染时直接命中，所以预取不再是浪费流量的空转。
14. As 一个设置页用户，我在并发请求模式上看到「仅 Web」说明，所以对原生端行为有正确预期。
15. As 一个维护者，四模式的选择逻辑、探针 TTL、失效兜底集中在一个 Java 深模块里，所以修一处全引擎生效，不会出现「图片改了 zip 忘了」。
16. As 一个维护者，缓存键与下载源的解耦有机器防线（anti-drift 测试），所以未来改动不会悄悄重新引入键断裂。
17. As 一个 Web/开发模式用户，我现有的图床行为（预取/竞速走代理路径）保持原样，所以开发体验零回归。

## Implementation Decisions

- **接缝（seam）**：Java 下载层的「URL 进 → 下载源出」。新增深模块 `ImageHostConfig`（双 flavor 共享源集），对外仅一方法 `resolve(officialUrl)`：图床关/配置损坏/无可用 host/非 http(s) 入参 → 原样返回；否则按模式选定 host 输出 host 替换形态（path+query 逐字节保留，`{path}` 模板语义与 JS `transformUrl` 一致）。
- **接入点（四个薄适配）**：共享图片加载核心的下载入口（覆盖 webview 图片+zip 显示与拦截、lynx 图片）；原生预取插件方法（下载源接 resolve，缓存键保持官方入参）；Lynx 动图模块的全量 zip 与流式 zip 两方法。
- **缓存键契约（不变量）**：缓存键恒为官方 URL（`keyToFilename(rewriteUrl 产物)`），与下载源解耦；调用方必须用官方入参而非 resolve 返回值计算键。源无关命中由此成立。
- **四模式映射**：单一 = 选中 host（无效回退第一个可用）；负载均衡 = 按权重每请求独立抽样；最快 IP = 内存探针结果 30s TTL 内用最快、过期立即回退负载均衡（不阻塞等探针）；并发请求 = 原生降级负载均衡 + UI 标注。
- **探针属主**：最快 IP 的路由探针移到 Java（惰性触发、单飞、专用单线程 executor、5s 超时、样本 URL 语义与 JS 一致），双引擎生效；设置页探针（WebView UI 展示用）保持现状，两者独立。
- **配置读取**：`RawProvider` 接缝生产化读共享设置存储中的图床 JSON（`masterEnabled/mode/selectedHostId/hosts[]/fastestHostId/fastestHostExpiresAt`），String 引用比对惰性重解析；生产依赖注入（Clock/Random/ProbeFn/executor）保证接口即测试面。
- **失败与兜底**：镜像失败 → 官方重试一次（四接入点一致）；镜像 connect/call 预算低于官方；配置损坏 → 图床视为关 + warn；镜像 host 为官方域则跳过（防自环）。
- **JS 侧收缩**：原生分支的图床改写退役（预取回归官方 URL 入参）；图床 JS 逻辑仅服务 Web dev 与设置页；并发请求模式加「仅 Web」文案。

## Testing Decisions

- **只测外部行为**：`ImageHostConfig` 全部测试从 `resolve()` 单口进出（接口即测试面），注入 RawProvider/Clock/Random/ProbeFn，不触 SharedPreferences、不发真 HTTP、不用真时钟。
- **Oracle 溯源**：weighted 抽样规则以 JS `selectWeightedHost` 源码为 oracle、fastest-ip TTL 判定以 `getFastestHost` 为 oracle；契约 fixture 取自图床 store 的真实持久化形态（禁止自洽 mock，测试硬约束 #2）。
- **Anti-drift 防线**：断言缓存键函数(官方 URL) ≡ 拦截侧重写产物，防键二次断裂。
- **集成测试**：共享加载核心的镜像下载与官方回退（mock OkHttp client，先例 `PixivImageLoaderTest`）；zip 两方法改写与回退（先例 `PictelioApiModuleTest` 的 StreamSource 注入模式）；预取键契约（镜像源下载 + 官方键落盘）。
- **JS 测试**：原生分支断言预取收到官方 URL；现有断言镜像入参的用例随行为申报更新。
- **验收（真机/模拟器）**：断代理 + 开图床 → 列表/详情/动图三类出图；二次访问拦截日志 `hit`；切源不失效；镜像 zip 路径探针 200；镜像 vs 官方 sha256 一致性抽检。

## Out of Scope

- Web/dev 模式图床断裂（预取与显示缓存预热错位）——开发机有网无实际损害，另行澄清。
- 并发请求模式的原生实现（N 路并发竞速）。
- Pixiv 直连（免梯 IP 表）effort——独立挂起立项；其落地后「图床 × 直连优先级」另行决策。
- 图床设置 UI 重构（仅加模式标注文案）；`ImageCachePlugin` 行为；`s.pximg.net` 静态资源（不经下载层）；iOS。
