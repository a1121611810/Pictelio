# UI 树通道的门禁与 e2e 断言收口（#1047 / #1048 / #1049 合并规格）

> **一句话**：把 ADR-0223 已落地的运行时 UI 树通道**接进消费侧**（e2e 断言），并把它承诺的「release 不导出」**从代码级推论变成机器断言**（dex 级），同时收口该通道剩余 **6 项已登记盲区**。
>

>
> **轮次约定**（消除「第 N 轮」的歧义）：本文的轮次标签一律带票号前缀——「**#1047 第 N 轮**」= 本票（#1047）第 N 次 review 及其修复；「**ADR-0223 第 N 轮**」= `ADR-0223` 那条决策线（#1045）的第 N 次 review 及其修复（其逐轮史见该 ADR §3.4）。**两套轮次不是同一序列**（同该 ADR §3.4），本文**不重编号**。

## Problem Statement

作为 Pictelio 的维护者，我在两类问题上**只能靠约定和推论**，拿不到机器可复核的结论：

1. **「页面到底渲染了什么」没有可断言的观测面。** Lynx 4.0.1 不暴露无障碍树节点，`uiautomator dump` 在 `pictelio_ui` 上必被 SIGKILL（exit 137）⇒ `transition-matrix` / `fab-hit-testing-regression` / `lynx-bookmark-tags` 三处 e2e spec 当年**整体退到「截图 + 像素分析」**。像素 diff 判不出「这个节点存在吗」「它的语义 id 是什么」「它的几何在哪」，只能判「画面变了没有」。ADR-0223 的 UI 树通道已落地，但它**只被当诊断工具用**，没有任何 e2e spec 消费它。
2. **「release 包不含 UI 树导出能力」只有代码级推论。** 现有两道防线——`verify:android-host:release-buildconfig`（只证 release 变体 `BuildConfig.DEBUG` 的**取值**为 false）与源级接线守卫（只证每个 `scheduleIfRequested` 调用点**传的是** `BuildConfig.DEBUG`）——**都证不到 R8 确实移除了这个类**。ADR-0223 §3.3 把这一层登记为「尚未覆盖」至今。

而在这两条之上，该通道**自身的机器防线还有 6 项已登记盲区**（ADR-0223 §3.3 / §3.4）：编排层的参数解析无门禁、源级守卫不证「没有第二个导出出口」、脱敏形态④⑤无「非恒定性」自证、release 守卫的实参判定与采样点判定都是子串匹配、release 守卫的调用点标记要求 `(` 紧贴。**其中 ④ 是安全相关的**：release 下 `BuildConfig.DEBUG || someFlag` 不可常量折叠 ⇒ 该调用点在 release 包里会**真的导出 UI 树**，而现有守卫**判绿放行**。

## Solution

三件事，按「先让观测面可用、再让承诺可证、最后把防线补齐」推进：

1. **e2e 侧**：**四处** e2e spec **纳入**本规格范围，其中**三处**各接一条**基于运行时 UI 树**的断言（**叠加**，不替换现有像素断言），并把抓树能力做成共用的一份实现。⚠️ **四处的落点不同**：`md3-visual-tokens` / `fab-hit-testing-regression` / `transition-matrix` 三处**实做**（树断言）；`lynx-bookmark-tags` **明确不改**——它按**颜色**识别 chip，而树给不出颜色（属性级覆盖不足）⇒ 树接管不了「识别」，只能接管采样窗几何 ⇒ 登记在「Out of Scope」里，**不是漏做**。
2. **产物侧**：一道 **dex 级**断言，输入 = release APK，判定「UI 树导出能力在不在 dex 里」，且判定**不是自证**（对照变体必须被检出）。
3. **门禁侧**：6 项盲区逐项收口——每项要么有机器防线，要么按承诺流程登记为例外。涉及判据强度变更的，收口后**按最终 HEAD 重算**门禁规模线台账。

## User Stories

1. 作为维护者，我希望 e2e 能直接断言「页面上存在某个语义 id 的节点」，以便把「这个元素到底渲染出来没有」从像素猜测变成确定性判断。
2. 作为维护者，我希望 e2e 能断言节点的**几何**（两套坐标系下的位置与尺寸），以便判断「点击目标落在哪」而不必依赖截图像素反推。
3. 作为维护者，我希望 e2e 能断言「这个节点**可交互**且绑定了某个事件名」，以便验证交互面而不必靠「点了画面有变化」间接推断。
4. 作为维护者，我希望 e2e 能断言 a11y 标注**出现在树里**，以便回归「a11y 树不暴露节点」这条旧死路被真正绕开。
5. 作为维护者，我希望三处 spec **共用一份**抓树实现，以便修一处判据三处同时受益，也避免三份漂移。
6. 作为维护者，我希望抓树**不破坏被测状态**，以便在同一场景里既有像素断言又有树断言。
7. 作为维护者，我希望树断言只用**跨次抓取稳定**的量（结构统计量），以便断言不会因作品内容变化而假红。
8. 作为维护者，我希望树断言能用**区间或 fixture 回放**表达计数类期望，以便在不引入漂移的前提下仍然能钉住某些数量关系。
9. 作为维护者，我希望节点对应/比对用 `nodeId`，以便两次抓取之间能对得上节点。
10. 作为维护者，我希望抓树的**产物路径与命名**有唯一来源，以便 e2e 与诊断脚本不会各认一套。
11. 作为维护者，我希望 e2e 仍然**不进 CI**（保持手动发布门的现状），以便不改动门禁边界。
12. 作为维护者，我希望有一条命令能判定「release APK 的 dex 里没有 UI 树导出能力」，以便把「release 不导出」从推论变成结论。
13. 作为维护者，我希望那条命令**吃一个 APK 路径**（与构建解耦），以便能对已构建好的产物运行。
14. 作为维护者，我希望那条命令**对照变体必须打红**，以便排除「判据恒真、永远绿」这类假防线。
15. 作为维护者，我希望那条命令**判定的是类/类型而不是字符串**，以便不会因日志 tag 常量残留而误判。
16. 作为维护者，我希望发版清单里明确列出这一步（构建签名 release APK → 跑检查），以便它不会因为「没人记得跑」而长期空转。
17. 作为维护者，我希望那条命令**证不到什么**被写下来（它证的是产物内容、证不到运行时行为），以便不把它当成万能防线。
18. 作为维护者，我希望编排层的参数解析（未知参数 / 缺值 / 空串 / `--wait` 非法值）有机器防线，以便这类缺陷在 CI 里就被抓住，而不是靠人工复验。
19. 作为维护者，我希望「宿主侧没有第二个导出 UI 树的口子」有机器防线，以便将来新增触发通道时能被拦住。
20. 作为维护者，我希望那条反向守卫**覆盖 debug 变体源集**，以便「把调用点放进只存在于 debug 的源集」这条最自然的写法不会成为逃逸路径。
21. 作为维护者，我希望脱敏的六种形态**每一种都有非恒定性自证**，以便「正则写错 ⇒ 恒真断言且无人发现」不再可能。
22. 作为维护者，我希望新增的脱敏自证**不往已超规模线的门禁文件里加码**，以便不以「加判据」为代价制造新的规模线偏差。
23. 作为维护者，我希望 release 守卫能判红 `||` 形态（release 下会真的导出 UI 树的那种），以便守住「release 不导出」这条承诺。
24. 作为维护者，我希望 release 守卫能判红采样点标识误传（cold ↔ hot 互换、拼错的常量名），以便诊断者不会按错误的冷/热归属读树。
25. 作为维护者，我希望 release 守卫**看得见** `(` 前留空格 / 换行的调用点写法，以便守卫自述的覆盖面（每个调用点）与实际一致。
26. 作为维护者，我希望收紧判据后**门禁规模线台账被重算**，以便台账不会停在旧快照。
27. 作为维护者，我希望 ADR-0223 的对应行从「已登记」升级为「已修复」并挂上票号，以便下次有人查剩余盲区时看到的是真实状态。
28. 作为维护者，我希望这三票的结论**各自留档在票面上**（实施记录 + 反事实演练），以便将来复核时能看到红绿都实跑过。

## Implementation Decisions

### 一、e2e 侧（#1047）

- **观测通道**：复用 ADR-0223 已落地的宿主侧 `UiTreeDump` 与诊断脚本；**不改宿主侧实现**（那是 #1048 / #1049 的范围）。
- **触发协议**：intent extra `uiTreeDump=1` 发到 `io.pictelio.app/.LynxActivity`。采样点 `cold`（`onLoadSuccess`）/ `hot`（`onNewIntent`）；一次触发连拍 0 / 1500 / 4000ms 三档。
- **产物位置**：设备上应用专属外部目录 `ui-tree/`，文件名 `ui-tree-<采样点>-<档位>ms-<序号>-<时间戳>.json`；`adb pull` 直取。
- **抓树不破坏被测状态**：`am start` 打到**前台运行**的 App ⇒ 走 `onNewIntent`（hot 采样点）⇒ Activity 不重建、状态保留。优先**把 extra 合并进该 spec 已经在发的那条导航 intent**（如 `transition-matrix` 已有的 `--es benchNav <scenario>`），让抓到的树正好是被断言的那个状态；若必须单独触发，须落在状态仍成立的位置并写明抓取顺序。
- **三处共用一份实现**：新增一个共享模块（与既有像素侧的共享模块同构），提供「触发 → 轮询等产物 → `adb pull` → 解析」能力；**不复用诊断脚本的命令行入口**（它的参数解析层无机器防线，见 #1049 ①；e2e 侧直接调 lib 层纯函数）。
- **可作活体断言基线**（跨次抓取稳定）：`nodeId` 唯一性 · `debugInfo` 键集 · `position` 坐标系结构 · tag 分布 · 事件名分布 · `attributes.class` 覆盖数。
- **不可作基线**（属性级、随作品内容漂移）：节点总数 · 最大深度 · `attributes.id` 与顶层 `id` 的非空计数 · `attributes.style`/`text`/`src` 覆盖数 · 字节数 · 耗时。⇒ 断言**结构**（「存在一个 `pictelio-hero-source-*` 语义 id 的节点」）而非**计数**；要断言计数则写成**区间**或**从入库 fixture 回放**。
- **回放用 fixture 的门禁已断言数**：顶层 `id` 占位符 **15** · `attributes.id` 占位符 **15** · 合并语义 id 计数 **16**。⚠️ ADR §3.2 表里的「`attributes.id` 16/140」是**属性级快照数、随内容漂移**，**不作期望值**。
- **节点对应 / 比对的键是 `nodeId`**（140/140 互不相同），**不是** `debugInfo.nodeIndex`（140 个取值恒为 0 ⇒ 作 diff 键**恒真**）。
- **能力边界**：本通道**拿不到源码位置**（上游 UI source map 的构建期打标是 React-only，vue-lynx 无 producer）⇒ 只能断言「结构 + 语义 + 几何」，**不能**断言「这个节点来自哪个 .vue」。
- **叠加而非替换**：现有像素断言全部保留（像素与树各答一个问题：像素答「画面变了没有」，树答「那个东西在不在、长什么样、能不能点」）。
- **门禁边界不变**：e2e 仍**不进 CI**（ADR-0084），仍是发版前手动跑的一组。
- **选档规则的单一出口（#1047 第 2 轮补）**：「哪一份产物最完整」由 `lib/ui-tree-dump-core.mjs` 的 `pickBestArtifact` 判定，**诊断编排层与 e2e 消费侧共用同一份** ⇒ 两侧不会选出不同的产物。⚠️ **这是诊断脚本的行为变更，不是等价重构**：下沉之前编排层的 tie-break 是 **节点数 → 字节数**，下沉后统一为 **节点数 → 采样档位 → 字节数** ⇒ 节点数相同的两份产物，在「4s 档字节更小」时旧规则选 1500ms 档、新规则选 4000ms 档 ⇒ 编排层收工时点名的「最完整的一份」（**面向人的结论**）在这些输入下会指向另一份产物。该变更由新增门禁 `ui-tree-dump-selection.test.ts` 的「档位优先于字节数」用例**钉成机器可见的事实**（并附旧规则对照计算 ⇒ 键序一旦被删即转红）。
- **⚠️ 已知失效面：设备上的产物会累积**（#1047 第 2 轮登记）：通道产物写在设备外部目录 `ui-tree/`，**跨运行不清理**（实测同一台模拟器上已累积 **6** 份）⇒ e2e 侧靠「**触发前快照 vs 触发后目录列表**」的差集只认**本次新增**的那些。残留失效面：若快照取到的时刻晚于产物落盘、或文件名重复（文件名含序号 + 时间戳，正常不会重复），本次产物会被误判为「旧产物」⇒ 差集为空 ⇒ 报「未产出任何产物」。这条**只有真机能复现**，CI 里**无机器防线**（IO 层单测用 mock 的目录列表，不含「累积」这一形态）⇒ 由「产物数 > 0」这条断言与真机走查兜住。

### 二、产物侧 / dex 级断言（#1048）

- **检查对象是 dex 里的类型定义**（`io.pictelio.app.UiTreeDump` 这个类），**不是字符串**。
  ⚠️ 该类持有 `TAG = "UiTreeDump"` 并在约 9 处 `Log.i/w` 里使用 ⇒ **R8 移除该类后，这个字符串常量仍极可能留在 dex 字符串池**。按字面量 grep 会恒红；写成「字面量必须不存在」则是一条**永久红**的断言。
- **判定口径定死一条**：**类 / 类型不在 dex 里**。该类 package-private，生产侧**只有 2 个引用**（都在 `LynxActivity`）⇒ 整类被移除是可能的；但 R8 也可能因某个成员仍可达而保留类壳 ⇒ 若实际构建做不到，**如实记录实际观测到的属性**，不静默把判据放软。
- **检查与构建解耦**：输入 = **APK 路径**（可对已构建好的产物运行）。
- **阳性对照变体**：在 `proguard-rules.pro` 里为 `io.pictelio.app.UiTreeDump` 加一条 keep 规则后构建的 APK —— 该检查**必须检出它**。⚠️ 该 keep 规则**只用于对照变体**，**不得**进生产构建（本仓已有同形态先例：`-keep class io.pictelio.app.PictelioImageService { *; }`）。
- **门禁落点 = 发版前手工门**（不进 CI）：CI 的 `android-unit-test` job **没有 keystore、也没有签名环境变量**（keystore 被 gitignore）⇒ 与 #1034 的 `generateReleaseBuildConfig`（**不需要** keystore，所以能进 CI）是两回事。形态 =「检查脚本/单测（吃 APK 路径）+ `docs/release-checklist.md` 里一条可手工执行的步骤（构建签名 release APK → 跑检查）」，并把「CI 化需要什么」写进 ADR 留档。
- **本检查证不到什么**：证的是**产物内容**，证不到运行时行为（release 包在真机上到底会不会导出）⇒ 作为已知失效面显式登记。

### 三、门禁侧 / 6 项盲区（#1049）

| # | 盲区 | 收口做法 |
|---|---|---|
| ① | 编排层参数解析无门禁 | **下沉到 lib 层**的纯函数：吃 `argv` 数组，吐已解析 opts 或**错误码**（不直接 `process.exit`）；编排层只把错误码映射成 `process.exit(2)`。门禁断言四条：未知参数 / 缺值 / 空串 / `--wait` 非正整数 ⇒ 非零退出 |
| ② | 不证「宿主侧没有第二个出口」+ 扫描面漏 `src/debug` | 新增**反向**源级守卫：扫宿主生产源码，断言「除 `UiTreeDump` 自身外，别处没有导出调用点」。**扫描面扩到 `src/debug/java`**（AGP 内置变体源集、自动编进 debug 变体、当前 0 个 `.java`）——本能力只存在于 debug 变体，把调用点放进它是最自然的写法。测试源集不进生产 APK，不构成风险 |
| ③ | 脱敏形态④⑤（p0 哈希 / 上传时间路径）无「非恒定性」自证 | **新增独立门禁文件**（不动已超规模线的既有门禁文件）；`FORBIDDEN` 六形态表提到**共享内核**供两处 import（**不复制正则**——复制抽取器是本仓吃过亏的老教训）。反向对照：还原 `<p0hash>` / `<uploadDate>` ⇒ 形态④⑤ **必须命中** |
| ④ | release 守卫的**实参判定是子串匹配** | 收紧为「该实参**恰好**等于 `BuildConfig.DEBUG`」。⚠️ **必须按单个实参比较**（在顶层逗号处切分实参列表、逐个 trim）——实参列表是多参形态（`…, getIntent(), BuildConfig.DEBUG, UiTreeDump.POINT_COLD`），拿整串去比会**永远为假、门禁当场转红**。配套阳性对照：`\|\|` 形态必须打红 |
| ⑤ | 采样点标识判定是子串匹配 | 收紧为「该实参**恰好**等于 `UiTreeDump.POINT_COLD` / `POINT_HOT`」。配套阳性对照：cold ↔ hot 互换、拼错的常量名，都必须打红 |
| ⑥ | 调用点标记要求 `(` 紧贴 | 放宽为「`UiTreeDump.scheduleIfRequested` 后**忽略空白**再找 `(`」。⚠️ 阳性对照**必须在 ≥3 个调用点的配置下做**：当前 2 个调用点时空白形态会红，但红的是「至少找到 2 个调用点」那条**计数下界**、**不是**逐调用点判据抓到的；调用点增至 3 个时（其中 1 个 = 空白形态 + 违规实参）守卫**全绿** ⇒ 这层保护**随调用点增长而消失** |

- **④⑤⑥ 全部属「判据强度变更」**（收紧判据 / 放宽标记）⇒ 收口后**按最终 HEAD 重算**门禁规模线台账。
- **规模线台账的重算口径**：分子 = **六个**真门禁文件行数（含 #1047 第 2 轮新增的 `ui-tree-dump-selection.test.ts`）；分母 = 消费侧口径（Node 侧 = core + 编排层；宿主侧 = `UiTreeDump` + `LynxActivity`；协议侧 = 协议两侧承载文件）；release 守卫的扫描面分母 = 扫描根递归的全部 Java 源文件。⚠️ **扫描根加了 `src/debug/java` 之后，复算命令里的 `find` 也必须同步加上第三个根**——否则台账登记的扫描面与守卫实际扫描面**不一致**（违反「分母必须与扫描面一致」）。
- **超线文件的加码禁令**：Node 侧 core 门禁（**43.7%**）与宿主侧协议门禁（**35.0%**）**已超 30%**，且 ADR-0223 里有一条**承诺**：此后不再往这两个文件加判据，必须加则先按 #1009 先例拆分。⇒ ③ 一律走**独立门禁文件**（ADR-0223 第 5 轮 `ui-tree-dump-outdir.test.ts` 的先例），**不拆分**（拆分会抬高门禁机器总量）。⚠️ **#1047 第 2 轮补的选档门禁同样走独立文件**（`ui-tree-dump-selection.test.ts`），并按 ADR §3.4 的要求**登记门禁机器总量变化**（1,646 → **1,804**、1.34× → **1.46×**）——「不拆分」不等于「不登记总量变化」。
- **④⑤⑥ 在既有门禁文件内改**（`uiTreeDumpReleaseGate.test.ts`）——判据本体在那个文件里，**另立文件或复制抽取器都不可取**。
- **② 的反向守卫**与 ④⑤⑥ 同属「release 接线守卫」这一道门禁、同一个文件 ⇒ 两票的先后顺序按「先 ② 后 ④⑤⑥」排，避免两票同改一个文件。

### 四、通用约束（来自仓库既有纪律）

- **门禁判别力三要件**：反事实（须喂两种以上换皮形态）· 抽取器自身有效（扫描面非空 + 命中数下界）· 阳性对照。
- **阴性证据三禁令**：搜到 0 条 / 手动跑过 / 门禁绿 ⇒ 一律视为空转门禁。
- **门禁硬化最多一轮**：门禁硬化只能占一轮 review-fix-loop；下一轮必须回到产品本身。
- **外部锚点**：#1048 的锚点是**真实签名 release APK 的 dex 内容**；#1047 的锚点是**真机上的真实树产物**；#1049 的锚点是**真实源码的反事实替换**（把真实源码改成违规形态 ⇒ 守卫必须打红）。
- **提交信息**：`type(scope): description`；本次预期落在 `test(android-host)` / `test(android-e2e)` / `docs(adr-0223)`。

## Testing Decisions

- **测外部行为，不测实现细节**。三条线的「外部」分别是：**e2e 的页面状态**、**APK 的 dex 内容**、**门禁对违规源码的判定**。
- **e2e 线（#1047）**：断言写在**既有 spec 内**（不是新 spec），期望值来自**真机抓到的树**；断言只用 §Implementation Decisions 一节列出的**可作基线**的那些量。判别力靠**反事实**：把被测的树产物换成一份结构不同的树（字段缺失 / 语义 id 不存在）时断言必须转红。⚠️ **「至少各有一条基于树的断言」这条验收项的兑现口径**：三处**实做**的 spec（`md3-visual-tokens` / `fab-hit-testing-regression` / `transition-matrix`）**每处都有一条 `expect` 的期望值直接来自树**（class 定位唯一性 / `tap` 事件 / 布局盒尺寸），**不是**「树只用来取坐标、断言仍是像素 diff」。
- **dex 线（#1048）**：判别力靠**阳性对照**——加 keep 规则的对照变体必须被检出；正常 release 变体必须报告「不在」。红绿都实跑并留记录。
- **门禁线（#1049）**：每条收紧的判据都必须带**阳性对照**（反事实源码 ⇒ 守卫打红），且 ⑥ 的对照须在 **≥3 个调用点**的配置下做。③④⑤⑥ 属判据强度变更 ⇒ 收口后按最终 HEAD 重算规模线台账并登记。
- **既有先例**：`uiTreeDumpReleaseGate.test.ts`（源级守卫 + 阳性对照 + 对真实源码的反事实替换）· `ui-tree-dump-core.test.ts`（真实样本回放 + 六形态脱敏 + 两条反向对照）· `ui-tree-dump-outdir.test.ts`（符号链接别名 / 大小写变体 / inode 判定）· `webviewRemovalInvariants.test.ts`（源级守卫）· `PictelioAppModuleDebugBuildTest`（BuildConfig.DEBUG 门禁）。
- **不新增 CI 门禁**：#1048 是发版前手工门（无签名凭据进不了 CI）；#1047 的 e2e 按 ADR-0084 仍不进 CI；#1049 的门禁进既有 CI 路径（`test:all` / 宿主 JVM 单测）。

## Out of Scope

- **改宿主侧 `UiTreeDump` 的实现本身**（抓取 / 连拍 / 落盘 / 告警语义）——本规格只消费与断言它。
- **诊断脚本的落齐判据、摘要统计、清理范围、目录安全校验**——那些已有门禁，本规格不动。
- **把 UI 树接进本规格范围外的其它 e2e spec**（本规格只覆盖上列**四处**既有 spec；`lynx-bookmark-tags` 虽在范围内但**明确不改**，理由见「Solution」第 1 条）。
- **断言源码位置**——上游 UI source map 的构建期打标是 React-only，vue-lynx 无 producer，此路已判死。
- **把 e2e 搬进 CI**（ADR-0084 的门禁边界不变）。
- **用树断言替换现有像素断言**——是叠加。
- **ADR-0223 §3.4 row 3 失效面 ③**（spec 字段表里那批覆盖数目前无断言）——已登记、无 follow-up，门禁冻结线第 5 条只要求登记、不要求开票。
- **新增 Gradle 模块 / 新增 source set 的扫描面**——今天 `settings.gradle` 只有 `:app` 一个模块；本规格只补**已存在**的 `src/debug` 缺口。
- **release 包在真机上的运行时行为观察**——#1048 证的是产物内容。
- **把 #1048 的门禁接进 CI**——需要仓库设置里新增签名 secrets，属仓库设置变更，不在本规格范围（已在 ADR 留档需要什么）。
