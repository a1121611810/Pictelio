# 送达通道 · 触达探测（delivery probe）

> 形态决策见 ADR-0220；术语见 notification-center 术语表「送达通道专用词条」。
> 本 spec 是 ADR-0188 D1 挂账的「Phase 2」与导航维度重构 spec §4「P2 · 送达通道」
> 这**同一件工作**的唯一规格。

## Problem Statement

作为 Pixiv 客户端的重度用户，我关注了作者、也把喜欢的系列加进了追更，但**我只能靠主动打开 App
去「更新」页翻看**，才知道有没有新作品、新章节。我希望的回执到得太迟——等我想到去看时，更新的新鲜感已经没了。

我知道官方 App 有推送，但那是 Pixiv 自有服务端的推送，第三方客户端没有接入通道。

更根本的问题是：**我不知道自己到底想不想要这个回执。** 没人问过我，我也没想过。
如果用户根本不点，那「要不要为它自建一套后台设施」这个问题就不该被提出。

## Solution

做一次**触达探测**（delivery probe）：在设备本地轮询通知，有新内容且用户**没有在主动查看**时，
发一条汇总的 Android 系统通知；记录发出与点击；**数据只留本机**。

它不是一个功能交付，**是一次测量**。产出是一个可判定的问题的答案：
「用户想不想要这个回执」——若答案是「没人点」，则连服务端推送都不必考虑。

## User Stories

### 探测的触发

1. 作为用户，我希望在我**打开 App 但没有去找更新**一段时间之后，才收到通知提醒，
   这样我不会在正看着内容时被通知打断。
2. 作为用户，我不希望我刚进 App 就立刻收到「你有新通知」——那一刻我本来就看得见更新。
3. 作为用户，我希望 App 在我**主动打开「更新」页**时不要发通知，因为那说明我已经在处理更新了。
4. 作为用户，我希望通知**不会在我前台浏览其他页面时**出现，因为它解决不了我「没打开 App」的问题。
5. 作为用户，我希望探测在 App 被完全关闭时**不运行**——本次不做后台调度（见 Out of Scope）。
6. 作为用户，我希望 App 长时间不用之后重新打开、且没看更新时，仍然能收到一条提醒。

### 通知本身

7. 作为用户，我希望一次轮询里有多条更新时，**只收到一条**通知，而不是被刷屏。
8. 作为用户，我希望通知告诉我**有多少条**新内容，而不是只说「有新通知」。
9. 作为用户，我希望通知**不泄露**具体内容（ Pixiv 通知文本多为日文且含 HTML 片段），
   点击后自己去看。
10. 作为用户，我希望通知栏的**摘要形态**与通知中心的条目语义一致，避免我点进去找不到对应的东西。

### 点击落点

11. 作为用户，我点通知后希望**直接到通知列表页**，而不是被送到一个不相关的聚合页。
12. 作为用户，我从通知中心返回后，希望能看到通知列表的正常滚动位置。
13. 作为用户，在 App **已被系统关闭**时点通知，希望它能正常把我带进 App 并落到通知列表页。

### 权限

14. 作为用户，我希望 App 只在**第一次需要时**问我一次通知权限，而不是每次启动都问。
15. 作为用户，如果我**拒绝**了通知权限，希望 App 不再反复打扰我。
16. 作为用户，如果我拒绝了通知权限，希望我仍然能在**外环「更新」项的角标**上看到未读——那是我已有的、
    不需要任何新权限的提示面。
17. 作为用户，我希望能知道「我到底有没有给权限」——否则「没数据」和「没人点」在我这里分不清。

### 未读与角标的一致性

18. 作为用户，我希望系统通知弹出时，**外环角标的未读数不要被清零**——
    因为我没点开它，不该算作已读。
19. 作为用户，我希望从通知点进来之后，角标**仍然显示真实的未读数**，直到我真的看过通知中心。
20. 作为用户，我不希望「发了通知」被系统当成「我已读」——那会让角标数字失真。

### 度量与结论

21. 作为产品负责人，我希望能读到**发出了多少条**通知，以便知道分母。
22. 作为产品负责人，我希望能读到**被点了多少次**，以便知道分子。
23. 作为产品负责人，我希望这两个数字**只存在我自己的设备上**，不上传任何行为数据。
24. 作为产品负责人，我希望能把「主动打开 App 的次数」与「通知点击数」对比，
    以判断通知是否真的带来了**增量**（本来不会打开的时刻变成了打开）。
25. 作为产品负责人，我希望**开始时间**被记下来，以便把多轮探测的时间线连起来。
26. 作为产品负责人，我希望重新开始一轮探测时，**计数清零但开始时间保留**。
27. 作为产品负责人，我希望探测报告里**明确写出权限是否拿到**，
    以免把「没权限所以没数据」误读成「有权限但没人点」。
28. 作为产品负责人，我希望结论**明确标注为定性观察**，不宣称「有用」或「无用」以外的强度。

### 边界与诚实性

29. 作为产品负责人，我希望知道本次探测**没有覆盖**哪些场景，以免过度解读结论。
30. 作为用户，如果 App 正在运行、我从通知栏点了通知，我希望它**不要表现得像坏了**。

## Implementation Decisions

1. **交付物是「触达探测」而非「通知功能」。** 验收标准是拿到一个可判定「用户想不想要这个回执」
   的数据点，**不是**「通知可用」。按功能验收会滑向「能用」，而「能用」证明不了「想要」。

2. **形态为「进入前台 + 静默期后轮询」，不使用 WorkManager 后台周期调度。**
   后台调度在系统省电策略下可能数小时不触发，会让发出样本的时间分布失真；
   而判定用的是比值，分母失真会直接毁掉判读。
   ⚠️ **这是与 ADR-0188 D1 挂账措辞（「WorkManager 周期后台检查」）的有意偏差。**

3. **必须新增一个「进入前台 / 进入后台」生命周期事件通道。**
   Lynx 侧**没有窗口 focus 事件**（既有查询客户端已因此关闭了窗口聚焦重取），
   故「前台」只能用生命周期事件近似。**沿用既有的 insets / 暗色事件同款机制**，不新造范式。
   ⚠️ 静默期因此是**近似值**，不是精确判定。

4. **新增一个原生通知模块**，承载「发通知」与「权限状态查询」。
   **计数存储不新建模块**——既有偏好存储模块已是字符串 KV，足够。
   ⚠️ 既有模块回传的字符串带 JSON 引号，JS 侧须先反解引号（既有先例可循）。

5. **计数以单一 JSON 值存储**于既有偏好存储，字段为发出数、点击数、开始时间。
   重置**只清计数两字段**、保留开始时间，使多轮探测的时间线连续。
   - **（#940 最终结论）点击数**不拆**冷/热**：只保留 `clicked` 总量。
     曾设计 `clickedCold` / `clickedWarm` 并要求 `clicked === 两者之和`，已**撤销**——
     真机逐一证伪四种候选判据（回调类型 / 进程内静态 / 持久前台标记 / 进程寿命），
     失败原因都是同一条：**处理点击这个动作本身就是状态跃迁**，点击时刻的进程内观测
     一律被它自己污染（详见 ADR-0220 §6-3）。
     留一个看似精确实则不可信的分类，比只留总量更危险——报告期一定会有人拿它下结论。
     ⇒ **口径影响**：`clicked` 是「用户点过通知」的总量，其中「App 仍开着时点的」与
     「被叫回来点的」比例**不可分离、也无法事后拆分**。报告期不得据此声称「被叫回来的比例」。
     若将来要回答该问题，需要能在点击**之前**观测的信号（如服务端到达埋点），另立决策。

6. **通知为汇总一条**，一次轮询计为**一个发出样本**，不论该批有几条更新。
   汇总形态的点击率是逐条形态的**上界**；先测上界，低于阈值即可砍掉整条路线。

7. **点击落点为通知中心列表页**，与通知本身的语义一致。

8. **只支持冷启动点击。** 冷启动可复用既有单任务 + 启动意图的架构；
   热启动需补 `onNewIntent` 覆写或全局事件总线，成本高一档。
   ⚠️ 由此产生一条**必须处理的空点**：App 存活时点通知会「点了没反应」，
   实现须保证该情形下不发通知（或补上热启动）。**这是实施期硬要求，不是可选项。**

9. **发通知不推进「本地已读记忆」。** 二者是不同语义：通知是提醒我去��，已读是我真的看过。
   混用会让外环角标与未读数失真。

10. **权限处理：查询状态 + 降级到外环角标 + 不做二次弹窗。**
    降级路径复用**已交付**的外环未读角标，零新增成本。

11. **度量口径：点击数 ÷ 发出数，再与「主动打开 App 的频率」作比。**
    绝对阈值是拍的（不同通知形态的自然点击率差一个量级），比值自校准。
    ⚠️ 但**本轮不设统计阈值**——见下条。

12. **单用户探测没有统计效力。** 把静默期代入推算：用户一天打开 App 约 5 次，
    其中约 3 次会直接去看更新而被静默期滤掉，剩余约 2 次可能发通知 ⇒ **一周约 14 个发出样本**。
    14 个样本量不出比例差异，且**这不是延长实验周期能解决的**——单用户样本上限就是用户的打开频率。
    ⇒ 结论只取**定性信号**（点过 / 没点过）。若结论为「没人点」⇒ 支撑「不必做服务端推送」；
    若为「有人点」⇒ **不可推广**。

13. **不上传任何行为数据。** 计数只落本机。若将来要做跨设备汇总，
    那是**独立决策 + 独立 ADR**，且必须先解决与决策 5（只存本地）的冲突。

14. **本探测恰好不覆盖服务端推送的主场。** 「App 长时间未打开、从通知栏被叫回来」这个场景，
    由决策 2 的前台形态排除在外。
    ⚠️ ⇒ **若结论为「没人点」，不能据此否决服务端推送。** 该限定必须写进结论。

15. **权限状态须写入探测报告。** 否则「没权限所以没数据」与「有权限但没人点」不可区分。

## Testing Decisions

**什么样的测试算好**：只测外部行为，不测实现细节。跨端契约一律断言**剥注释后的源码形态**，
且每个检测器带**夹具自检**（真实形态夹具命中、注释夹具不命中）——这是本仓既有纪律，
因为「把实现删掉只在注释里留一句」能让朴素的全文包含断言照样全绿。

**主 seam（最高层，优先使用）**：**跨端契约门禁**。既有四份同款先例（暗色 / 安全区 / 剪贴板 / 图库桥），
形态是「JS 侧读宿主源码、剥注释、断言两侧的事件名 / 方法名 / 载荷格式 / 权限声明一致」。
本批次需钉住的契约：

- 生命周期事件名与其两侧一致（新增）
- 通知模块的方法名与其两侧一致
- 权限声明（清单中存在通知权限）
- 计数存储键名两侧逐字一致
- 通知点击落点与路由一致

**次 seam**：
- **宿主侧 JVM 单测**（既有先例：剪贴板模块、下载器等模块级测试）——覆盖「本轮是否该发通知」
  这类**纯判定**逻辑（静默期是否已过、有没有新未读、汇总条数怎么算）。
- **JS 侧单测**——覆盖计数的 JSON 读写、字段级重置（开始时间保留）、发出/点击递增。

**e2e（手动发版门，不进 CI）**：覆盖「冷启动点通知直达通知中心页」这一条端到端链路。
⚠️ 不可作为唯一防线：e2e 不进 CI，且本仓已多次出现「单测全绿而真机错」。

**变异自证**：本仓纪律要求**给门禁构造它最隐蔽的坏形态并确认转红**，否则「一条断言从没红过」
本身就是可疑信号。本批次至少覆盖：把生命周期事件名改成注释里的同名字符串（应仍绿）、
真删掉发射调用（应转红）、把权限声明从清单移走（应转红）。

## Out of Scope

- **服务端推送 / FCM**（无接入通道，ADR-0188 D1 已排除）
- **WorkManager 等后台周期调度**（与决策 2 的有意偏差；本轮只在前台形态下测量）
- **前台常驻服务**及其权限
- **热启动点击落点**（决策 8；「点了没反应」的空点须在实现中规避而非本轮解决）
- **通知的逐条形态**（决策 6；汇总形态的点击率是其上界）
- **富通知 / 大图 / 进度条 / 通知分组 / 自定义声音**
- **通知内容翻译**（沿 ADR-0188：通知文本为日文 HTML 片段，剥标签纯文本渲染，不翻译）
- **跨设备统计与任何行为数据上传**（决策 13）
- **服务端已读上报**（Pixiv 无该端点；沿 ADR-0188 D5 本地推导口径）
- **角标逻辑改动**（外环未读角标已交付，本轮只复用不修改）

## Further Notes

### 与既有文档的关系

本 spec 是 ADR-0188 D1 挂账的「Phase 2」，也是导航维度重构 spec §4「P2 · 送达通道」。
**这两处此前各写一遍、依据不同、措辞不同、互不引用、都没有立项**；
ADR-0188 原文要求「系统推送需自建后台基础设施，独立立项」且「后台轮询的电量/配额/权限面
属独立 Grill 议题」——本 spec 即那次 Grill 的落地。

### 实施期硬要求（来自 ADR-0220 §6）

1. **命名陷阱**：`Updates` 页内存在一个**页面本地**的未读计数（第三段小胶囊角标），
   与通知 store 的未读计数**不是同一个东西**。降级路径要接的是**后者**（外环角标 + Me 圆点）。极易接错。
2. **热启动空点**必须规避（见 Implementation Decisions 8）。
3. **权限状态须入报告**（见 Implementation Decisions 15）。
4. **冷启动补投**沿用既有深链已验证的**多窗口重发**手法对抗渲染竞态——
   该手法在既有代码里已有先例，不要另发明一套。

### 结论的读法

本探测结束时，报告应能回答且**仅**能回答：
「在**用户主动回到 App 且没有立刻去看更新**的时刻，发一条汇总通知，会不会被点？」

它**不能**回答：「用户想不想要更新提醒」（覆盖场景太窄，见决策 14），
也**不能**回答：「通知功能对用户有多大价值」（样本量不足，见决策 12）。

### 如何读这份结论（探测器会写，但没人能读 ⇒ 实验无法收口）

计数器落在设备本地 `SharedPreferences("CapacitorStorage")` 的 `delivery_probe_v1` 键，
**没有 UI 读入口**（探测器是诊断装置，不进产品界面）。读法：

```bash
ADB=~/Library/Android/sdk/platform-tools/adb
# ① 计数（注意 &quot; 是 XML 存储层的转义，JS 拿到的是真引号）
$ADB shell run-as io.pictelio.app cat shared_prefs/CapacitorStorage.xml \
  | grep -o '<string name="delivery_probe_v1">[^<]*'
# ② 权限是否真的授予（决定了「没数据」是用户拒绝还是探测器坏了）
$ADB shell dumpsys package io.pictelio.app | grep POST_NOTIFICATIONS
```

把 ① 的 JSON 与 ② 的 granted/denied 喂给 `utils/deliveryProbeReport.buildProbeReport`，
即得出一份带四条限制的结论。**报告里必须保留那四条限制**——它们不是免责声明，
是结论的适用边界（尤其第 4 条：点击数不可被说成「被叫回来的比例」）。

⚠️ 计数会**跨轮污染**：`resetRound()` 只清计数、不清已读记忆；而落点进入通知列表页后
该页按 ADR-0188 D11 推进已读记忆 ⇒ 未读归零 ⇒ 探测器下一轮判 `no-unread` 根本不发通知。
做新一轮探测前需把 `notifications_last_read_time` 退回过去（e2e #942 的步骤 0 同款）。
