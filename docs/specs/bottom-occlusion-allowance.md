## 1. 问题陈述

根容器给 GlobalFab 预留的全局底部占位带已删除（ADR-0216），但**末屏可点性尚未恢复**：
列表滚到底时，右下角约 19.2vw × 19.2vw 区域落在 FAB 圆盘下 —— 视觉遮挡 + 吞点击
（原生不识别 `pointer-events`，透明化无效）。

现状是「删了全局带，但没人接手」。本 spec 把它交给**滚动内容末尾**。

## 2. 数据流

```
GlobalFab 自身几何（**按路由分两档**，ADR-0132 决策 2 + 票 #922）
        │   menu 档  ：bottom-4 = 4.267vw + 本体 14.933vw            ⇒ 顶边 19.200vw
        │   search 档：bottom = 43.734vw（避开分页菜单顶 42.667）   ⇒ 顶边 58.668vw
        │
        ├─▶ utils/fabGeometry.ts
        │      fabAllowanceHeightVw(routeMode)   ◀── 单一数值来源
        │        │        （routeMode = menu→19.2vw / search|hidden→58.668vw，
        │        │          由 createGlobalFab 的 routeMode computed 纯路由派生）
        │        └─▶ FabAllowanceSpacer（高度由 fabGeometry 算出的零内容 <view>）
        │                 │
        │                 └─▶ 挂在三个根页滚动容器【末尾】
        │                          · IllustList / NovelList：<list> 内末尾追加 full-span list-item
        │                          · Me：<scroll-view> 内末尾追加 <view>
        ▼
   FAB 改尺寸 ⇒ 占位自动跟随（GlobalFab 与占位共读 utils/fabGeometry.ts）
```

**不经过**根容器。系统栏 inset（`safeBottom`）仍由根容器消费一次，两者**正交不叠加**。

## 4. 接口

### 4.1 新组件 `components/FabAllowanceSpacer.vue`

```
零业务哑组件。只出内容，高度由 `utils/fabGeometry.ts` 的 `fabAllowanceHeightVw(view.routeMode)` 得出
（`menu` 19.2vw / `search` 58.668vw，**页面不传任何高度** —— 档位由路由自动推导，
否则新页面漏接线就会静默落到 19.2vw，正是票 #922 的成因）。
与 FeedListFooter 完全同构的定位：组件只出内容，外层 list-item 留在各页
（原生 <list> 只认 list-item 子节点，见 FeedListFooter 头注）。
```

### 4.2 各页接线（形态不同，但语义一致）

```vue
<!-- 插画页 / 小说页：<list> 内，**必须在 footer 之后**（= 最后一个子节点）。
     放 footer 之前会让 footer 可见时（加载中/到底）让位带不再覆盖最底部。 -->
<list-item :key="'fab-allowance'" item-key="fab-allowance" class="w-full" full-span>
  <FabAllowanceSpacer />
</list-item>
```

```vue

<FabAllowanceSpacer />
```

### 4.3 硬约束（违反即缺陷）

| # | 约束 | 理由 |
|---|---|---|
| C1 | **不得**塞进既有 footer `list-item` | footer 是 `v-if` 三态条件渲染，三态皆假时节点不存在 ⇒ 占位在最常见态失效（ADR-0217 §2.2） |
| C2 | **不得**改回根容器 `paddingBottom` 承载遮挡让位 | 内容滚不过去；沉浸页会再次受损（ADR-0216 §2.2） |
| C3 | **不得**用父容器 padding 替代零内容占位 | border-box UA 默认 vs web-core 预览不复刻 ⇒ 跨渲染器分叉（`topInset.ts` 约束 2） |
| C4 | 高度**不得**回退为 Tailwind 编译期档位或任何字面量，必须经 `utils/fabGeometry.ts` 的 `fabAllowanceHeightVw(routeMode)` 求值，**并由模板 `height:` 绑定其结果** | 档位与 FAB 的 JS 几何**不同源**，复用档位得不到跟随（code-review 实测：把 `spacing.18` 改成 30vw，占位高度纹丝不动）；回退即多出一个独立来源，重蹈漂移 |
| C5 | `item-key` 必须与相邻节点不同且稳定 | 原生 `<list>` 用它识别变更（lynxjs `<list>` 文档「Required item-key」） |

| 层级 | 方式 |

### 5.1 「主」数值量测记录（2026-10-03）

**设备**：emulator-5554 / Android 14 / 1080×2160 / density 480 / **手势导航**。

**平台真值**（不靠反推，取自 `adb shell dumpsys window` 的 `InsetsSourceControl`）：

| inset | 真值 | 含义 |
|---|---|---|
| `statusBars` | `Insets{top=72}` | 顶部安全区 |
| `navigationBars` | `Insets{bottom=72}` | 底部安全区 = `safeBottom`（根容器消费） |

⇒ 根容器内容区底边 = 屏幕底(2159) − 72 = **y 2087**。

**方法（染色法）**：占位块是**零内容、视觉不可见**的，直接截图量不出它的边界 ⇒ 临时给
`FabAllowanceSpacer` 的 `<view>` 加 `background:#ff0000` 重新构建装机，按红色像素包围盒定位，
量完**逐字节还原**（`diff` 已确认还原，APK 已重装还原版）。
选择染色而非「量末项位置」的原因：末项底边依赖页面滚动状态与既有留白，不稳定；占位块是**确定的几何体**。

**结果**：

| 量 | 实测 | 理论 | 偏差 |
|---|---|---|---|
| **占位块高度**（红块包围盒） | **207px** | `19.2vw` = 207.36px | **−0.36px（−0.17%）** ✅ |
| 占位块横向覆盖 | x = 0 … 1076（通栏） | `w-full` | ✅ |
| 占位块底边 → 屏幕底 | 72px | `FAB_EDGE_VW`(46.1) + `safeBottom`(72) = 118.1px | 72px ⚠️ 见下 |
| FAB 高度 | 162px | `14.933vw` = 161.3px | +0.7px ✅ |
| 存量 8vw 观感留白（末项底边 → 占位块顶边） | 132px | 8vw = 86.4px | **+45.6px** ⚠️ 见下 |

**结论**：**本 ADR 引入的让位几何精确命中理论值（−0.17%）**，验收通过。

**⚠️ 两处如实登记的偏差（均不属本 ADR 范围，未整改）**：

1. **占位块底边 → 屏幕底 = 72px，而非 118.1px**。差额恰等于 `safeBottom`。
   即占位块的底边**正落在根容器内容区底边**上 —— 这是**正确**的：
   `safeBottom` 已由 `App.vue` 的 `paddingBottom` 在根容器消费，占位块只需填满内容区，
   不应也不需再叠一次系统栏高度（那才是术语表 §三·1 禁止的「重复消费」）。
   **本条按「正确但反直觉」记录**，不是缺陷；初量时它曾让我误判为偏差。
2. **存量 8vw 观感留白实测 132px（理论 86.4px，+45.6px）**。该留白是 `Me.vue` 里既有的
   `h-[8vw]`（本 ADR **未增未减**）。实测偏大说明既有留白并非恰好 8vw，
   但它**不影响**让位结论：让位块自身高度已精确命中（上一行）。

**未覆盖**：插画 / 小说两页**未做**同法量测。两页的**结构**正确性由 T0 spike（末尾追加安全）
+ 门禁 16 条覆盖，但**数值**未取证。

⚠️ **[2026-10-03 已尝试并确认：染色法在 `<list>` 无限流页上不可行]** —— 这不是「尚未验证的推测」，
是动手试过后的结论。染色构建 + 真机实测记录：

| 尝试 | 结果 |
|---|---|
| 插画页连续 fling 20+ 次 | 列表**持续分页追加**，末项始终不到达，染色块不在屏内 |
| 小说页连续 fling 14 次 | 同上 |
| 断网让分页停止 | ⚠️ **不可行**：401 清掉登录态、跳回登录页，反而丢失了被测环境 |

⇒ **根因不是 `<list>` 的渲染差异，而是「无限流列表没有可达的末尾」** ——
染色法需要「滚到底」这个前提，而推荐流永远滚不到底（这与 ADR-0162 的 list 结构约束无关）。

| 分页 FAB 与 `GlobalFab`「逐字同构」 | **不同构**。`GlobalFab` 在这些页上是 search 模式，比分页 FAB 高出 **39.467vw** |
| `TagNeighbors` 复用 `RefreshableList` 自带 FAB | 该页**根本不用** `RefreshableList`（裸 `<list>`），无分页 FAB |
| 让位 19.2vw 足够 | **不足 39.467vw**。真机实测（收藏页滚到底，emulator-5554 / 1080×2160）：搜索 FAB 底边 **43.796vw**、顶边 **58.611vw**、尺寸 14.907vw（与理论偏差 <0.15%），**压在末张卡片 `y≈1318..1739` 上**（FAB `y[1383..1543]` `x[872..1033]`）⇒ 点末项右侧开的是搜索弹层 |

⇒ **§5.3 的抽验结论（207px / −0.17%）只证明了「占位块被正确渲染成 19.2vw」，
不证明「19.2vw 够用」。** 让位够不够用，取决于该页**真实遮挡源的顶边**，
而这正是 19.2vw 漏掉的量。

✅ **该缺陷已于 2026-10-03 修复**（票 #922）：让位改为按 FAB 路由档位分两档
（`menu` 19.2vw / `search` 58.668vw），档位由 `globalFab.view.routeMode` 自动推导，
search 抬高推导迁入 `utils/fabGeometry` 单一来源，并补接线 4 个从未接线的页面。
修复后真机复验（收藏页）：末项底边 **634px = 58.704vw** vs 理论 633.6px，**偏差 +0.06%**，
与搜索 FAB 顶边间隙 1px、**零重叠**（修复前重叠 356px）。完整决策与门禁见
[ADR-0217 修订节](../adr/ADR-0217-bottom-occlusion-allowance-scoped-to-scroll-content.md)。

**门禁**：`LIST_PAGES` 已扩到 **13 个 `<list>` 页**（三根页 2 + #921 九页 + #922 补接线 2）；
断言数经四轮扩到 **90 条**（接线形态）** + 6 条**（几何 oracle，另立 `tests/fabGeometry.test.ts`）。
⚠️ 清单完备性不靠这份数组，而靠**从 `router.ts` 反查**的判据（新增页面漏接线会转红并点名）。
占位移到 footer 之前 ⇒ 转红；占位加 `v-if` ⇒ 转红。

⚠️ **实现期踩到的一个真回归**（已修）：9 页的占位说明最初写在**模板区**的中文注释里，
被 `TagNeighbors.template.test.ts` 的「模板区零中文」门禁判红 ——
该判据只剥标签、**不剥 `<!-- -->` 注释**，所以模板注释里的中文会被当成硬编码文案。
⇒ 说明文字已统一迁到 `<script>` 区（组件头注是那里允许中文注释的地方）。

### 5.2 FAB 展开态的末项可点性（2026-10-03 真机实测）

**问题**：19.2vw 让位按「FAB **收起态**几何」取值（`FAB_EDGE_VW + FAB_SIZE_VW`）。
展开态环项的半径更大（R_OUTER ≈ 376px vs FAB 本体 161px），**是否会压住末项**？

**先算后测**：按外环四项实测角度（推荐 -9.7° / 插画 -38.2° / 小说 -67.1° / 我的 -89.7°，
半径 376px，环项圆直径 161px）推算，「插画」环项的垂直覆盖 y=[1576,1736] 与
Me 页真正末项（WebDAV「恢复」按钮，y=[1658,1748]）**重叠**。

**真机实测**（emulator-5554，Me 页滚到底 → 展开 FAB → 点末项）：

| 观察 | 结果 |
|---|---|
| 视觉 | 环项**确实**压在末项区域上（「插画」环项正盖住「恢复」按钮）—— 推算正确 |
| 交互 | 点末项 `(350, 1629)`（已避开环项圆心）⇒ **0 响应**，菜单保持展开 |
| 归因 | **不是**让位高度不够，而是 **scrim 全屏遮罩吞掉了点击** |

**结论：这是 M3 FAB menu 的标准设计，不是缺陷。**
`GlobalFab` 的遮罩是 `v-if="view.isOpen"` + 显式 vw 全屏 + `@tap="dispatchClose"`
（点空白收起）—— ADR-0123 §26/§34 明写「展开态：遮罩全屏 `@tap` 收起」，
且与 ADR-0111 `RefreshableList` 的 scrim **同语义**。展开时全屏是交互面本就吞点击，
与「末项被让位不足遮挡」是两件事。

⚠️ **推算与实测的关系**：本例推算**正确**（环项确实压住末项），
但**结论**要靠交互实测才成立 —— 若只做几何推算就下「这是 bug」的结论，
会误报一个不存在的问题（正是本轮反复出现的教训）。视觉重叠 ≠ 交互缺陷。

⇒ 保持现状：让位按收起态取值（19.2vw），不为展开态加大。
理由：展开态本就有全屏 scrim 阻断交互，末项可点性在收起态才是有效场景；
且加大让位会让**收起态**底部出现多余空隙。

## 6. 不做（明确排除）

  `Notifications` / `Ranking` / `TagNeighbors` / `UserHome` / `Watchlist`）：
  票 **#921** 接入接线、票 **#922** 修复几何（search 档 58.668vw），**两票均已落地**。
  ⚠️ 当时「几何完全同构、可平移复用同一占位」的理由**是错的**，已在 §5.3 与 ADR-0217 修订节订正。
  ⚠️ **覆盖缺口自下述状态更新起为 9 页**；此前 spec / ADR / `App.vue` 曾把这 9 页记作
  「已挂账 #920」，**该表述不成立**（#920 不含此项），已订正。
