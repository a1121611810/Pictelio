# ADR-0158: 排行榜不新增导航分类——feed 内融合入口 + 独立榜单页（两端形态不同）

- 状态：accepted
- 日期：2026-09
- 关联：spec `docs/specs/ranking.md`、差距报告 P0-1（排行榜为最后一个 P0）、原型归档 commit `58170a2b` / `6a2b20fc`、ADR-0075（首页 C shell + L5 固定布局）、`docs/specs/related-injection.md`（feed 内注入的先例）、`docs/specs/search-advanced-filters.md`（lynx 无原生日期输入的既有裁剪结论）

## 背景

排行榜是本项目功能差距盘点的最后一个 P0（P0-1）：竞品 7/7 均具备，而两端源码 `grep ranking` 零命中。官方 App API `/v1/illust/ranking`（`mode` + `date`）可复用既有认证、分页与图片流水线。

用户诉求是「不想另外新加一个分类」——即不接受为排行榜新增导航 tab 或首页子 tab。两端推荐流的既有形态差异很大：webview 是 C shell + 单列 Feed，lynx 是推荐页沉浸式单卡轮播 + 独立的插画页双列瀑布流。而排行榜自身的复杂度（7 档维度 + 按日期回看 + 无限滚动）无法塞进「一个分类项」或「一行入口」里。

## 决策

**D1. 不新增任何导航分类**。入口以 feed 内注入形态与推荐流融合：webview 在推荐 Feed 顶部注入横滑条（与相关作品注入行同形态）；lynx 在插画页推荐 tab 顶部注入「榜首编辑大卡」。

**D2. 两端入口形态不统一，这是有意为之**。webview 取**密度**（横滑条一眼扫 20 名，与 webview 的 C shell 列表语言一致）；lynx 取**沉浸**（榜首大卡全幅背景 + 信息叠加，与 lynx 推荐页的轮播卡语言一致）。强行统一会牺牲其中一端既有的设计语言。

**D3. 完整浏览能力收进独立路由 `/ranking`**，两端各自新增该路由。入口只承载「今日日榜」的展示与跳转，**不承担维度/日期状态**：入口标题恒定（「今日排行 Top 20」），不随用户在榜单页里选过的维度/日期变化——否则标题与实际内容会失真。

**D4. 退出口 = 设备级持久开关（默认开）+ 入口内即时收起**。与传统接相关作品注入的既有模式同构；默认开是因为排行榜是用户期待的能力，默认关会让人以为没做。

## 备选与否决理由

- **新增「排行」导航 tab / 推荐页子 tab**：与「不新增分类」的直接诉求冲突；且「维度 × 日期」两维在 tab 行里没有落点。
- **两端统一为横滑条**（或统一为大卡）：牺牲一端的设计语言；lynx 的瀑布流上下文里横滑条还有既有的原生限制（list-item 内横滑容器不可靠，相关作品行已因此降级为网格）。
- **入口内做维度切换并与榜单页联动**：入口标题会失真，且需要把选择状态持久化；维度/日期一律收进榜单页更内聚。
- **只做入口、不做榜单页**：维度切换与日期回看全部缺失，P0-1 只能算部分关闭（竞品 7/7 均具备日期回看）。

## 后果

- **两端入口行为存在差异**（横滑条 vs 大卡），需要在测试与文档中显式固定，避免后续「对齐两端」的误改。
- **既有过滤口径的不一致在榜单页被放大**：webview 的过滤链会把受限条目**滤除**，在榜单页留下**名次空洞**（第 4、5 名消失而第 6 名仍显示为 6）；lynx 则保留条目并盖受限遮罩、名次不变。本 ADR 明确不为榜单页破例（沿用各端现有口径），名次空洞记为**已知行为**而非缺陷。
- **扩展维度（性别偏好 / 漫画 / AI 榜）需要升级 chip 行形态**：一维 chip 行（当前 7 档）再加档位会撑爆窄屏，届时需改为分组 chip 或二级筛选。
- 榜单页的名次只能由 `offset + index + 1` 推得（服务端响应不含名次字段），因此**任何客户端侧的重排都会破坏名次**——数据层必须走单源分页，禁止走会按 `create_date` 重排的 merge 路径。
