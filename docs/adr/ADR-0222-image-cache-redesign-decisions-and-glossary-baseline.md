## 1. 背景

图片缓存此前**没有一套可依赖的「容量 / 淘汰 / 可观测」决策**。本轮重设计的动因是五个互相咬合的缺陷（详见 spec #975）：

1. **容量写死不看设备**：内存层固定 64MB、磁盘层固定 300MB，皆为常量。
2. **磁盘层不是真 LRU**：淘汰按「最后修改时间」排序，而该时间**只在写入时更新**——天天在看的图因「写得早」反而最先被删；淘汰还只在写入后触发，启动时不清理。
3. **两层键空间不一致**：磁盘层以 rewrite 后的官方 CDN URL 为键，内存层以未 rewrite 的原始 URL 为键。
4. **预取只喂磁盘**：首屏首次显示仍要磁盘读 + 解码。
5. **完全不可观测、也无从清理**：没有命中率、没有占用展示、没有手动清理入口。

**本 ADR 只解决其中「词汇与决策」这一层**：把决策与明确拒绝项一次写清，并统一被腐化的编号。代码改动由 #977–#983 分片交付。

### 1.1 两套互不相干的「三层」编号（本 ADR 的直接动因）

| 来源 | 编号方式 | 现状 |
|---|---|---|
| `packages/android-host/CONTEXT.md`「缓存三层」 | 内存 `LruCache` / 内存盘 `ImageMemoryCache` / Java 磁盘 | ❌ **把容器与其使用者各算作一层**——`LruCache` 是 `ImageMemoryCache` 的内部实现，两者是同一层 |
| ADR-0090 标题的「三层」 | A 磁盘 / B 浏览器缓存头 / C JS 预取 | ❌ **层 B 在 Lynx 下已无载体**，随 WebView 客户端整体删除（ADR-0203） |

两套编号指向**不同的层集合**，并存会持续误导后续改动。⇒ 统一为一套。

## 2. 决策

### 2.1 现行编号：**两层缓存**

按**是否需要一次 IO 才能拿到数据**划分，与容器/使用者无关：

| 层 | 载体 | 命中效果 | 当前键 |
|---|---|---|---|
| **内存层** | `ImageMemoryCache`（内部持 `LruCache` 作 LRU 容器；**二者同属这一层**） | 免磁盘读 + 解码 | 官方 CDN URL（`cacheKey` 产物，#980 已统一） |
| **磁盘层** | `PixivImageLoader` 的 `getCacheDir()` 文件 | 免网络 | 官方 CDN URL（rewrite 产物） |

**ADR-0090 的「三层」是历史编号**（磁盘 / 浏览器缓存头 / JS 预取），其中**浏览器缓存头层已随 ADR-0203 整体删除**，在 Lynx 下无载体。引用 ADR-0090 时须按本节重新对号入座，**不得**当作现行层数。

_Why 两层而非三层_：ADR-0090 的层 B（WebView HTTP 磁盘缓存）属**引擎能力**而非本仓自管缓存；Lynx 不暴露它，本仓也无从配置或观测它。把它计入层数，等于让一个不存在的载体长期占据架构讨论。

### 2.2 单一策略决策点

引入**集中的缓存策略对象**作为「内存预算、磁盘预算、内存压力响应、统计口径」的**唯一决策点**；内存层与磁盘层只消费它，不再各自持有常量。该对象必须是**纯计算、可注入**的（不直接依赖 `Context`），使容量预算算法能被纯 JVM 单测直接验证。

### 2.3 内存预算的外部一手出处

**做法**：内存预算 = 屏数法（按屏幕尺寸 × 屏数估算目标值）**与** 进程可用内存比例封顶**取小**；低端机（`isLowRamDevice()`）用更保守的系数。

**一手出处：Glide `MemorySizeCalculator`（bumptech/glide，`library/src/main/java/com/bumptech/glide/load/engine/cache/MemorySizeCalculator.java`）**，已逐行核对源码：

| 量 | Glide 真实取值 |
|---|---|
| 封顶系数 | `MAX_SIZE_MULTIPLIER = 0.4f` |
| 低端机封顶系数 | `LOW_MEMORY_MAX_SIZE_MULTIPLIER = 0.33f` |
| 内存缓存屏数 | `MEMORY_CACHE_TARGET_SCREENS = 2` |
| bitmap pool 屏数 | `BITMAP_POOL_TARGET_SCREENS = 4`（Android O 以下）/ `1`（O 及以上） |
| 竞争余量 | `ARRAY_POOL_SIZE_BYTES = 4MB`，低端机减半 |
| 超限收缩 | 目标值之和超 `availableSize` 时，按比例缩减两池（`part = availableSize / (两池屏数之和)`） |

⚠️ **必须同时记明的反证**：网络上流传的「**Glide 默认 1/8**」**并非 Glide 的事实**——`MemorySizeCalculator` 源码中不存在该系数（已核对）。1/8 是 **Android 官方《Caching Bitmaps》指南的示例值**，属另一出处、另一语境，**不得据以实现**。
（取证说明：本轮该官方指南页已下线、返回 404，Wayback 亦无快照，故此处只登记「1/8 出自官方指南示例」这一**归属**，不作现时引用；Glide 侧系数为本轮逐行核对源码所得。）

### 2.4 磁盘淘汰改按访问时间

**做法**：磁盘条目在**命中时刷新其访问时间戳**，使淘汰顺序反映「最近被用过」而非「最近被写下」；淘汰触发点从「仅写入后」扩展为「**启动时 + 写入后**」。

**一手出处：Fresco 磁盘缓存实现（facebook/fresco，`imagepipeline-base/src/main/java/com/facebook/cache/disk/DefaultDiskStorage.kt`）**，已逐行核对源码：

- 读取路径调用 `touch(resourceId, debugInfo)`，其实现为 `query(resourceId, touch = true)`：
  ```kotlin
  private fun query(resourceId: String?, touch: Boolean): Boolean {
    val contentFile = getContentFileFor(resourceId)
    val exists = contentFile.exists()
    if (touch && exists) {
      contentFile.setLastModified(mClock.now())   // ← 命中即刷新时间戳
    }
    return exists
  }
  ```
- 淘汰比较所依据的时间戳取自同源：`EntryImpl.getTimestamp()` 返回 `cachedFile.lastModified()`。

⇒ 「命中刷新访问时间戳」是**成熟实现既有做法**，不是臆想。写盘路径另有 `commit()` 显式 `setLastModified(time)`。

### 2.5 保留的两条键不变量

1. **缓存键恒官方 CDN URL**（ADR-0143 §D2）
2. **预取 / 显示拦截 / zip 三链路共用同一键空间**

✅ **这两条现覆盖内存层与磁盘层两层**（#980 已交付）——两层键均由
`PixivImageLoader.cacheKey(url)` 唯一产出（= `rewriteUrl` 产物 = 官方 CDN URL），
磁盘层与内存层不可能再算出不同的键。此前内存层以未 rewrite 的原始 `url` 为键，
同一张图的两种形态会「磁盘一条目、内存两条目」。防线：`ImageCacheKeySpaceTest`
断言内存层键恒等于 rewrite 产物、且不以原始 url 为键。

> ✅ **「唯一产出」现已覆盖全部五条链路**（#987 已交付，2026-10-11）：预取 / 显示 / zip 导出 /
> 保存到相册 / 下载器。此前只覆盖预取与显示两条——zip / 导出 / 保存三条链路的 7 处调用点
> 绕过 `cacheKey`，只因传入的恰好是官方 URL 而**巧合正确**。修法不是逐个改调用点，而是把键的
> 产出**收口到 loader 内部的唯一文件名产出点** `cacheFileName(url) = keyToFilename(cacheKey(url))`
> （读路径 `cachedFile` 与三个 `*CachedFirst` 入口的写路径全部经它）——漏一处需要改 7 处
> 调用点的方案不具备结构性。防线：`ImageCacheZipChainKeyTest` 逐入口断言代理形态与官方形态
> 共用同一条目（详见 §4）。

### 2.6 命名与存量处置

- 磁盘层入口方法名须体现「缓存优先」语义（现名 `loadBytes` 掩盖了该语义）。
- 存量缓存**直接清空、不做迁移**：缓存不是真相源，删后可从网络重建；避免新旧两套策略并存以致无法判断用户在用哪套。

## 3. 明确拒绝项（逐条登记理由，防下个 agent 重提）

### 3.1 不引入第三方图片库（Glide / Coil / Fresco）

替换整条图片链路的收益（省掉自写预算/淘汰/并发）**不抵其代价**：既有加载链路的**产品语义**（画质档位、三态机、lazy-load 分工、图床决策、防盗链注入）均已围绕自管实现成型且有契约测试把守；整体替换会一次性冲掉这些不变量。Fresco 仅作为**做法出处**被采纳（§2.4），不作为依赖引入。

### 3.2 不引入 OkHttp Cache（HTTP 缓存层）

三条理由，任一条独立成立：

1. **前提不成立**：Pixiv CDN 不下发 `Cache-Control` / `ETag`，HTTP 缓存无从生效。
2. **会形成双轨缓存**：与自管磁盘层并存即双轨——而既有决策已把双轨缓存判为**架构劣化**（镜像流量绕开缓存即其反面教材，ADR-0143）。
3. **条件请求层无价值**：Pixiv 图片 URL 不含签名、内容不可变，`ETag` 校验拿不到增量收益。

### 3.3 不做可插拔淘汰策略抽象（LFU / 2Q / TinyLFU / ARC）

**在没有命中率数据之前，策略抽象是拿不到收益的复杂度。** 顺序必须是「**先能观测，再谈策略是否够用**」——没有命中率就无法判断 LRU 是否已经够好，也无法判断换策略是否真的更好。策略抽象留待 #983（可观测统计）交付后再议。

### 3.4 其他不做的事

不改解码采样算法（2048 上限不动、不引入按请求尺寸精细采样）；不引入硬件 Bitmap / bitmap pool；不动多图详情页加载策略；不做缓存加密或访问控制（缓存内容为公开作品图元数据，随 `cacheDir` 生命周期）。

  **仍不是内存峰值实测**——峰值须在真机加载大量图片后读 `dumpsys meminfo`，本轮未做，模拟器数据更不得作为依据。
  票面 AC 亦明文「模拟器数据不得作为验收依据」。
- **#985 的三处刻意边界**（不得读成「已修」，登记于 2026-10-11 Spec 轴 code review）：
  1. **进程级互斥锁 `CACHE_DIR_MUTATION_LOCK` 是修本票自己制造的回归**：升级清空把原本罕见的「删除落在 tmp→目标 rename 中间」放大成一次性全删必然触发，修复本票引入的竞态属票面隐含授权。**不要**当成历史包袱删掉——删回去 `GallerySaver` 系列测试会红。
  2. **冷启动闸门 `startupMaintenanceGate` 是未经票面 AC 授权的行为变更**：它把 `getCacheDir()` 变成缓存读路径上的新全局同步点。**最坏情况：升级后首日若存量缓存较大，首屏图片最多延迟 15 秒**（`STARTUP_MAINTENANCE_WAIT_SECONDS`，超时 fail-open 且 `Log.w`，不卡死启动）。这是「用一种用户可见延迟替换另一种用户可见故障」的**产品侧权衡**，票面未授权，也**没有单测钉住该时延**。跟踪票 [#990](https://github.com/a1121611810/Pictelio/issues/990) **已于 2026-10-11 评估完毕并结案**：实测取证（删除吞吐约 1.76 万文件/秒，现实内容对应 2.2–8.7s，要吃满 15s 需约 26.5 万文件；且闸门每次冷启动都关，而存量清空在标记已存在时是**零工作 no-op** ⇒ 常态代价毫秒级）后，决策为**两项改动都不做**——「改为读盘不阻塞」会把「读者拿到马上被删的文件」这个容错义务转嫁给每个读路径调用方，「清空分批」对峰值时延无改善。**真正残余的风险是共享单线程 `TRIM_EXECUTOR` 的排队**（它被 #981 内存压力收缩复用，而闸门在提交前关闭），**不是清空 I/O**；将来若真见首屏卡顿，应先查执行器排队。机器防线已由 `ImageCacheStartupGateTest` 补齐（此前该调度方法全仓零测试调用）。
  3. **用户手动清理与容量淘汰**对「File 句柄交予调用方、调用方之后才读」的时序暴露面**保持原样未修**（早于 #985 即如此，不属该票范围）；闸门只整体排除了升级清空那一条路径。

| 屏数法（像素×4B×2 屏） | 6.50 MB | 17.20 MB |
| 封顶（memoryClass×0.4） | 19.20 MB | 76.80 MB |
| **实测预算（logcat）** | **6 MB** | **17 MB** |
| 生效项 | 屏数法 | 屏数法 |

两档预算不同（6MB vs 17MB），且两档都由**屏数法**封顶（屏数法项 < memoryClass 封顶项），
与 ADR-0222 §2.3 记载的 Glide `MemorySizeCalculator` 口径一致。
`getDisplayMetrics()` 返回 1184/2088 而非屏高 1280/2160，是 Application 上下文已扣除状态栏与导航栏所致。

**#986 磁盘上限 —— `StatFs` 真机读数非 0，比例生效、未被钳制**

| | `pictelio_low` | `pictelio_ui` |
|---|---|---|
| `StatFs` 可用（logcat 实测） | 5446 MB | 3189 MB |
| × 2% 手算 | 108.92 MB | 63.78 MB |
| **实测上限（logcat）** | **108 MB** | **63 MB** |

两档都落在 10–250 MB 钳制区间**内部**⇒ 走的是比例分支，**未**触碰上下界；
此前 Robolectric 下 `StatFs` 返回 0、只覆盖了「探测失败 → 告警 + 取下界」分支，该分支现已得到实证。

清掉 `purged_generation` 标记模拟「升级那一刻」，重启触发清空：

**#984 产品面 UI（模拟器目视已做，2026-10-11 补记）**：`BENCH_NAV=1` 构建 + `am start --es benchNav advanced`
深链直达 `/advanced`，滚动到图片缓存组实测：四行读数与清理按钮均正常渲染——磁盘占用 2.7 MB、
**缓存条目 48 项**、内存占用 0 B、命中率 3%、清理按钮在原生可用态呈 `bg-primary` 启用外观。
本轮由此**抓出并修掉一个真 bug**：「缓存条目」一行的标签与值共用 `advanced.cache.entries`，
而该 key 文案无 `{{count}}` 占位符 ⇒ 条目数被静默丢弃、值侧一直显示「缓存条目」四个字，
条目数**从未显示过**。类型检查 / lint / zh-en 键清单同步守卫全部放行，只有渲染才暴露
（已修 + 加 `i18nInterpolationGuard.test.ts` 拦这一类）。该 bug 由 #988 走查产出，非 #984 交付时已知。

⚠️ **订正**：上条那个「内存占用 0 B」是**空内存层的真实读数，不是恒为 0 的 bug**——取读数时该进程
尚未加载任何图片；同日第二轮在**先加载 Feed 图片**后复读，分别为 5.6 MB / 17.0 MB（见下节）。
**不得据这条旧记录认为「内存占用恒为 0」或「该行坏了」。**

**#979 内存层「上限守得住」—— 字节级读数（2026-10-11 第二轮补记，#988 走查产出）**

上一轮只验了**预算公式**（logcat 打出 6 MB / 17 MB）。本轮改用**应用自身的字节级读数**
（设置页 →「高级」→ 图片缓存组 →「内存占用」，取自 `ImageMemoryCache.totalBytes()`，
即内存层 LRU 的当前 `currentSize`）复测，得到**两档都不越界、且灌入新图后一动不动**的直接证据：

| | `pictelio_low` | `pictelio_ui` |
|---|---|---|
| logcat 预算 | 6 MB | 17 MB |
| 灌图前内存占用 | **5.6 MB** | **17.0 MB** |
| 灌图后内存占用 | **5.6 MB** | **17.0 MB** |
| 同区间磁盘条目 | 68 → **121**（+53） | 40 → **111**（+71） |
| 同区间磁盘占用 | 8.5 → **15.2 MB** | 5.9 → **10.5 MB** |

两档的磁盘层随新图**线性增长**，内存层**逐字节不变**（`pictelio_low` 低于预算 0.4 MB、
`pictelio_ui` 正好贴住预算线）⇒ **LRU 收缩按预算生效，内存层对新增图片零增长**。
这比上一轮用 `dumpsys meminfo` 进程 PSS 作推断强得多：PSS 是进程级、不隔离图片缓存，
而本读数**直接就是内存层自己的字节数**。

**但仍不得据此宣称 #979 已验收**：该票 AC 原文要求「真机验收……模拟器数据不得作为验收依据」。
本节证明的是**机制成立**（预算被遵守且不随负载增长），不是**真机内存峰值实测**。
另有一处已知的读数陷阱：悬浮 FAB 会遮住「内存占用」行的值，需微调滚动位置才能读全。

**仍未做（不得宣称）**：#979 的**内存峰值实测**
（本节只验证了内存层自身不越界，**仍未做**峰值实测：峰值须在真机加载大量图片后读
`dumpsys meminfo`，模拟器读数不得作为依据）；**#984 的 web-core 降级目视验收不可行**——
`/advanced` 带 `requiresAuth: true`，而 web-core 不解析令牌且路由用 memory history（无 URL 深链），
故该环境**根本到不了该页**（已在 `lynx.config.ts` 中作为既有事实记载）。

**已订正（2026-10-11）**：上文曾把「#982 解码失败分支」也列为未做、需构造损坏图片走真机——
**该前提是错的**。那条「Robolectric 解码过于宽松、分支不可观测」的结论是在**默认（LEGACY）图形模式**
下得出的；切到 `@GraphicsMode(NATIVE)`（真实原生解码）后实测，非图片字节的 bounds 为 `outWidth=-1`、
`decodeByteArray` 返回 `null`，分支在 JVM 单测里可观测。该分支现由
`PictelioImageServiceDecodeFailureTest` 钉住降级契约三条（告警可见 / 内存层不填 / **磁盘层保留**——
降级不等于丢下载），并经变异验证确认有检出能力。
另有一处已知但未处理的观察：页面右侧的搜索 FAB 会浮在读数行上方，滚动位置不当时遮挡
「缓存条目 / 内存占用」的值（不影响数据正确性，属既有布局行为）。

## 5. 后果

- 领域词汇层新增「两层缓存 / 内存层 / 磁盘层」，并把 ADR-0090 标注为**历史编号**；两套「三层」编号合并为一套。
- 「缓存键恒官方 CDN URL」「三链路共用同一键空间」两条不变量保留并**覆盖两层**（#980 已交付）：键由 `PixivImageLoader.cacheKey()` 唯一产出。此前标注的「内存层当前未满足」已不成立，勿再据此词条认为内存层仍分叉。
  ✅ **「唯一产出」现已覆盖全部五条链路**（#987 已交付）——预取 / 显示 / zip 导出 / 保存到相册 / 下载器，见 §4。
- 内存预算系数与「命中刷新时间戳」两项做法各自带**外部一手出处**，后续实现票可直接沿用，**不必重新论证**，也不得凭感觉改系数。
- 三条拒绝项各有独立理由，**重开任一条须新开 ADR 推翻本节**。
