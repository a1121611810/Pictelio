## 1. 问题

「用户想知道关注的作者/追更的系列有没有更新，不必打开 App。」今天必须主动打开 App 去「更新」页看。

但**这件事的形态从未被单独决策过**：它同时以两个身份存在——

| 出现处 | 怎么写的 | 缺什么 |
| --- | --- | --- |
| `docs/specs/notification-center.md`（ADR-0188） | 「系统推送挂账 **Phase 2**：WorkManager 周期**后台**检查 + Android 系统通知」 | 无票、无形态决策 |
| `docs/specs/app-lynx-navigation-dimension-restructure.md` §4 | 「**P2 · 送达通道**：`POST_NOTIFICATIONS` + Lynx 原生模块 + **本地周期拉取**」 | 未指向 ADR-0188；未提「后台/前台」；依据是 LINE WEBTOON |

两处依据不同、措辞不同、**都没有立项**。ADR-0188 明确要求先过一遍 Grill——本 ADR 补上。

## 2. 决策

**这次不交付「通知功能」，只跑一次「触达探测」（delivery probe）。**

验收 = **拿到一个可判定的数据点**（「用户想不想要这个回执」），**不是**「通知能用」。

理由：spec 原文给 P2 定的真正作用就是「**验证"用户想不想要这个回执"**——若打开率很低，说明回执本身价值有限，
也就不必回头考虑服务端方案」。一个**验证需求**的装置，若按功能来验收，验收条件会自然滑向「通知能用」，
而「能用」证明不了「想要」——那 P2 就退化成一个普通功能，成本（原生模块 + 权限 + 周期调度）远高于收益。

### 逐项决策（Grill 3 轮）

| # | 决策 | 要点 |
| --- | --- | --- |
| D1 | **当实验做** | 验收是数据点，不是功能可用性 |
| D2 | **补生命周期事件，只在「进入前台 + 静默 N 秒」后轮询** | 见 §3 形态取舍 |
| D3 | **查权限状态 + 降级到角标，不做二次弹窗** | 二次弹窗是本仓反复吃亏的模式（#908 那类「用户看到的东西 ≠ 实际能力」） |
| D4 | **只量「点击样本 ÷ 发出样本」，本机可读、不上传** | 跨设备汇总要上传行为数据，与决策 5（只存本地）直接冲突。**破例该单独决策，不该藏在 P2 里顺手做** |
| D5 | **汇总一条通知**（非逐条） | 汇总形态的点击率是逐条的**上界**；先用上界测，低于阈值则整条路线可砍 |
| D6 | **点击落到「通知」页** | 入口与承诺一致：通知里说的是通知，点进去还该是通知列表 |
| D7 | **阈值用相对值**（对比「主动打开 App 的频率」） | 绝对阈值（如 30%）是拍的，不同通知形态的自然点击率差一个量级。比值**自校准**，回答的正是想问的问题 |
| D8 | **固定周期 + 阈值预登记，到点就判** | 事后定阈值等于没阈值。本仓有先例：卡氏排序「前置被豁免、验证从未运行」 |
| D9 | **只支持冷启动点击**（不做热启动） | 冷启动可复用 `singleTask` + `getIntent()`；热启动需补 `onNewIntent` override |
| D10 | **只拿定性信号，不设统计阈值** | 见 §3 样本量 |
| D11 | **发通知不推进「本地已读记忆」** | 否则用户没点通知也被标已读，**角标与未读数随即失真** |
| D12 | **计数存 JSON，字段级重置** | `{ sent, clicked, startedAt }`：重置只清 `sent`/`clicked`，`startedAt` 跨轮保留 |

## 3. 三处形态取舍（与直觉相反，故展开）

### 3.1 「前台」在 Lynx 侧不可精确观测 ⇒ 必须补生命周期事件

`api/queryClient.ts` 已显式设 `refetchOnWindowFocus: false`，注释写明「**lynx 无 window focus 事件**」。
`LynxView` 虽有 `onEnterForeground` 转发，但 `LynxActivity` 只发了三个 JS 事件（insets / darkMode / back），
**没有前景切换事件**。

⇒ 最初设想的「前台定时」实际只能是「**进程存活期间**定时」——用户正盯着 App 时也弹通知，
而这恰是「用户已经看得见更新、通知是多余的」那个场景。**该形态测不到 D7 要的东西**：
在 App 里点通知进来，不构成「本来不会打开 App 却打开了」的增量。

⇒ 决定补一个生命周期事件（照抄 insets / darkMode 的既有机制，不是新范式）。**成本换可测性。**

### 3.2 单用户探测**没有统计效力**（D10 的由来）

把 D2 代进去推一遍：用户一天开 App 约 5 次，其中约 3 次进 App 后几十秒内就滚到「更新」页看了
⇒ 被静默期滤掉、不发通知；剩约 2 次可能发。⇒ **一周约 14 个发出样本**。

14 个样本量不出「打开率 20% 还是 40%」。**这不是多跑几周能解决的**——单用户实验的样本上限
就是用户的打开频率。

⇒ 决定：只取**定性**信号（我点过 / 我没点过），**不设统计阈值**。结论**能提示「可能无用」，
不能证明「有用」**。若结论是「没人点」⇒ 支撑「不必做服务端推送」；若是「有人点」⇒ **不可推广**。

⚠️ 另一条路（多设备分层采样）需要上传行为数据，与决策 5 冲突，不在本文范围。

### 3.3 与 ADR-0188 Phase 2 措辞的偏差

ADR-0188 写的是「WorkManager 周期**后台**检查」。本文 D2 定的是「**前台**生命周期 + 静默期」。

**为什么偏离**：后台周期（WorkManager）在 Doze 下可能数小时不跑 ⇒ 发出样本的时间分布失真，
而 D7 的阈值是**比值**，分母失真会直接毁掉判读。且后台调度需要常驻/前台服务权限，成本高一档。
**代价**：本次探测**只覆盖「用户主动回到 App 且没有立刻去看更新」的时刻**，
不覆盖「App 长时间没开、用户从通知栏被叫回来」的场景——**后者恰恰是服务端推送的主场**。
⇒ 若本轮结论是「没人点」，**不能**据此否决服务端推送。已在 §5 登记为失效面。

## 4. 代价与已知失效面

| 项 | 说明 |
| --- | --- |
| **样本量不足** | 见 §3.2。结论是定性的 |
| **覆盖场景偏窄** | 见 §3.3。不覆盖「App 久未打开」的主场 |
| **失去淡入** | 无关本 ADR（那是 ADR-0211 D1 的代价） |
| **权限被拒即无数据** | 降级到角标后 `sent` 恒 0，探测**静默失效**。须在结论里写明「是否真的拿到了权限」 |
| **汇总形态掩盖单条价值** | 回答不了「用户想为每条更新单独被打扰吗」。若要那个答案须逐条，且实验周期显著拉长 |
| **热启动点击会落空** | D9 选了只支持冷启动。若用户在 App 存活时点通知 → `onNewIntent` 未 override，extra 静默丢弃 → **点了像没点**。须在实现时确保该情形不产生通知（见 §6 待办） |

## 5. 与决策 5（只存本地）的关系

D4 明确：**不上传任何行为数据**。计数落在设备本地 `PictelioPrefs`（`SharedPreferences("CapacitorStorage")`
的 String KV），由 `PictelioPrefsModule` 承载——**无需新建存储模块**。

⚠️ `PictelioPrefsModule` 回传字符串带 JSON 引号，JS 侧须 `unquoteNativeString`；
`notificationStore.nativeKv` 已有此处理，先例可循。

若将来要做跨设备汇总，**那是独立决策 + 独立 ADR**，且必须先解决与决策 5 的冲突。

## 6. 待办（不阻塞本文，但实施期必须处理）

1. **对齐两份 spec**：`docs/specs/notification-center.md` 与
   `docs/specs/app-lynx-navigation-dimension-restructure.md` §4 的「Phase 2 / P2」
   应互相引用并标注「形态决策见 ADR-0220」，避免第三次各写一遍。
2. **命名陷阱**：`pages/Updates.vue` 内有一个**本地** `const unreadCount = ref(0)`
   （第三段的小胶囊角标），与 `stores/notificationStore.ts` 的 `unreadCount`
   **不是同一个东西**。降级路径要接的是**后者**（外环角标 + Me 圆点）。极易接错。
3. **热启动的空点**：D9 只支持冷启动，但「进程存活时点通知」这条路径会产生「点了没反应」。
   要么在该情形不发通知，要么补 `onNewIntent`。
4. **权限状态须入结论**：探测报告必须写明 `POST_NOTIFICATIONS` 是否真的拿到了，
   否则「没数据」和「没人点」无法区分。

## 7. 复盘

Grill 过程中有一处**推荐被自己的取证推翻**：初版推荐「前台定时」，随后子代理查明 Lynx 侧
**没有窗口 focus 事件**，「前台」只能近似为「进程存活」⇒ 推荐改为「补生命周期事件」。
另有一处**术语重复**：初判「P2 是个全新功能缺口」，随后在既有术语表里查到
`glossary-notification-center.md` 早已有「系统推送 = Phase 2」词条 ⇒ 结论改为
「P2 即 ADR-0188 的 Phase 2，本文是对其要求的『独立立项 + 独立 Grill』的落地」。

⚠️ 两处的教训同源：**先查既有文档再下新结论**。前者是缺了「前台不可观测」这个环境事实，
后者是缺了「术语表已预留该词条」这个仓库事实。
