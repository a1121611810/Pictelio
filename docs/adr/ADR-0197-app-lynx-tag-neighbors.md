# ADR-0197：app-lynx 标签近邻（Tag neighbors）——标签组合降维检索

- 状态：Accepted（已采纳）
- 日期：2026-09-27
- 取代：ADR-0196（站外溯源）—— 该方向的**技术调研结论仍然有效**（Pixiv 图床防盗链的一手事实、竞品实现机制），但产品决策已改为「标签近邻」，故 0196 标记 Superseded
- 关联：issue #606（Lynx 单引擎化地图）、`packages/app-lynx/CONTEXT.md`「标签近邻」「站外溯源」词条、`packages/app/CONTEXT.md`「搜索关键词」词条（含本次实测的两个硬约束）、`@pictelio/search-core`（共享搜索核心，`search_target` 参数真值 oracle）、`relatedInjectionStore`（官方 related 注入，本功能的分工对象）、ADR-0086/0189 无关

## 背景

本项目此前没有「以图搜图」类能力（全仓零命中），是竞品对比中被识别为**成本最低、差异感最强**的空白项之一（`docs/research/competitor-comparison-2026-09.md`：Shaft / P站助手 / pixez-flutter 均有；后经一手核实，**后两者其实没有**，见 §调研结论 3）。

初始方向是**站外溯源**（把图交给外部反向搜图服务查更早出处）。该方向的完整技术调研见 ADR-0196，其中产出了大量有效的一手事实（防盗链、竞品实现、`i.pixiv.re` 中转等），但**产品决策在调研后改变**。

### 为什么改方向

站外溯源撞上一条硬约束：**Pixiv 图床 `i.pixg.net` 强制 Referer**（无 pixiv 域 Referer 恒 403，换 UA 无效，六域名一致），因此**不能让引擎自行代拉 URL**，必须由 App 先带 Referer 下载再上传。而上传路径又依次撞上：

- Cloudflare 质询（概率性，实测 1.25MB 上传可通过，但 1.8MB 曾致质询）
- 与 #607「WebView/Capacitor 线下线、单 Lynx 引擎」方向**架构冲突**（竞品 Shaft 的最终形态依赖 WebView 跑质询 JS）
- 逐引擎差异（SauceNAO 需 `api_key` 才有稳定路径；Ascii2D 被 CF managed challenge 挡；TinEye 是 SPA 只能走浏览器）

**换方向后，这些问题整体消失** —— 标签近邻**根本不碰图片**，只传标签词去调已验证的搜索 API，防盗链、Cloudflare、原生通道、字节跨桥全部不涉及。

## 调研结论

1. **`tags` 数组按关联度降序返回**（实测，2026-09-27 取真实作品 `147445188`）：`[0] GenshinImpact ← [1] 原神 ← [2] HoYoverse ← [3] シトラリ ← [4] 嫉妬 ← [5] シトラリン`，首项为作品核心（角色名），末项关联度最低（同一角色的非敬语写法）。→ **「从尾部开始收标签」= 收关联度最低的，规则成立。**
2. **`translated_name` 大量为 `None`**（同一实测样本 6 个标签全部 `None`）→ 检索必须用 `tag.name`（原名）。与既有实现一致（`IllustTags.tsx` / `IllustDetail.vue` 点标签跳搜索均传 `tag.name`）。
3. **官方已有黑盒关联**：`/v2/illust/related`（`loadRelated`），已在 feed 中作「相关作品注入」使用（`relatedInjectionStore`）。**标签近邻不是它的替代品，而是它的可解释补充**——官方没说清「为什么这两张相关」，本功能能说清「它有 4/5 个共同标签」。
4. **`/v1/user/illusts` 每条 item 自带完整 `tags`**（2026-09-27 实测，作者 `120290822`：30/30 条全带，**零额外请求**）。→ **「先扫作者作品集、再在本地算相似度」在成本上完全可行**：一个作者 300 张作品 = 10 次分页请求，而非 300 次逐图详情。这一条使「作者优先」成为可选项而非奢侈项。
5. **站外溯源的能力边界（不可被本功能覆盖）**：站外的图没有 Pixiv 标签，故标签近邻**到不了站外**。它能找到的是「Pixiv 站内标签相近的其它作品」，**不是**「这张图最早发布在哪」。二者是不同的能力，术语上必须分开（见 `CONTEXT.md` 两个词条）。

## 决策

**D1 功能命名与边界——叫「标签近邻」，不叫「溯源」。**
用该作品的标签组合逐级放宽地搜 Pixiv 站内**其它作品**。排除：站外溯源（能力不同，见调研结论 4）、「相册选图搜」（输入源不同）、「角色识别 / 图生 tags」（本质是图像识别）。写入 `packages/app-lynx/CONTEXT.md` 词条（含 `_Avoid_` 排除项）。

**D2 候选池优先级——两阶段：作者作品集优先，全站标签检索兜底。**

**阶段 1（作者优先）**：取当前作品的 `user.id`，经 `/v1/user/illusts` 拉该作者**最近 ≤300 张插画**（≈10 次分页请求），逐张在**本地**算与当前作品的标签相似度，按相似度降序取前 20。
**阶段 2（全站兜底）**：**仅当阶段 1 产出 < 5 条时**触发——用当前作品的标签做全站降维检索，逐层放宽直至结果补足。

**为什么阶段 1 不也逐层放宽**：**API 成本在「拉列表」，不在「算相似度」**。分页拉 300 张的成本已经付了，本地算 Jaccard 零成本，故阶段 1 一次扫完候选集；而阶段 2 的每一次放宽都是一次新的网络请求，必须省着用。这个不对称是混合方案的全部价值来源。

**D3 阶段 2 的降维规则——逐层放宽，每层一个组合。**
设标签按关联度降序为 `t₁…tₙ`（`tags` 原序，**不重排**）。第 k 层用前 k 个检索，即每层收掉尾部关联度最低的一个。**不做全子集枚举**（n=5 达 31 次请求，n=10 达 1023 次）。

**D4 相似度口径——Jaccard = |共同标签| / |标签并集|，以「共同标签数 / 总标签数」双值显示。**
_Jaccard 而非「共同标签数」_：单纯数共同标签会偏爱标签少的小集合；Jaccard 对集合规模不敏感，是标签集相似度的标准口径。
**取舍（已接受）**：用 `tag.name` 原名做集合运算——日英标签分属不同命名空间，混算会漏配（这与 D12「不掺画师名」同源）。

**D5 相似度门槛与条数。**
阶段 1 取 **Jaccard ≥ 30%** 的条目（低于此视为噪音），上限 **20 条**；阶段 2 沿用 ADR-0196 撤下的「阈值 5 条即停」口径（见 D6）。

**D6 阶段 2 的终止条件——某层结果数达 5 即停。**
逐层放宽，**一旦某层检索结果数 ≥ 5，立即停止放宽**并定格该层。优先呈现最严的匹配。
_理由_：把「够不够」作为唯一放宽驱动，避免对过宽组合的无谓请求。

> ⚠️ **本条经实施前实测更正（2026-09-27）**：初稿要求「统计口径必须用服务端 `total`，不是本页条数」——**该字段不存在**，该要求无法实现。正确判据见 §更正记录 1，以更正记录为准。

**D7 跨阶段去重与排除。**
两阶段结果并入同一列表，**跨阶段去重**；**一律排除当前作品自身**。

**D8 标签数不足时跳过阶段 1。**
若当前作品标签数 < 2，阶段 1 的 Jaccard 几乎必然全低分（并集≈任一方，规模主导分值），无区分度 → **直接跳过阶段 1，只走阶段 2**，并在 UI 上说明原因，不做静默降级。

**D9 结果列表形态——统一按 Jaccard 降序，同分按时间新→旧。**
跨阶段混排（阶段 1 的条目与阶段 2 的条目按实际相似度统一排序），每条**标注来源**（同作者 / 全站）——这是本功能可解释性的落点：用户能看见「94% · 4/5 共同标签 · 同作者」这样的归因。

**D10 标签一律用 `tag.name` 检索，禁用 `translated_name`。**
依据调研结论 2。（本条同时是 D4 相似度运算的输入约定）

**D11 空格失配面——跟随 Pixiv 官方行为，不自创语法。**
Pixiv 搜索中**空格是 AND 分隔符**。故若 `tags[i].name` 自身含空格，按空格拼接会把它拆成两个标签 → 失配。实测 `"川崎 Sera"` **加引号亦无效**（0 条）。
_取舍（已接受）_：**不自创引号语法**去"修复"它——Pixiv 官方 App 遇到同样输入结果相同，跟随即正确；自创语法反而制造与官方不一致的诡异行为。此项作为**已知限制**在 spec 中显式记录，不静默处理。

**D12 不掺画师名。**
`/v1/search/illust` 的 `word` **只认标签**：实测 `原神 <画师名>` = 0 条（画师名被当标签筛），纯画师名亦 0 条；画师名须走独立端点 `/v1/search/user`。
_取舍（已接受）_：不实现「标签 + 画师」的混合维度——它**在 Pixiv 侧不成立**，不是我们能补的。「看某画师的其他作品」已有现成通路（`/v2/illust/related` 或用户主页作品列表）。

**D13 复用既有搜索核心，不新建检索实现。**
经 `@pictelio/search-core` 的 `buildIllustSearchRequest` 走既有参数构建（`search_target` 规则为照 iOS 官方 8.6.5–8.7.3 抓包定的真值 oracle），**不新造一套参数拼装**。

**D14 入口与作用对象——详情页动作行，作用于作品级。**
入口为作品详情页动作行新增一项（与「↓ 保存」「💬 评论」并排）。多图作品取**首页图**对应的作品级标签（标签是作品级的，与页数无关——本功能不涉及「当前页」概念，详情页是通栏连续列表）。
_取舍（已接受）_：**不引入长按某页的入口**（原「站外溯源」的 B 入口随之取消；手势透传的可行性调研见 ADR-0196 §调研结论 3，将来若要再加）。

**D15 引擎选择与第三方引擎整体退出本功能。**
不做引擎子开关、不做可达性探测、不做设置页讲解页、不做原生上传通道 —— 这些均为站外溯源的配套（ADR-0196 D2/D3/D5/D8/D10），随方向变更一并作废。

**D16 R18/R18G 门控照旧。**
检索结果须过既有 `R18/R18G` 三态过滤（`filterFeedIllusts` / `isRestricted`），**不做静默过滤**；受限条目按既有语义呈现。

## 备选与否决理由（汇总）

| 备选 | 否决理由 |
| --- | --- |
| 继续做站外溯源（ADR-0196 方向） | 撞防盗链硬约束 → 需上传通道 → 撞 Cloudflare 质询 → 与 #607 单引擎化架构冲突；三重复杂度换一个能力边界不同的功能 |
| 每层全子集枚举 | n=5 达 31 次请求，n=10 达 1023 次；API 压力与时延不可接受（D2） |
| 一次性搜完所有层 | 违反 D3 的「够 5 条即停」，对过宽组合做无谓请求；且用户看不到放宽过程，丢失可解释性 |
| 阈值用「累计总数」而非「本层结果数」 | 累计会掩盖「本层过宽」；用户口语明确是「4 个标签只搜出两张」（指本层），故按本层计（D3） |
| 掺画师名做混合检索 | Pixiv 侧不成立：`/v1/search/illust` 的 `word` 只认标签，实测混合必 0 条（D7） |
| 为含空格标签自创引号语法 | Pixiv 官方亦不支持；自创只会造成与官方不一致的诡异行为（D6） |
| 用 `translated_name` 检索 | 实测大量标签无中文翻译（值为 `None`），会静默降级（D5） |
| 重排标签以人为定义「相关性」 | `tags` 已是官方关联度降序；重排会引入我们自己的、未经验证的权重（D2） |
| 新建独立检索实现 | 既有 `@pictelio/search-core` 已是真值 oracle，另起一套必然漂移（D8） |
| 做「相册选图搜」作为同功能入口 | 输入源与语义完全不同；且与本站内标签近邻无共享逻辑 |
| **纯全站降维（无作者优先阶段）** | 匹配度只能隐含于「用了几个标签」，无法算出可显示的相似度；噪音大（同标签的他人作品混入）；D2 的实测表明作者阶段成本仅 ≈10 次请求，却能换来精确相似度与零噪音，性价比不对称 |
| **作者阶段也逐层放宽** | **API 成本在「拉列表」不在「算相似度」**——分页成本已付，本地算 Jaccard 零成本；逐层放宽会把已拉数据浪费掉且多发请求 |
| **逐图调 `/v2/illust/detail` 取标签** | N 个作品 = N 次请求（300 张 = 300 次）；实测 `/v1/user/illusts` 已自带 tags，完全不必要 |
| **阶段 1 扫全量作者作品** | 活跃画师可达数千张，分页数不可控；且老作品与当前作品的标签关联度随时间衰减，收益递减 |
| **相似度用「共同标签数」而非 Jaccard** | 单纯数共同标签会偏爱标签少的小集合（一作品 1 个共同标签 vs 十作品 4 个），对集合规模不敏感；Jaccard 是标签集相似度的标准口径（D4） |
| **相似度用「包含率 = 共同/当前标签数」** | 分母固定为当前作品数，对「对方标签特别多」的作品天然失真（共同 3 / 当前 5 = 60% 会盖过 共同 2 / 当前 2 = 100%） |
| **作者作品用 `translated_name` 运算** | 实测大量标签无中文翻译（`None`），会静默丢配（D10） |
| **标签数 < 2 时仍跑阶段 1** | Jaccard 几乎必然全低分（并集规模主导），无区分度；应直接跳阶段 2 并说明（D8） |
| ~~**阶段 2 统计用本页条数而非 `total`**~~ | ⚠️ **本行前提被实测否证，见 §更正记录 1**：`total` 字段不存在，「用本页条数」在本项目的 30 条/页 + 5 条阈值下是**可靠**的。原判断错误 |
| webview 端同批实现 | webview 正在下线（#607），本期 lynx-only |

## 后果

- 正面：补上一个**零原生改动、零新增依赖、零第三方依赖**的能力；绕开了 ADR-0196 里全部三重技术风险；检索行为完全可控且**可解释**（每层能标注「用了几/几个标签」）；与既有搜索核心共享参数真值。
- 取舍（已接受）：能力边界收窄为「Pixiv 站内相似作品」，**放弃站外出处查找**（已另立词条「站外溯源」并标注当前不做，将来若重启，ADR-0196 的调研结论可直接复用）；含空格标签名存在失配（跟随官方行为）；阈值 5 为固定值，未做用户可配。
- 风险：连续多层请求会放大对 Pixiv App API 的压力（**限流退避尚未在 API 层通用化**——见 ADR-0196 §后果中记录的生态普遍短板）；阈值过松可能导致单层返回大量结果。
- 后续候选（不在本期）：把放宽过程做成可手动推进的「再放宽」交互（当前为自动到阈值即停）；按「共同标签数」标注每条结果；长按某页入口（透传可行性见 ADR-0196）。

> 本节记录**在实施阶段被一手实测否证的决策**。保留原文与理由以便追溯，不删除（沿用 ADR-0196「被自证否证的推测」条目的做法）。

### 更正 1（2026-09-27）：D6 的「必须用服务端 `total`」——该字段不存在

**初稿断言**（已作废）：
> 阶段 2 的终止条件：某层检索结果的**服务端 `total` ≥ 5** 即停。
> ⚠️ 计数必须用服务端 `total`，不得用本页条数——若用本页条数，分页上限填满时第一层几乎必然被误判为"够 5 条"，**放宽序列将完全失效**。

**实测证据**（`bash docs/research/verify-tag-neighbors-api.sh`，2026-09-27 一手抓取）：

| 端点 | 响应顶层键 | 结论 |
|---|---|---|
| `/v1/search/illust`（单词 / 多标签） | `illusts`, `next_url`, `search_span_limit` | **无 `total`** |
| `/v2/search/illust` | `error` | **端点不存在**（404「指定されたエンドポイントは存在しません」） |
| `/v2/illust/related`（对照） | `illusts`, `next_url` | 同族端点亦无 `total` |

`PixivIllustListResponse`（`packages/app-lynx/src/api/types.ts`）只有 `{ illusts, next_url }`——**app-lynx 全仓零 `per_page`／零 `page` 端点参数**（grep 确认），分页一律走 `next_url` 游标。故"服务端总数"在本项目的检索链路上**无法取得**，初稿要求不可实现。

**同时被否证的还有初稿的担心本身**。实测「结果集不足一页时 `next_url` 必为 `null`」：

| `word` | 本页条数 | `next_url` |
|---|---|---|
| `原神` | 30（满页） | `SET` |
| `ホビィ` | 4 | **`null`** |
| `川崎 Sera` | 0 | **`null`** |
| `zhni 拼图` | 0 | **`null`** |

于是「本页条数 ≥ 5」在 30 条/页 + 5 条阈值下是**可靠**的：满页恒为 30（≫5），本页 ≥5 蕴含全站 ≥5；不足一页时 `next_url=null`，本页即全量。

**更正后的判据（D6 现行）**：

```
enough(layer) = len(layer.illusts) >= 5
```

**正确性依赖的不变量（须在测试中钉死）**：Pixiv 检索固定 30 条/页，且结果集不足一页时 `next_url` 为 `null`。若将来调整阈值使其**超过页大小**，或出现「本页不足一页但仍有下一页」的异常态，本判据失效——届时须改为按 `next_url` 继续翻页累计。

**被否证的连带产物**：spec 的第 5 条断言（「构造本页满 30 条但 `total` 为 3」的响应并断言继续放宽）**对应一个 API 无法产生的响应**（30 条与 total=3 自相矛盾），属手写自洽 fixture。已改为用**一手抓取的真实样本**（`ホビィ` 4 条 + `next_url=null`）断言「页大小与阈值的关系是判据成立的前提」。

### 更正 2（2026-09-27，实施后 code-review B1/B2）：D16「不做静默过滤」的落地方式

**D16 原文**：「检索结果须过既有 `R18/R18G` 三态过滤，**不做静默过滤**；受限条目按既有语义呈现。」

用户无从知道「结果里少了东西」。独立 code-review 判为阻塞项（对照 spec user story 27

`gatedCount`（被门控拦下的条目数，两阶段都计），store 透出，页面渲染成一行可见说明
