# app-lynx 集成 vue-tsc 统一术语表

> 范围：`packages/app-lynx` **类型检查工具从 `tsc` 切到 `vue-tsc`** 的统一术语。结论来源：[ADR-0144-app-lynx-vue-tsc.md](./ADR-0144-app-lynx-vue-tsc.md)（2026-09-10 接入，17 个 vue-tsc 报错、3 个为真运行时 bug、13 个为 tsc 静默放过但实则违规）。本表只定义领域语言，不写实现；具体改动以分支 `feat/app-lynx-vue-tsc` 实际 diff 为准。

## 核心术语

| 术语 | 定义 | 与 tsc 对照 |
|------|------|--------------|
| **vue-tsc** | Vue 官方 `vue-tsc` 命令行：把 `.vue` SFC 拆成 `<script>` / `<template>` / `<style>` 三段，分别用 TS compiler + `@vue/compiler-sfc` 类型化模板，再统一过 TypeScript 检查。本项目装 `vue-tsc@^3.3.11`（与 TS 5.7+ 配套）。_Avoid_: 期望 vue-tsc 解析 template 内 JS 表达式为 JS 语法（非 TypeScript 表达式——模板里写 `foo.bar` 推断不了 foo 的具体类型，由 `@vue/compiler-sfc` 的 `defineProps` / `withDefaults` 推导路径主导）；把 vue-tsc 当 ESLint 替代（**它只查类型，不查风格**——app-lynx 风格由 oxlint/vp lint 承担，ADR-0144 §4）。 | 原 `tsc` 命令行：纯 TypeScript，**对 `.vue` 文件静默跳过**（`files`/`include` 命中后只解析 TS 部分，template 0 文件参与） |
| **check 脚本（app-lynx 侧）** | `packages/app-lynx/package.json` 的 `"check"` 命令。`tsc --noEmit -p src/tsconfig.json`（旧）→ `vue-tsc --noEmit -p src/tsconfig.json`（新）。`-p src/tsconfig.json` 仍是单一事实源（`vueCompilerOptions.plugins: ["vue-lynx/types/volar-plugin"]` 已配置）。_Avoid_: 在 check 脚本里写 `tsc && vue-tsc`（双跑耗时 ×2、且两者对 .ts 重复检查，无收益）；改 check 跳过 vue-tsc（直接回到盲区——vue-tsc 暴露的 17 错都查不到）。 | 一对一替换；脚本名 `check` 不变（其它包/根命令引用） |
| **泛型 SFC（generic SFC）** | `<script setup lang="ts" generic="T">` 语法（Vue 3.3+）：让 SFC 的 `defineProps<...>` / `defineSlots<...>` 等宏**带类型参数**。本项目典型用法：`CarouselSwiper.vue` 改为 `generic="T"` + `slides: T[]`，把滑页条目类型透传到 `#slide` 插槽（之前 `slides: unknown[]` 致 Recommended 拿不到 `MixFeedItem`）。_Avoid_: 在 `<script setup generic="T">` 内**首条语句就写 `declare`**（vue-tsc 无法把后续 import 提升出生成的 setup 作用域——本次踩坑：把 `declare const SystemInfo` 留在 import 之前 → TS1184「Modifiers cannot appear here」+ TS1232「import 只能用于顶层」+ TS2307「找不到模块」三连报。**正确顺序：import 在前，declare 在后**或声明挪到全局 d.ts）；泛型 SFC 内部不能用 `withDefaults` 配 `declare` 局部（必须全局声明 + 引用处可选链守）。 | 不支持（普通 SFC 的 `defineProps` 不能带泛型参数） |
| **vue-lynx volar 插件** | `vue-lynx/types/volar-plugin`（项目内 `src/tsconfig.json` 的 `vueCompilerOptions.plugins` 已挂）：vue-lynx 团队给 volar/vue-tsc 的扩展插件，提供 lynx 内置标签（`<view>`/`<text>`/`<list>`/`<list-item>` 等）的类型识别（`isNativeTag`）+ 修饰符守门（`.capture`/`.passive` 等不支持的修饰符报 SyntaxError code 1001）。本项目接入 vue-tsc 不需额外配置。_Avoid_: 自己再写一份同名插件（重复实现 + 漏掉 lynx 团队对 M3 标签的私有元数据）；在 volar 插件里加自定义模板类型转换（volar plugin API 不支持 transform AST 类型节点，只能 resolveTemplateCompilerOptions）。 | tsc 完全不走模板编译路径，**模板相关错误一概查不到**（vue-tsc 接入后暴露出 4 处 template 类型错误，全部在 Recommended/CarouselSwiper 链路） |
| **runtime bug 抓出（vue-tsc 副作用）** | 接入 vue-tsc 顺便抓到 tsc 静默放过的运行时 bug：① `useSettingsStore().ugoiraMode` / `.detailQuality` 在 Pinia 迁移后变为**普通值**（非 ref），原调用点却写 `ugoiraMode.value` → 运行时传 `undefined`；`resolveQualityUrl(undefined, …)` 走 `default` 兜底返回空串 → 详情图全白。② `loadFollow(restrict, signal)` 首参是 restrict（信号在第二位），与 `loadRecommended(signal)` 签名位不同；旧 `const first = m === 'recommend' ? loadRecommended : loadFollow; first(signal)` 联合后，关注模式下 `signal` 落到 `restrict` 位 → 请求参数变 `[object AbortSignal]`、abort 丢失。③ `NovelDetail.vue` 用 `let prompt: WatchlistPromptController \| null` 在模板读 `prompt?.watchAdded`/`?.dialogOpen`——CFA 把 `let` 收窄成 `never`、实例替换不触发重渲染（弹窗状态、追更徽标均失效）。修复：① 改 `const settings = useSettingsStore()` + `settings.ugoiraMode`；② 改为两分支显式调用 `loadFollow('public', signal)`；③ `let` 改 `shallowRef`、模板读 `prompt.value?.xxx`。_Avoid_: 把这类 bug 当"类型噪声"忽略（`unknown`/`never`/参数位错配都是**编译器送上门的事故线索**）；**只调 `.value` 不读 .ts 文件**（类型系统已经告诉你传参错位了）。 | tsc 全部静默——`.value` 在普通值上是合法属性访问（值为 undefined 不报错）、`first(signal)` 在联合函数类型下被视作签名最宽泛的兼容、`let null` 在模板里被推断为 `never` 但不阻断编译 |
| **shallowRef 替换 let（响应性修复）** | `NovelDetail.vue` 的 `prompt` 控制器实例：**`let prompt: T \| null` 在模板里读 → 不响应**（赋值 `prompt = newController` 不触发依赖追踪）→ 需改 `const prompt = shallowRef<T \| null>(null)` + 读 `prompt.value`、写 `prompt.value = newController`。shallowRef（vs ref）：控制器内部已是响应式（Vue reactive），不需深代理——`ref` 会多余代理一层且性能无收益。_Avoid_: 用 `ref(null)`（多余深代理）；用 `reactive({ prompt: null })`（深响应 + 失去 swap 语义清晰度）；保留 `let` + 强制重新渲染（与「先渲染后加载」硬约束相悖——状态翻转需可追踪）。 | tsc 静默放过 `let` + 模板读，运行时表现为「弹窗状态、追更徽标偶发不更新」——只有 vue-tsc + 模板类型推导同时才能抓出 `never` |
| **rest 参数位语义（loadFollow / loadRecommended 签名差）** | `loadFollow(restrict, signal)`：restrict 是首参，signal 是第二；`loadRecommended(signal)`：signal 是首参。把两者**联合成一个函数值**再 `first(signal)` 调用时，TS 按"两者参数列表并集的最宽泛形态"推断 `first: (signal: AbortSignal) => Promise<…>`，类型层绿、运行时 signal 落到 restrict。_Avoid_: 任何"首参位置不同的多态函数"用条件表达式联合（要么重载 `function load(restrict?, signal?)`，要么彻底走分支独立函数调用）；用 `as never` 强转（绕过类型即绕过错位检查）。 | tsc 5.x 在 `m === 'recommend' ? loadRecommended : loadFollow` 这种条件表达式里同样误推断——**vue-tsc 接入是首触发场景**，但 tsc 也会查。**区别**：vue-tsc 在 `.vue` 脚本里跑、tsc 在 `.ts` 里跑，本项目这一处恰好都在 .vue script setup——vue-tsc 抓到 |
| **declared but unused 抑制（`verbatimModuleSyntax`）** | app-lynx 沿用 `verbatimModuleSyntax: true` + `noUnusedLocals/Parameters` 等同于关闭的策略。**vue-tsc 接入未触发类型变化**（这两个规则行为一致），但 vue-tsc 在解析模板里 `import`/`declare` 时的行为与 tsc 略不同（详见「泛型 SFC」条 `declare` 位置约束）。_Avoid_: 因 vue-tsc 而关闭 `verbatimModuleSyntax`（破坏已上线的 import 风格契约——`isolatedModules`/`verbatimModuleSyntax` 是 .ts 编译与 .vue 解析共享的契约开关）。 | tsc/vue-tsc 行为一致；本项目无新增风险 |
| **check 工具分工** | 接入 vue-tsc 后，app-lynx 的"类型/风格"工具分工：① **vue-tsc**（新）= 类型检查（含 .vue 模板类型）；② **tsc**（仍保留在 `tsconfig.json` 可被 IDE 调用）= TS 部分类型检查（vue-tsc 内部走 tsc 包装）；③ **oxlint / vp lint**（不变）= 风格 + 规则（correctness / suspicious / perf），不含 .vue 模板类型；④ **rspack / SWC**（build 路径，不变）= 编译产物（rspack 走 SWC 转 .vue，**不走 vue-tsc**——vue-tsc 只在 check 时跑、build 路径无影响）。_Avoid_: 让 build 路径走 vue-tsc（rspack 集成 vue-tsc 会把类型检查拖入构建，~10× 慢）；用 vue-tsc 替代 oxlint（vue-tsc 无规则引擎、不会报风格问题）。 | tsc 静默 .vue、lint 不查类型、rspack 不查类型——三工具**正交**互不重叠；接入 vue-tsc 后四工具仍正交（vue-tsc 与 tsc 重叠但分主备，vs lint/rspack 不重叠） |

## 边界约定

- 本表只定义领域语言；vue-tsc 的具体命令参数（`--noEmit -p src/tsconfig.json`）、CarouselSwiper 的 import/declare 顺序约束、NovelDetail 的 `prompt` 浅 ref 改造细节均以 [ADR-0144-app-lynx-vue-tsc.md](./ADR-0144-app-lynx-vue-tsc.md) 与分支 `feat/app-lynx-vue-tsc` 实际 diff 为准。
- vue-tsc 与 rspack（build 路径）**不共用任何编译路径**——rspack 走 `@lynx-js/rspeedy` 的 SWC/Babel 转 .vue，vue-tsc 走 `@vue/compiler-sfc` + TS compiler。两者在项目里互不触发。
- 「declared but unused」等静态规则保持原状（`verbatimModuleSyntax: true`、未开 `noUnusedLocals`）——本次接入**未引入**新的 lint 规则调整。
- vue-tsc 抓出的 3 个 runtime bug（pinia `.value` / `loadFollow` 参数位 / `let prompt` 非响应）属**vue-tsc 副作用**，不是设计目标——后续若 vue-tsc 长期无新发现，**不应**期待它"持续抓 bug"；它的本职是"闭 .vue 盲区"。
