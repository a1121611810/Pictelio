# app-lynx 状态管理 Pinia 迁移统一术语表

> 范围：`packages/app-lynx` **手写模块级 store（`src/stores/*.ts` 的模块顶层 `ref` 单例 + 导出函数）→ Pinia setup store（`defineStore(id, () => {...})`）** 迁移的统一术语。结论来源：官方文档（[vue.lynxjs.org/zh/guide/pinia.md](https://vue.lynxjs.org/zh/guide/pinia.md)：`app.use(createPinia())` + setup store 语法，项目内双端未实证部分以 `docs/research/app-lynx-pinia-feasibility.md` 为准）与现有代码结构分析（`packages/app-lynx/src/stores/` 9 个模块，36 处 import / 19 个消费文件）。本表只定义领域语言，不写实现；实现细节（pinia 单例 seam、各 store 迁移形态、调用方改法）以 ADR 与 spec 为准。

## 核心术语

| 术语 | 定义 | 与旧手写对照 |
|------|------|--------------|
| **手写模块级 store（手写 store）** | app-lynx 现役状态管理模式：模块顶层声明私有 `ref`（如 `_user`），`computed` 导出 getter（如 `isLoggedIn`），普通函数导出 action（如 `loginWithToken`），闭包读写模块级 ref。无状态管理库、无实例概念——模块即单例。语义 = 跨组件共享的全局单例响应式状态。_Avoid_: 用「composable」泛指（composable 指 `useX()` 工厂，每次调用生成独立实例，与本模式不同）；与「页面本地状态」（`<script setup>` 内 ref）混称。 | = 本词条即旧实现（迁移起点）；语义由 Pinia store + 消费方改写维持 |
| **Pinia setup store** | Pinia 的**组合式（setup）**口味：`defineStore(id, () => { const x = ref(...); const g = computed(...); function a() {}; return { x, g, a } })`。state = `ref`、getter = `computed`、action = 普通函数，全部声明在 setup 闭包内；**只有 return 的对象是 interface**，未 return 的 ref 物理上不可达（真私有）。_Avoid_: 选项式（options）口味（state/getters/actions 对象字面量）——与现状代码形态差距大，迁移选择 setup 口味以「原样搬运 + 减 return」完成；把 setup 内未 return 的状态当作 public（它不是——interface 就是 return 对象）。 | 模块顶层 ref + 顶层 computed + 顶层函数 → 全部移入 `defineStore` setup 闭包；`_` 命名约定 → setup 闭包物理封装 |
| **store 实例（useXStore()）** | `defineStore` 的产物是 **store 使用函数**（按约定命名 `useXStore`）。组件 setup / 任意函数内调用 `useXStore()` 得到该 store 的实例（同一 pinia 下**全局唯一**，跨组件共享同一实例）。实例上的属性访问自动解包：`store.isLoggedIn` 是值而非 ref（模板与 script 均如此，无需 `.value`）；解构时用 `storeToRefs` 保响应性。_Avoid_: 把 `useXStore()` 当「每次调用生成新状态」（它返回的是单例实例）；未在 active pinia 存在时调用（抛 `getActivePinia was called with no active Pinia`）；直接解构 store 实例（`const { isLoggedIn } = useXStore()` 丢响应性——要用 `storeToRefs`）。 | `import { isLoggedIn } from '../stores/authStore'`（模块级绑定）→ `const auth = useAuthStore()`（实例属性）；`.value` 访问 → 属性直接访问 |
| **active pinia（活跃 pinia 实例）** | Pinia 的「当前默认实例」全局状态：`app.use(createPinia())` 安装时自动 set；`useXStore()` 无参调用时取 active 实例。**非组件上下文（模块顶层、普通函数）**必须先有 active pinia 或显式传实例 `useXStore(pinia)`。_Avoid_: 假定「模块加载后 useXStore() 一定可用」（可用性 = active pinia 已设置，是**时序契约**不是代码形状保证）；在 `app.use(pinia)` 执行前的模块加载期调用无参 `useXStore()`。 | 无（模块级 ref 天然模块加载即可读）→ 新增时序契约：active pinia 必须先就位 |
| **pinia 单例 seam（src/stores/pinia.ts）** | 迁移引入的共享实例 seam：`export const pinia = createPinia()` 单例模块。`index.ts` 的 `app.use(pinia)` 与所有非组件上下文（router 守卫、测试）**用同一实例**——若各自 `createPinia()` 会生成两个实例，store 状态互不同步（守卫读到空状态是表象，实际是「两个 app」）。_Avoid_: `index.ts` 继续内联 `app.use(createPinia())` 另起实例；把 seam 放组件内（组件卸载即销毁实例，App 级状态丢失）。 | 无 → 新增 seam 位置；它是迁移的「第一行代码」，先于任何 store 改造落地 |
| **时序契约（module-load timing contract）** | 「store 状态在模块加载期即可读」这一现状隐含契约。破坏点：`router.ts` 模块顶层执行 `void router.replace(RECOMMENDED_PATH)`（router.ts:119）→ 首导航触发 `beforeEach` 守卫读取登录态。手写模式：模块求值即就绪，无风险；Pinia 模式：`useAuthStore()` 依赖 active pinia，而 `index.ts` 的 `app.use(pinia)` 在 `import { router }`（模块加载）之后——**守卫首次执行可能落在 `app.use(pinia)` 之前**。虽然不是必然触发（守卫链是 microtask 级），但这是**时序依赖而非契约保证**，必须以显式机制（pinia 单例 seam + 守卫内取实例）落实，spike 第一条验证。_Avoid_: 用「大概率 microtask 来得及」当防御；把 `useAuthStore()` 放模块顶层（在任何 app.use 之前必然抛错）。 | 手写：模块求值 → refs 可用（零初始化）→ Pinia：`app.use(pinia)` 完成后 store 才可用 |
| **消费方（consumer）** | import 或调用某个 store 的代码单元（页面/组件/router/api 模块）。authStore 有 8 个消费文件 + 1 个内部跨 store 消费（settingsStore）；全项目 19 个文件 / 36 处 import。迁移粒度 = 消费方逐个改写（一个 store 一个 commit）。_Avoid_: 把「消费方」与「组件」混称（消费方含 router.ts、settingsStore 等非组件模块）；同一次 commit 混迁两个 store（review 面混淆）。 | 手写：`import { isLoggedIn }`（具名导入）→ Pinia：`useAuthStore()`（实例）+ 属性访问 |
| **跨 store 组合（store-to-store composition）** | 一个 store 的 setup/action 内调用另一个 `useXStore()` 获得依赖（如 `settingsStore` 在 setup 内 `const auth = useAuthStore()` 取 `currentUser` 派生存取账号级键 `show_r18_${uid}`）。**标准 Pinia 姿势**，替代手写模式的跨模块 `import { currentUser }`。_Avoid_: setup 顶层解构；store 间循环依赖（A 的 setup 顶层调 useB、B 的 setup 顶层调 useA——初始化死循环）；在 getter/action 里「为了取值重进 store 图」反复调用（实例是单例，重复调用无害，但读入局部变量更清晰）。 | 手写：`stores/settingsStore.ts` `import { currentUser } from './authStore'`（模块级）→ Pinia：`const auth = useAuthStore()`（组合式取用） |
| **测试隔离（setActivePinia per-test）** | 每个测试/describe 的 `beforeEach` 执行 `setActivePinia(createPinia())`——每用例一个全新 pinia、全新 store 状态，**天然隔离**，无需手写 `resetXxxForTest`。_Avoid_: 不 reset 直接用（用例间状态串扰，与手写单例相同问题）；把 `setActivePinia` 放 `vi.mock` 工厂里（mock 工厂执行时机早于用例前置逻辑）；对需要**真实交互**的 store 用 mock（mock 面缩小为 `useXStore` 一个函数，能 mock 则优先 mock 之，但 auth 语义测试应跑真实 store + setActivePinia）。 | 手写：模块级单例 + `resetXxxForTest()` 手动清 → Pinia：`setActivePinia(createPinia())` 自动隔离；`resetWatchlistStoreForTest`/`resetSearchHistoryForTest` 类测试钩子可删除 |
| **深度模块（deep module）** | codebase-design 术语：**小 interface + 大 implementation**（调用方少量学习换大量行为）+ deletion test（删掉它复杂度会散布到 N 处而非消失）。authStore 现状 7 成员 interface（3 getters + 4 actions）承载双模式 OAuth 编排、持久化时机、永久失效语义、401 接线——删掉 8 个消费方各自内联 token/刷新/失效逻辑，属深度模块。Pinia 化不改变这一判断：换容器不减深度，**私有 ref 封装反而从「`_` 命名约定」升级为「物理不可达」**。_Avoid_: 迁移时顺手「优化」interface（如把 `authError: string` 改成分类对象）——那是行为变更，必须单独 ticket；setup 内已 return 的成员再设 getter 拦截。 | 手写：interface = 具名导出集合；私有性靠 `_` 约定 → Pinia：interface = return 对象；私有性靠闭包 |
| **会话中心（session center）** | authStore 的职责定位（本迁移范围）：app-lynx 的登录态唯一事实源——`isLoggedIn`（`_accessTokenReady` 就绪 ∧ `_user` 非空）/`currentUser`/`authError` 只读视图 + `restoreToken`/`loginWithToken`/`logout`/`registerUnauthorizedHandler` 四个动作。网络层在 `api/client.ts`（store 只编排、不实现）。_Avoid_: 把 client.ts 的 `accessToken` 全局变量「收纳进」store（client 不依赖 store，方向应当保持单向：store → client 的 setter seam）；把 token 放进 Pinia state 重复存储（`_refreshToken` 保留私有 ref 即可）。 | 不变（职责边界不随容器改变）；`api/client.ts` 的 `setAccessToken`/`setOnUnauthorized`/`setAuthPermanentFailure` 是 store 与传输层的 setter seam，迁移后原样保留 |
| **401 自动刷新（auto refresh）** | `client.ts` 遇 401 调 `setOnUnauthorized` 注册的 handler（authStore 的 `performRefresh`），刷新成功重放原请求、失败判定永久失效（OAuth 400 → 清状态 + 弹全屏错误页）。handler 注册点是 `registerUnauthorizedHandler()`（`initRouter` 第一行）——**接线动作是 authStore 的 action 之一**，暴露给调用方；迁移后保留为 action（不内化，避免行为变更）。_Avoid_: 把「注册」塞进 store setup 自动执行（行为变化：store 首次 use 时机提前/推迟对注册时机有影响，须单独 ticket）；注册两次 handler（幂等性由 client.ts 保证，但调用方仍应只调一次）。 | 不变：handler 注册机制、401 重放语义、永久失效判定全部保留 |
| **永久失效（permanent failure）** | OAuth 400（凭证错误/invalid_grant）与网络/解析类错误的区分语义：前者 = `setAuthPermanentFailure(true)` + 清空 `_refreshToken`/`_accessTokenReady`/`_user`（401 刷新失败 → 全屏错误页；登录页输入错 token → 内联错误）；后者 = 仅置 `_authError`，允许重试。迁移后判定逻辑原样搬入 action，**不因容器变化而重构**。_Avoid_: 把 `authError` 裸字符串换成错误分类结构（见「深度模块」——行为变更，独立 ticket）；迁移中改变「哪些错误算永久失效」的判定列表。 | 不变（`err.includes("凭证") || err.includes("invalid")` / `ApiErrorType.UNAUTHORIZED` 分支原样保留） |
| **持久化 seam（tokenStorage）** | `utils/tokenStorage.ts`：双 adapter 真 seam（两个 adapter = 真 seam）——原生 `PictelioSecureStorage`（Keystore）/ web-core `idbKV`（IndexedDB），authStore 只依赖其 Promise 接口。迁移**不触碰**（它不是状态，是 IO 边界）。_Avoid_: 把 tokenStorage 的读写逻辑搬进 store；用 Pinia plugin 做持久化（现状 seam 已满足，不引入plugin 滥用）。 | 不变 |

## 边界约定

- 本表只定义领域语言；每个 store 的具体 interface 形态（return 哪些、私有哪些）、消费方逐条改法、`src/stores/pinia.ts` seam 代码、测试改造点以 `docs/adr/ADR-0139-app-lynx-pinia-migration.md` 与 `docs/specs/app-lynx-pinia-migration.md` 为准。
- 迁移**范围分两批**：第一批 = `authStore`（试点，8 消费方 + 3 测试文件）；第二批 = `searchHistoryStore`/`searchSheetStore`/`modalStack`/`clientSwitchStore`/`updateStore`/`settingsStore`（6 个，确认试点后逐个迁移）。`watchlistStore`（非响应式 Set/Map 缓存）与 `globalFab`（惰性工厂接线，非状态 store）**明确排除**——它们不是「模块级 ref 单例」，Pinia 化无收益。
- 「实例级 composables」（`primitives/useSearch`、`createMixFeed` 等，每次调用独立实例、生命周期绑定页面）**不在迁移范围**——它们是与「全局单例 store」语义相反的东西，强迁会破坏「页面独有数据由组件管理生命周期」硬约束。
- 迁移是**纯重构**（行为不变约定，AGENTS.md「重构行为不变约束」）：字段名、常量、默认值、错误文本、判定逻辑、持久化键、注册时机**全部不得改动**；任何「借机优化」都违反门禁，须单独 ticket。
